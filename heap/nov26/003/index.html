Lesson 3: TF32, Choosing FP32 Islands and NaN Forensics

0. Interview skills

  1. Explain what TF32 changes and what it does not. Configure it with the current PyTorch API and say when to switch it off.
  2. Decide which ops need FP32, including the ones autocast does not know about. Justify each choice with Lesson 1 numbers.
  3. Run a structured NaN investigation: when, reproduce, which stage, where, why, fix.
  4. Recognize the classic NaN traps on sight: sqrt(0), the torch.where gradient trap, fully masked softmax, 0·log 0, and FP16 epsilon underflow.

2. TF32: FP32 range, FP16 precision, only inside GEMMs and convolutions

2.1 Format (compare with Lesson 1)

FormatSign / Exp / MantissaUnit roundoff uMax
FP321 / 8 / 232−24 ≈ 6.0e−8≈ 3.4e38
TF321 / 8 / 10 (19 bits used, stored in 32)2−11 ≈ 4.9e−4≈ 3.4e38

2.2 What TF32 actually does

  • On Ampere and newer Tensor Cores, the inputs of an FP32 matmul or convolution are rounded to TF32. Products are accumulated in FP32, and the output is FP32.
  • Storage does not change. Tensors stay torch.float32, so TF32 does not save any memory.
  • The error comes mostly from rounding the inputs. The normwise relative error is about 1e−4 to 1e−3 and is roughly independent of K. Lab part 1 measures it.
  • Elementwise ops, reductions and softmax are not affected. They run in normal FP32.

2.3 Controls in current PyTorch

ControlValuesNotes
torch.backends.cuda.matmul.fp32_precision"ieee", "tf32"Current API for CUDA matmuls. The main docs also list a BF16x9-emulation value. Check its exact name and availability for your version.

torch.backends.cuda.matmul.fp32_precision = "ieee"   # strict FP32 math
print(torch.backends.cuda.matmul.fp32_precision, torch.get_float32_matmul_precision())

2.4 When to use "ieee"

  • Linear algebra on ill-conditioned matrices: solves, inverses, eigendecompositions, Cholesky. Error is amplified by the condition number κ.
  • Reference implementations, unit tests with tight tolerances, and numerical gradient checks.
  • Comparisons across hardware. "Results differ between V100 and A100" is often TF32, because convolutions had it on by default.
  • Scientific or simulation code where FP32 accuracy is part of the specification.
Island trap: an FP32 island (autocast(enabled=False) plus .float()) still runs its matmuls in TF32 if TF32 is enabled. "FP32 island" means FP32 storage and FP32 elementwise math. It does not automatically mean IEEE GEMMs.

3. Choosing FP32 islands

Autocast already handles its lists (softmax, losses, norms). Your job is the ops it does not know about: custom math, positional encodings, routers and optimizer-adjacent code. Ask five questions:

#QuestionLesson 1 number
1Range: can the value exceed the format's max or fall below its min (exp, squares, sums of squares, large products)?FP16 max 65504; exp overflows for x > ≈11.09
2Cancellation: do you subtract nearly equal numbers, as in E[x²] − E[x]²?Relative error is amplified by |a| / |a − b|
3Accumulation / swamping: are many small terms added to a large one (long sums, w + lr·g)?An update below ulp/2 is lost: BF16 at 1.0 has ulp 2−7
4Integers / discretization: are positions, indices or timesteps stored as floats?Exact integers only up to 256 (BF16) and 2048 (FP16)
5Decisions: does a small numeric difference flip a discrete choice (argmax, top-k, routing)?BF16 spacing near 1 is ≈ 0.008

3.1 Catalogue

CandidateRisk (question #)Typical treatment
Logits → cross-entropy over a large vocabulary1, 3Autocast already runs CE in FP32. Pass logits.float() into custom losses, and use log_softmax instead of log(softmax).
Attention scores / softmax1, masked rowsUse fused SDPA / FlashAttention, which accumulate in FP32 with an online softmax. Scale by 1/√d. Watch logit growth.
Normalization statistics2, 3Compute statistics in FP32 (Welford or a two-pass algorithm). Autocast does this for its listed norms. Custom RMSNorm should do x.float() before pow/mean/rsqrt.
RoPE / sinusoidal positions4, 1Compute pos · inv_freq and sin/cos in FP32, then cast the result.
MoE router logits / softmax / top-k5Run the router in FP32. The Switch Transformer used "selective precision" (verify).
Weights, optimizer states, update3FP32 parameters/master weights and FP32 Adam states (Lesson 2).
Grad norms, metrics, loss averaging across steps3Accumulate in FP32.
Custom exp/log/pow, diffusion schedules, timestep embeddings1, 4Use FP32 or work in log space.
Cost model: islands are usually elementwise ops or reductions, which are memory-bound. The FP32 math is nearly free. You pay for bytes moved and extra cast kernels, and for FP32 activations saved for backward. Keep islands small and fuse them where possible (e.g. torch.compile). Don't put GEMMs in islands unless you have to.

4. NaN forensics

4.1 Workflow

StepQuestionHow
1 · WhenWhat is the first non-finite step? Were there precursors?Cheap telemetry: loss, grad norm, loss scale, max|activation| per block. Accumulate on the device and sync only every N steps.
2 · ReproduceCan you trigger it on demand?Resume from the last good checkpoint with the same seed and data order. Save the offending batch.
3 · StageForward, backward, optimizer or communication?Loss non-finite → forward. Loss finite but grads not → backward. Grads finite but params NaN after step() → optimizer. One rank bad before all-reduce → that rank's data or hardware.
4 · WhereWhich op?Forward hooks: find the first module whose inputs are finite and outputs are not. For backward, run torch.autograd.detect_anomaly(check_nan=True) on that single step (slow).
5 · WhyWhat about its inputs?Check magnitude vs. format max, exact zeros, masks, dtype, and the data.
6 · FixFix the cause, not the symptomnan_to_num or skipping steps only hides the bug.

4.2 Common sources

PatternSymptomFix
sqrt(x) at x = 0 (hand-written norms, pairwise distances, std)Forward is fine. Backward gives Inf, which becomes NaN via 0·Inf.clamp_min(eps) or eps inside the sqrt; torch.linalg.vector_norm

Division by zero variance or an empty countInfeps; guard against empty batches and masks
FP16 epsilon underflow (1e−8 → 0)0/0 in Adam or normalization running in FP16Do that math in FP32 (FP16's smallest subnormal is ≈ 6e−8)

Divergence (logit / activation growth)Loss spikes and rising max|act| before the NaNLR/warmup, clipping, QK-norm, z-loss (verify refs)
Bad dataReproducible at one specific batchAssert isfinite on inputs; validate labels
Uninitialized memory (torch.empty)Non-deterministic NaNszeros, or make sure every element is written
Every isfinite(...).item() is a device→host sync. In production, accumulate flags on the device and check them every N steps. Use hooks and anomaly mode only during debugging. With DDP, a NaN on one rank reaches every rank through the all-reduce, so check per-rank values before reduction.

5. Interview answers (30 s each, say them out loud)

"Should we enable TF32?"
"TF32 keeps FP32 range but rounds GEMM and conv inputs to a 10-bit mantissa, then accumulates in FP32. Storage stays FP32, so it buys speed, not memory. For DL training it's usually fine. I set fp32_precision="ieee" for solvers, reference tests and cross-hardware comparisons. allow_tf32 is deprecated now. Also, FP32 islands still use TF32 GEMMs unless I switch them to IEEE."
"What do you keep in FP32 in BF16 training?"
"Weights and optimizer states, because of swamping. Softmax, losses and norm statistics, which autocast handles. Then the things autocast doesn't know about: RoPE angles, because BF16 is only exact for integers up to 256; router logits, because top-k decisions can flip; custom exp/log; and metric reductions. My criteria are range, cancellation, accumulation, integers and decisions."
"Loss went NaN at step 40k. What do you do?"
"First the telemetry: was it a sudden NaN or a spike preceded by growing activations or logits? Then I resume from the last good checkpoint with the same data order and save the batch. I find the stage: is the loss non-finite, the grads, or the params after the step? For forward problems I use hooks to find the first module with finite inputs and non-finite outputs. For backward problems I run anomaly mode on that step. Then I fix the root cause, whether it's data, a numeric trap like sqrt(0) or a masked softmax, FP16 overflow, or real divergence, which needs LR/warmup, QK-norm or z-loss. I don't fix it with nan_to_num."

Part 1: TF32 vs. IEEE matmul error (CUDA, Ampere+)

import torch
assert torch.cuda.is_available()
print(torch.cuda.get_device_name(), "capability", torch.cuda.get_device_capability())
print("matmul:", getattr(torch.backends.cuda.matmul, "fp32_precision", "n/a"),
      "| cudnn.conv:", getattr(getattr(torch.backends.cudnn, "conv", None), "fp32_precision", "n/a"),
      "| float32_matmul_precision:", torch.get_float32_matmul_precision())

def set_matmul(mode):                       # "ieee" or "tf32"
    m = torch.backends.cuda.matmul
    if hasattr(m, "fp32_precision"):
        m.fp32_precision = mode             # current API
    else:
        m.allow_tf32 = (mode == "tf32")     # legacy fallback for old PyTorch only

def rel_err(c, ref):
    return ((c.double() - ref).norm() / ref.norm()).item()

torch.manual_seed(0)
for K in (256, 4096, 65536):
    a = torch.randn(256, K, device="cuda")
    b = torch.randn(K, 256, device="cuda")
    ref = a.double() @ b.double()
    err = {}
    for mode in ("ieee", "tf32"):
        set_matmul(mode)
        err[mode] = rel_err(a @ b, ref)
    print(f"K={K:6}: ieee {err['ieee']:.1e}  tf32 {err['tf32']:.1e}  ratio {err['tf32']/err['ieee']:.0f}x")
set_matmul("ieee")
Expected

IEEE: about 1e−7 to 1e−6, growing slowly with K. TF32: about 3–5e−4, roughly flat in K, because input rounding at u = 2−11 dominates. The ratio is in the hundreds to thousands. On pre-Ampere GPUs both errors are the same, because there is no TF32. Note the defaults you printed: the matmul and convolution settings may differ.

Part 2: Integers, swamping, epsilon (CPU)

import torch
pos = torch.arange(4096, dtype=torch.float32)
for dt in (torch.float16, torch.bfloat16):
    p = pos.to(dt).float()
    first_bad = int((p != pos).nonzero()[0])
    print(f"{str(dt):15} distinct={p.unique().numel():5}  first inexact={first_bad}  4095 -> {p[4095].item():.0f}")

for dt in (torch.float32, torch.float16, torch.bfloat16):
    w = torch.ones((), dtype=dt)
    for _ in range(1000):
        w = w + 1e-3
    print(f"{str(dt):15} 1 + 1000 x 1e-3 = {w.item():.7f}")

print("1e-8 in fp16:", torch.tensor(1e-8).half().item(), "| bf16:", torch.tensor(1e-8).bfloat16().item())
m = torch.zeros(1, dtype=torch.float16); v = torch.zeros(1, dtype=torch.float16)
print("Adam-style m / (sqrt(v) + 1e-8) in fp16:", m / (v.sqrt() + 1e-8))
Expected and why
  • FP16: distinct = 3073, first inexact = 2049, 4095 → 4096. BF16: distinct = 769, first inexact = 257, 4095 → 4096. That is why RoPE angles are computed in FP32.
  • FP32 ≈ 2.0000. FP16 = 1.9765625: each +1e−3 rounds to one ulp of 2−10, so the total is 1 + 1000/1024. BF16 = 1.0000000: 1e−3 is below half an ulp (2−8), so every update is lost. This is the master-weights argument in one line.
  • 1e−8 becomes 0.0 in FP16, because it is below half of 2−24. In BF16 it is ≈ 1e−8. As a result, the FP16 expression evaluates to 0/0 = nan.

Part 3: NaN traps (CPU)

import torch
x = torch.tensor([0.0, 4.0], requires_grad=True)
x.sqrt().sum().backward();                                   print("a ", x.grad)

x = torch.tensor([0.0, 2.0], requires_grad=True)
torch.where(x > 0, torch.log(x), torch.zeros_like(x)).sum().backward();  print("b ", x.grad)

x = torch.tensor([0.0, 2.0], requires_grad=True)
safe = torch.where(x > 0, x, torch.ones_like(x))             # double-where fix
torch.where(x > 0, torch.log(safe), torch.zeros_like(x)).sum().backward(); print("b'", x.grad)

s = torch.tensor([[1.0, 2.0, 3.0], [1.0, 2.0, 3.0]])
keep = torch.tensor([[True, True, False], [False, False, False]])
print("c ", torch.softmax(s.masked_fill(~keep, float("-inf")), -1))
print("c'", torch.softmax(s.masked_fill(~keep, torch.finfo(s.dtype).min), -1))

p = torch.tensor([0.0, 0.5, 0.5])
print("d ", (p * p.log()).sum().item(), torch.xlogy(p, p).sum().item())
Expected and why
  • a: [inf, 0.25], because d/dx √x = 1/(2√x).
  • b: [nan, 0.5]. where sends a gradient of 0 into the log branch, and 0 · (1/0) = 0 · Inf = NaN. Masking the forward does not mask the backward.
  • b': [0., 0.5].
  • c: row 0 is [0.269, 0.731, 0], row 1 is NaN, because (−Inf) − (−Inf) = NaN. c': row 1 is uniform 1/3. It is finite but meaningless, so zero fully masked rows explicitly.
  • d: nan vs. −0.6931.

Part 4: Forensics tools

4a: forward hooks (CUDA). The bug is an FP16 overflow that FP32 hides.

import torch, torch.nn as nn

class Scale(nn.Module):
    def __init__(self, s): super().__init__(); self.s = s
    def forward(self, x): return x * self.s

def nonfinite(t):
    return torch.is_tensor(t) and t.is_floating_point() and not torch.isfinite(t).all()

def install_nan_hooks(model):
    """Debug only: every check is a device-to-host sync."""
    report, handles = [], []
    for name, mod in model.named_modules():
        if not name:
            continue
        def hook(m, inp, out, name=name):
            outs = out if isinstance(out, (tuple, list)) else (out,)
            if any(nonfinite(t) for t in outs) and not any(nonfinite(t) for t in inp):
                amax = max((t.abs().max().item() for t in inp if torch.is_tensor(t)), default=float("nan"))
                report.append(f"{name} ({type(m).__name__}): finite in (max|x|={amax:.3g}) -> non-finite out, {outs[0].dtype}")
        handles.append(mod.register_forward_hook(hook))
    return report, handles

torch.manual_seed(0)
model = nn.Sequential(nn.Linear(64, 64), nn.GELU(), Scale(1e6),
                      nn.Linear(64, 64), nn.LayerNorm(64), nn.Linear(64, 1)).cuda()
report, handles = install_nan_hooks(model)
x = torch.randn(32, 64, device="cuda")
for amp in (False, True):
    report.clear()
    with torch.autocast("cuda", dtype=torch.float16, enabled=amp):
        loss = model(x).float().pow(2).mean()
    print(f"amp={amp}: loss={loss.item():.3g}", report or "no non-finite values")
for h in handles:
    h.remove()
Expected

With amp=False, the loss is finite because LayerNorm rescales the ~1e6 activations. With amp=True, the loss is nan and the report points at 2 (Scale): the max |x| is about 2–3, and ×1e6 exceeds 65504. If your version runs GELU in FP32, the report points at 3 (Linear) instead, because the overflow happens in its FP16 input cast. LayerNorm is not reported because its input was already non-finite, and that is exactly why the "first finite-in / non-finite-out" rule works. With GradScaler, this bug would show up as "S halves every step".

4b: anomaly mode (CPU). The example is a hand-written distance at zero, e.g. identical embeddings.

import torch
x = torch.zeros(4, 3, requires_grad=True)
try:
    with torch.autograd.detect_anomaly(check_nan=True):   # forward must also run inside the context
        dist = torch.sqrt((x ** 2).sum(-1))
        dist.sum().backward()
except RuntimeError as e:
    print("anomaly:", str(e).splitlines()[0])

x.grad = None
torch.linalg.vector_norm(x, dim=-1).sum().backward()
print("vector_norm grad finite:", torch.isfinite(x.grad).all().item())
x.grad = None
torch.sqrt((x ** 2).sum(-1).clamp_min(1e-12)).sum().backward()
print("clamped grad row 0:", x.grad[0])
Expected

Something like Function 'PowBackward0' returned nan values in its 0th output. The exact name depends on the version. A warning shows the forward traceback of x ** 2. Note that SqrtBackward0 produces Inf, which anomaly mode does not flag, and the NaN appears one op later as Inf · 2 · 0. vector_norm → True, because it uses a zero subgradient at 0 (verify on your version). The clamped grad row is zeros.
