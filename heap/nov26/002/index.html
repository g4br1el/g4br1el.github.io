Lesson 002

Lesson 2: Autocast Op Policy, GradScaler Internals and Memory Accounting

0. Interview skills

  1. Predict the output dtype of any op under autocast and justify the policy using Lesson 1 numbers.
  2. Walk through one GradScaler iteration at the kernel/state level, including where it syncs with the host.
  3. Read a loss-scale trajectory and diagnose what is wrong.
  4. Do memory accounting for model states out loud: bytes per parameter, ZeRO stages, and when AMP does not help.

1. Warm-up (recall from Lesson 1, no notes)

FP16 smallest subnormal = 2k. What is k?

k = 1 − 15 − 10 = −24 (≈ 5.96e−8).

Why is FP8 E4M3 max 448 and not 240?

It has no Inf and only S.1111.111 is NaN, so the top exponent field is usable: 28 · 1.75 = 448.

Does TF32 halve tensor memory?

No. It is a Tensor Core math mode. Storage stays FP32.

2. Autocast: a per-op cast policy, not a model conversion

torch.autocast intercepts ops at the dispatcher level. For each op it checks a policy list and casts that op's inputs. The model's parameters are never modified. That is why native AMP keeps FP32 parameters, as covered in Lesson 1.

2.1 The four categories (CUDA)

CategoryExamplesWhy (Lesson 1 link)
Cast to FP16/BF16mm, matmul, bmm, addmm, baddbmm, linear, conv1d/2d/3d, conv_transpose*, prelu, RNN cellsThese are Tensor Core GEMMs. The kernel already accumulates in FP32 internally, so low-precision inputs are safe.
Cast to FP32exp, log, pow, rsqrt, reciprocal, softmax, log_softmax, logsumexp, cumsum, layer_norm, group_norm, norm, most losses (mse_loss, nll_loss, l1_loss, kl_div, binary_cross_entropy_with_logits, …)Range: exp(x) overflows FP16 for x > ≈11.09 (ln 65504), and x² overflows for |x| ≥ 256. Precision: long reductions get swamped.
Promote to widest inputcat, stack, addcmul, addcdiv, atan2, bilinear, cross, index_put, scatter_add, tensordotMixed-dtype inputs would otherwise error or silently lose precision.
Unlistedrelu, add, mul, dropout, view ops, batch_normThese run in the dtype their inputs already have, using standard type promotion. FP16 + FP32 → FP32.

Special case: F.binary_cross_entropy / nn.BCELoss raise an error under autocast. Use BCEWithLogitsLoss, which fuses sigmoid and log stably.

These lists are version-dependent. The authoritative source is the "Autocast Op Reference" in the torch.amp docs for your installed version. Lab part 1 checks them empirically.

2.2 Rules interviewers probe

  • Wrap only the forward pass and the loss. Backward ops automatically run in the dtype of their forward op. Wrapping backward() is unnecessary and not recommended.
  • Cast cache: inside one autocast region, each FP32 leaf tensor that requires grad (i.e. each parameter) is cast once and cached. The FP16 copy can stay alive until backward, because GEMMs save it for the weight-gradient computation.
  • In-place ops and ops with explicit out= are not autocast.
  • Gradients come back in FP32. The backward of the FP32→FP16 cast produces an FP32 .grad on the parameter. This is what GradScaler relies on.
  • BF16 autocast on CUDA uses the same lists, with BF16 as the low-precision type. CPU autocast has its own lists and defaults to BF16.

2.3 FP32 islands: manual overrides

with torch.autocast("cuda", dtype=torch.float16):
    h = backbone(x)                          # FP16 GEMMs
    with torch.autocast("cuda", enabled=False):
        logits = head(h.float())             # explicit cast is REQUIRED:
                                             # disabling autocast does not upcast h
loss = criterion(logits, y)

# For custom autograd Functions:
#   @torch.amp.custom_fwd(device_type="cuda", cast_inputs=torch.float32)
#   @torch.amp.custom_bwd(device_type="cuda")

A common bug: the nested enabled=False region receives FP16 tensors and keeps them in FP16, so the "island" silently runs in FP16. Lesson 3 covers how to choose which ops need an island.

3. GradScaler internals

3.1 State

  • _scale: a 1-element FP32 device tensor. It is kept on the device so that scaling never forces a host sync. get_scale() does sync.
  • _growth_tracker: a device int tensor that counts consecutive clean steps.
  • Per-optimizer state: stage (READY → UNSCALED → STEPPED) and a found_inf flag per device.

Defaults (verified, PyTorch AMP docs): init_scale=2**16, growth_factor=2.0, backoff_factor=0.5, growth_interval=2000.

3.2 One iteration

CallWhat happensInterview detail
scale(loss)Returns loss * S. The scale tensor is created lazily on first use.Backward intermediates in FP16 are lifted away from the 2−24 underflow floor.
unscale_(opt)One fused foreach kernel per device/dtype multiplies every .grad by 1/S and sets found_inf if any value is Inf or NaN.Must run before clipping or any norm logging. Calling it twice before update() raises an error. FP16 grads raise ValueError.
step(opt)Unscales if not done already. Then calls opt.step() only if no found_inf is set; otherwise the step is skipped.The default path reads found_inf with .item(), which is a device→host sync every step. Fused optimizers that support AMP scaling (e.g. AdamW(fused=True)) receive the scale and flag directly and avoid the sync (verify for your version).
update()Combines the flags from all optimizers and devices, then adjusts S (see 3.3).Call it once per iteration, after all step() calls.

3.3 The update rule

# semantics of torch._amp_update_scale_
if found_inf:
    scale *= backoff_factor          # 0.5
    growth_tracker = 0
else:
    growth_tracker += 1
    if growth_tracker == growth_interval:   # 2000
        scale *= growth_factor       # 2.0
        growth_tracker = 0

The result is a sawtooth: S rises until it hits the overflow boundary, halves, and rises again. S tracks the largest safe power of two, within about 2×. With default settings, S often starts too high, so the first few steps are skipped. This is also why you see the warning "lr_scheduler.step() called before optimizer.step()".

3.4 Diagnosing from the scale trajectory

PatternLikely meaningAction
Sawtooth around a stable level, rare skipsHealthyNone
A few skips at the start, then stableinit_scale too high (normal)Ignore, or lower init_scale
Skips every step, S falls toward 0The non-finite value does not depend on S: forward activation > 65504, log(0), division by zero, bad data, or diverged weightsLoss scaling cannot fix this. Do NaN forensics (Lesson 3): hooks, detect_anomaly, data checks
Frequent skips mid-trainingGradient spikes or instabilityCheck LR/warmup and clipping; consider BF16
Key insight: loss scaling only solves the gradient range problem in backward. It cannot fix forward overflow, because the forward pass runs before any scaling is applied.

3.5 Production recipes

# Gradient accumulation: S must stay constant within one effective batch
for i, (x, y) in enumerate(loader):
    with torch.autocast("cuda", dtype=torch.float16):
        loss = loss_fn(model(x), y) / accum
    scaler.scale(loss).backward()          # with DDP: wrap non-boundary steps in model.no_sync()
    if (i + 1) % accum == 0:
        scaler.unscale_(opt)
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        scaler.step(opt)
        scaler.update()                    # exactly once per effective batch
        opt.zero_grad(set_to_none=True)

# Checkpointing: the scale is part of training state
ckpt = {"model": model.state_dict(), "opt": opt.state_dict(), "scaler": scaler.state_dict()}
  • Multiple optimizers or losses: use one scaler. Call step() for each optimizer, then update() once.
  • DDP: the all-reduce spreads Inf/NaN to every rank, so all ranks skip the same steps.
  • FSDP: each rank sees only its own gradient shard. Use ShardedGradScaler, which all-reduces found_inf across ranks (verify).
  • BF16: no scaler needed, because BF16 has FP32's exponent range (Lesson 1).

4. Memory accounting

4.1 Model states (persistent, bytes per parameter)

SetupBreakdownB/param
FP32 + Adamw 4 + g 4 + m 4 + v 416
Native AMP + Adamw 4 (FP32) + g 4 (FP32) + m 4 + v 416
Classic MP / ZeRO accountingw 2 + g 2 + master 4 + m 4 + v 416

On top of this, native AMP adds up to about 2 B/param transiently for cached FP16 weight casts. These partly overlap with gradient allocation, because backward frees casts while it creates grads. Optimizer kernels also allocate temporary buffers. Measure them in Lab part 4.

4.2 Activations: where AMP actually saves memory

  • Tensors saved by FP16 ops (GEMM inputs) take half the memory.
  • Tensors saved by FP32-list ops (softmax output, layer_norm, losses) stay FP32. So "AMP halves activations" is an approximation.
  • If the model is parameter-dominated (small batch), AMP barely reduces peak memory. If it is activation-dominated (large batch or long sequences), AMP helps a lot.
Stretch: transformer activation formula (verify)

Korthikanti et al. (2022) estimate activation memory per layer, without recomputation and with 16-bit activations, as s·b·h·(34 + 5·a·s/h) bytes (s = sequence length, b = batch, h = hidden size, a = heads). The a·s² term comes from attention scores and is what fused attention removes.

4.3 ZeRO: sharding the 16 bytes (Ψ = params, Nd = data-parallel GPUs)

StageShardsPer-GPU model states
Baseline DPnone16Ψ
ZeRO-1optimizer states (12 B)4Ψ + 12Ψ/Nd
ZeRO-2+ gradients2Ψ + 14Ψ/Nd
ZeRO-3 / FSDP full shard+ parameters16Ψ/Nd

Paper sanity check (verify): Ψ = 7.5B, Nd = 64 gives 120 → 31.4 → 16.6 → 1.9 GB. PyTorch FSDP's mixed-precision accounting differs in detail; that comes in a later lesson.

5. Interview answers (30 s each, say them out loud)

"Walk me through GradScaler."
"scale() multiplies the loss by S, 216 by default, so FP16 backward intermediates don't underflow. unscale_ runs one fused kernel that multiplies the FP32 grads by 1/S and sets a found-inf flag. It must happen before clipping. step() reads that flag, which is a host sync unless the optimizer is fused and AMP-aware, and skips the update on Inf/NaN. update() halves S on overflow, or doubles it after 2000 clean steps. So S follows a sawtooth just below the overflow boundary. If it decays every step, the problem is a non-finite value in the forward pass, which scaling can't fix."
"Where does memory go for a 7B model with AdamW?"
"Model states are 16 bytes per parameter whether or not you use AMP: FP32 weights, FP32 grads, two FP32 Adam moments. That's 112 GB, more than one 80 GB GPU even before activations. AMP saves activations and bandwidth, not optimizer state. So you shard: on 8 GPUs, ZeRO-1, 2 and 3 need 38.5, 26.25 and 14 GB per GPU. Activations then decide batch size, recomputation and sequence length."

Part 2: Scale trajectory and skipped steps

import torch
torch.manual_seed(0)
model = torch.nn.Linear(16, 1).cuda()
opt = torch.optim.SGD(model.parameters(), lr=1e-3)
scaler = torch.amp.GradScaler("cuda", init_scale=1024.0, growth_interval=3)

for step in range(10):
    x = torch.randn(8, 16, device="cuda")
    if step == 5:
        x[0, 0] = float("inf")                       # inject an overflow
    w_before = model.weight.detach().clone()
    s_before = scaler.get_scale()
    with torch.autocast("cuda", dtype=torch.float16):
        loss = model(x).float().pow(2).mean()
    opt.zero_grad(set_to_none=True)
    scaler.scale(loss).backward()
    scaler.step(opt)
    scaler.update()
    s_after = scaler.get_scale()

Part 3: The model.half() trap

m = torch.nn.Linear(16, 1).cuda().half()
opt = torch.optim.SGD(m.parameters(), lr=1e-3)
sc = torch.amp.GradScaler("cuda")
loss = m(torch.randn(8, 16, device="cuda", dtype=torch.float16)).float().mean()
sc.scale(loss).backward()
try:
    sc.step(opt)
except ValueError as e:
    print("ValueError:", e)
Expected and why

ValueError: Attempting to unscale FP16 gradients. GradScaler assumes FP32 parameters (native AMP). Unscaling FP16 grads in place would bring back exactly the underflow that scaling was meant to prevent.

Part 4: Measure bytes per parameter

import torch, torch.nn as nn

def run(amp, batch=256, layers=8, d=4096):
    torch.cuda.empty_cache()
    model = nn.Sequential(*[nn.Linear(d, d) for _ in range(layers)]).cuda()
    opt = torch.optim.AdamW(model.parameters(), lr=1e-4)
    x = torch.randn(batch, d, device="cuda")
    def step():   # no scaler: we only measure memory here
        with torch.autocast("cuda", dtype=torch.float16, enabled=amp):
            loss = model(x).float().pow(2).mean()
        loss.backward()
        opt.step()
        opt.zero_grad(set_to_none=True)
    step()                                   # creates Adam state lazily
    torch.cuda.reset_peak_memory_stats()
    steady = torch.cuda.memory_allocated()
    step()
    peak = torch.cuda.max_memory_allocated()
    n = sum(p.numel() for p in model.parameters())
    print(f"amp={amp!s:5} batch={batch:5}: steady={steady/n:5.2f} B/param  peak={peak/n:5.2f} B/param")
    del model, opt, x

for b in (256, 16384):          # 4b (16384) needs ~8 GB
    for amp in (False, True):
        run(amp, batch=b)
What to expect (then explain your actual numbers)
  • Steady state ≈ 12 B/param in both modes: FP32 w + m + v. The grads were freed by set_to_none=True.
  • Batch 256: the peak is dominated by model states and optimizer temporaries, so AMP and FP32 peaks are similar. AMP does not help here.
  • Batch 16384: saved activations are about 2.1 GB in FP32 (≈16 B/param) and about half that in FP16, so the AMP peak is clearly lower.
  • Exact numbers depend on the foreach vs. fused Adam implementation and the caching allocator. Explain every difference greater than 1 B/param.
