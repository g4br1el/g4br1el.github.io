Lesson 6: Block-Scaled Formats

Interview skill: Design and defend an FP8 training recipe: format per tensor, scale computation, what stays in higher precision, and how it fails.

Legend: verified = checked against the primary source in this session · verify = from memory; check before quoting in an interview.

1. From L5: why per-tensor scaling stops working

Per-tensor scaling puts the tensor's amax at the top of the format. Every other element then has to fit in the binades below it. The fewer binades the element format has, the more one outlier pushes the bulk of the tensor into underflow or coarse rounding:

Element formatMaxMin subnormalBinades
FP8 E4M34482−9≈17.8
FP6 E3M2282−4≈8.8
FP6 E2M37.52−3≈5.9
FP4 E2M160.5≈3.6

FP4 has only ~3.6 binades, so a single scale for the whole tensor cannot work. The fix is to shrink the scaling domain until the values inside it share a local magnitude: one scale per block of 16 or 32 elements.

3. The MX (OCP Microscaling) standard

  • Structure: k narrow elements share one scale X. The value of element i is X · Pi. The paper evaluates MX as "a block-level scale on top of narrow bit-width elements" verified (arXiv:2310.10537).
  • Shared scale is E8M0: "All concrete MX formats use E8M0 (an 8-bit exponent) as the format for the shared scale. The representable exponents of these formats is a superset of the representable exponents of FP32." verified (arXiv:2310.10537)
  • E8M0 means no sign bit and no mantissa: X = 2e−127, with 0xFF reserved for NaN and no encoding for zero verify. Scales are therefore powers of two only. Applying one only shifts the exponent, but the scale itself can be off by up to 2× from ideal.
  • Block size k = 32 for all concrete formats: MXFP8 (E4M3/E5M2), MXFP6 (E3M2/E2M3), MXFP4 (E2M1), MXINT8 verify (Table 1).
  • Storage cost: MXFP8 = 8 + 8/32 = 8.25 bits/element; MXFP4 = 4 + 8/32 = 4.25 bits/element.

Scale rule and its clipping problem

OCP rule:     X = 2^( floor(log2(amax_block)) - emax_elem )      # emax: E2M1=2, E4M3=8
              P_i = quantize_saturating( V_i / X )
Consequence:  amax / X lies in [2^emax, 2^(emax+1))
              E2M1: [4, 8)    but max is 6   -> values in (6, 8) clip
              E4M3: [256,512) but max is 448 -> values in (448, 512) clip
Fix (used in MXFP8 training recipes): round the scale UP
              X = 2^ceil( log2(amax_block / FMAX) )   # never clips, but wastes up to 1 binade

Worked example (E2M1, block amax = 7.5):

  • Floor rule: floor(log2 7.5) = 2, so X = 22−2 = 1. Then 7.5 saturates to 6, a 20% error on the largest element. The largest element is often the one that matters most.
  • Ceil rule: X = 2ceil(log2 1.25) = 2. Then 7.5/2 = 3.75 rounds to 4, giving 8: 6.7% error. But every other element in the block is now on a grid twice as coarse.

Rounding the scale up for MXFP8 is recommended in NVIDIA's MXFP8 pre-training recipe verify (Mishra et al. 2025, arXiv:2506.08027). This is a good concrete example of a choice the spec leaves open but that affects training.

4. NVFP4: smaller blocks, finer scales, two levels

MXFP4NVFP4
ElementsE2M1E2M1
Block size3216
Block scaleE8M0 (power of two)E4M3 (fractional)
Second levelnoneFP32 per-tensor scale
Bits/element4.254.5 (+ negligible per-tensor scale)

All NVFP4 rows: verify (NVIDIA Blackwell docs / NVFP4 paper).

g        = amax_tensor / (6 * 448)                     # FP32 per-tensor scale
s_block  = cast_e4m3( (amax_block / 6) / g ) * g       # block scale, ~3-bit mantissa
x_q      = cast_e2m1( x / s_block )
  • Why an E4M3 scale: The block amax lands close to 6 instead of anywhere in [4, 8). This recovers most of the "up to 1 binade" waste of E8M0.
  • Why the FP32 second level: E4M3 covers only ~18 binades (L5), while E8M0 covers more than FP32. Without g, block scales of small tensors (e.g. gradients ~1e−6) would underflow in E4M3. g moves the whole tensor into the range where E4M3 scales work.
  • Why block 16: Fewer elements share an outlier's scale. The cost is twice the scale metadata and scale-handling work.

5. Systems: what block scaling does to the GEMM

per-tensor:  C[i,j] = (1 / (sA * sB)) * Σ_k Aq[i,k] Bq[k,j]          # scale factors out -> epilogue
per-block:   C[i,j] = Σ_b  sA[i,b] * sB[b,j] * Σ_{k in b} Aq[i,k] Bq[k,j]
  • Blocks must run along K, the reduction dimension. Then each partial dot product has one constant scale product. Block scales cannot be pulled out into the epilogue: they must be applied inside the K loop. Blackwell does this in hardware with block-scaled MMA (MXFP8/6/4, NVFP4) verify (PTX ISA / Blackwell docs). On Hopper there is no native support. DeepSeek-V3 emulated it with FP8 MMAs and FP32 promotion on CUDA cores (L5).
  • Transpose problem: Forward reduces W over input features. Backward computes dgrad = dY·W and wgrad = XT·dY, which reduce over other dimensions. A 1×32 block along rows is the wrong blocking for the transposed use. You need a second quantization of the original high-precision tensor along the other axis. Re-quantizing the quantized one adds error twice. That means two FP8/FP4 copies (rowwise and columnwise), extra memory traffic, and forward and backward that see slightly different weights. The NVFP4 recipe uses 16×16 2D blocks for weights so both directions see the same quantized W verify.
  • Scale-factor layout: Hardware expects scale factors in a specific swizzled layout. Producing them is part of the quantize kernel, and if it isn't fused it shows up in profiles as extra memory-bound work verify (cuBLAS / TE docs).

7. Block vs. tensor scaling: trade-off summary

Per-tensor (FP8, L5)MX (k=32, E8M0)NVFP4 (k=16, E4M3 + FP32)

Scale precisionexact (FP32)power of two (up to 2× off)~3 mantissa bits
Metadatanegligible0.25 bit/element0.5 bit/element

Note: Block scaling is always "current" scaling. The block amax is computed when the cast happens, so delayed scaling's staleness problem from L5 goes away. The cost is a reduction inside the quantize kernel.

8. Interview answer (~30 s)

"Below 8 bits the element format has only a few binades. E2M1 covers about 3.6, so one scale per tensor can't hold both outliers and the bulk of the values. MX puts a shared power-of-two E8M0 scale on every 32 elements. NVFP4 uses 16-element blocks with an E4M3 scale, plus an FP32 per-tensor scale that keeps those block scales in range. Blocks run along the GEMM's K dimension, so scales are applied inside the MMA loop, which Blackwell does in hardware. The costs: separate rowwise and columnwise quantized copies for backward, scale metadata, and the scale-rounding choice. The OCP floor rule can clip the block max, so recipes round the scale up. FP4 training also needs Hadamard rotations against outliers, stochastic rounding for gradients, and a few BF16 layers."

9. Lab (~15 min, CPU is fine, PyTorch ≥ 2.1)

import torch, math
torch.manual_seed(0)
GRID = torch.tensor([0., .5, 1., 1.5, 2., 3., 4., 6.])   # non-negative E2M1 values
FP4_MAX, E4M3_MAX = 6.0, 448.0

def round_fp4(y):
    """Round to nearest E2M1 value, saturating at +-6.
    argmin breaks exact ties toward the smaller magnitude (true RNE differs only on exact ties)."""
    a = y.abs().clamp(max=FP4_MAX)
    idx = (a.unsqueeze(-1) - GRID).abs().argmin(dim=-1)
    return torch.sign(y) * GRID[idx]

def quant(x, block, scale_fmt):
    """Fake-quantize x to FP4 with one scale per `block` contiguous elements (last dim)."""
    xb = x.reshape(-1, block)
    amax = xb.abs().amax(dim=1, keepdim=True).clamp(min=1e-30)
    if scale_fmt == "fp32":            # exact scale (reference)
        s = amax / FP4_MAX
    elif scale_fmt == "e8m0_floor":    # OCP MX rule, emax(E2M1) = 2
        s = torch.exp2(torch.floor(torch.log2(amax)) - 2)
    elif scale_fmt == "e8m0_ceil":     # round scale up: block max never clips
        s = torch.exp2(torch.ceil(torch.log2(amax / FP4_MAX)))
    elif scale_fmt == "nvfp4":         # E4M3 block scale + FP32 per-tensor scale
        g = x.abs().max().clamp(min=1e-30) / (FP4_MAX * E4M3_MAX)
        s = ((amax / FP4_MAX) / g).clamp(max=E4M3_MAX).to(torch.float8_e4m3fn).float() * g
        s = s.clamp(min=1e-30)
    y = xb / s
    clip = (y.abs() > FP4_MAX).float().mean().item()
    return (round_fp4(y) * s).reshape(x.shape), clip

def rel_err(x, xh):
    return ((x - xh).norm() / x.norm()).item()

def rand_hadamard(n, seed=1):
    H = torch.ones(1, 1)
    for _ in range(int(math.log2(n))):
        H = torch.cat([torch.cat([H, H], 1), torch.cat([H, -H], 1)], 0)
    g = torch.Generator().manual_seed(seed)
    d = torch.randint(0, 2, (n,), generator=g).float() * 2 - 1
    return (H * d) / math.sqrt(n)      # H @ diag(d): orthonormal

# ---- Part 1: format comparison on three distributions ----
N = 4096 * 64
data = {
    "gaussian":                torch.randn(N),
    "student-t(3)":            torch.distributions.StudentT(3.0).sample((N,)),
    "gauss + 0.1% outliers x50": torch.randn(N) * (1 + 49 * (torch.rand(N) < 1e-3).float()),
}
configs = [("per-tensor FP4",      N,  "fp32"),
           ("MXFP4 floor (k=32)",  32, "e8m0_floor"),
           ("MXFP4 ceil  (k=32)",  32, "e8m0_ceil"),
           ("NVFP4       (k=16)",  16, "nvfp4")]
R = rand_hadamard(16)
for name, x in data.items():
    print(f"\n{name}")
    for label, k, fmt in configs:
        xh, clip = quant(x, k, fmt)
        print(f"  {label:22s} rel_err={rel_err(x, xh):.4f}  clipped={clip:.4%}")
    xr = (x.reshape(-1, 16) @ R).reshape(-1)          # rotate along K in chunks of 16
    xh, _ = quant(xr, 16, "nvfp4")
    back = (xh.reshape(-1, 16) @ R.T).reshape(-1)     # rotate back (exact inverse)
    print(f"  {'NVFP4 + RHT(16)':22s} rel_err={rel_err(x, back):.4f}")

# ---- Part 2: the transpose problem ----
W = torch.randn(256, 256)
Wr, _ = quant(W, 32, "e8m0_floor")                    # blocks along dim 1 (fprop K)
Wc, _ = quant(W.t().contiguous(), 32, "e8m0_floor")   # blocks along dim 0 (bwd K)
print("\nrowwise vs columnwise quantized W differ by rel", rel_err(Wr, Wc.t()))
