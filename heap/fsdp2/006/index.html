Lesson 006 Core V100-Specific

Mixed Precision in FSDP2: fp16 on V100

The full interaction between MixedPrecisionPolicy, FSDP2's internal casting, and the precision dangers specific to V100's fp16-only world.

Why This Is More Complex Than DDP + AMP

In DDP, mixed precision is your problem:

# DDP pattern (what you're used to):
scaler = torch.cuda.amp.GradScaler()
with torch.cuda.amp.autocast(dtype=torch.float16):
    output = model(input)
    loss = criterion(output, target)
scaler.scale(loss).backward()
scaler.step(optimizer)
scaler.update()

In FSDP2, precision is interleaved with communication. The dtype of a parameter matters at five different points: storage, all-gather, compute, reduce-scatter, and optimizer update. MixedPrecisionPolicy controls this entire pipeline — and on V100, you must get it right because fp16's narrow dynamic range leaves no margin for error.

The Three Knobs of MixedPrecisionPolicy

from torch.distributed._composable.fsdp import MixedPrecisionPolicy

policy = MixedPrecisionPolicy(
    param_dtype=torch.float16,      # Dtype for compute (forward + backward)
    reduce_dtype=torch.float32,     # Dtype for gradient reduce-scatter
    output_dtype=None,              # Dtype to cast module outputs to (rare)
)
KnobControlsImpact on V100
param_dtype The dtype of parameters AFTER all-gather, during forward/backward compute fp16 → uses Tensor Cores (8× FLOPS vs fp32). Must be fp16 on V100 (no bf16 hardware).
reduce_dtype The dtype used when gradients are reduce-scattered across ranks fp32 recommended on V100. Prevents gradient underflow during summation. Costs 2× comm bandwidth on reduce-scatter only.
output_dtype Optional cast applied to module outputs before passing to next module Rarely needed. Use only if downstream module expects specific dtype. Default: no cast (inherit from compute).

Full Precision Lifecycle in FSDP2

Let's trace the dtype of a single parameter through one complete training step:

Parameter precision lifecycle (V100, param_dtype=fp16, reduce_dtype=fp32): ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ [AT REST] Master weight: fp32, Shard(0), shape [P/N, ...] ← stored permanently [PRE-FORWARD HOOK] 1. all-gather master weight shards → full fp32 param (communication in fp32) 2. Cast fp32 → fp16 (local op, no comm) 3. Module sees: fp16, Replicate, full shape [P, ...] ← compute dtype Memory at this point: - fp32 shard (P/N × 4 bytes) — retained - fp16 full param (P × 2 bytes) — transient [FORWARD COMPUTE] Uses fp16 parameters, produces fp16 activations Tensor Core utilization: matrix multiplies run at fp16→fp32 accumulate→fp16 output [POST-FORWARD HOOK] 4. Free fp16 full param buffer (memory reclaimed) Only fp32 shard remains [PRE-BACKWARD HOOK] 5. all-gather master weight shards → full fp32 param (communication in fp32) 6. Cast fp32 → fp16 (for grad computation) [BACKWARD COMPUTE] Computes gradients in fp16 (matching forward precision) grad_weight: fp16, full shape, Partial(sum) on each rank [POST-BACKWARD HOOK] 7. Cast grad fp16 → fp32 (upcast BEFORE reduction) 8. reduce-scatter in fp32 → sharded fp32 grad (communication in fp32) 9. Free fp16 full param buffer Result: fp32 grad shard, shape [P/N, ...] [OPTIMIZER STEP] Inputs (all fp32, all sharded): - Master weight shard: [P/N, ...] - Gradient shard: [P/N, ...] - Adam m shard: [P/N, ...] - Adam v shard: [P/N, ...] Update: entirely fp32, entirely local, no communication
Key insight: The master weights are ALWAYS fp32. FSDP2 never stores fp16 parameters permanently. The fp16 copy exists only transiently during compute. This is different from some DDP + AMP implementations where the model's .parameters() might be fp16 with separate fp32 copies in the optimizer — in FSDP2, the parameters ARE the fp32 masters, and fp16 is a cast applied on-the-fly.

Why No GradScaler Is Needed

This confuses many people migrating from DDP + AMP. The reasoning:

ConcernDDP + AMP solutionFSDP2 solution
fp16 gradients underflow to zero GradScaler scales loss → amplified gradients stay in fp16 range reduce_dtype=fp32: gradients are upcast to fp32 BEFORE reduction. Optimizer sees fp32 grads. No underflow possible in the critical path.
fp16 gradient overflow (NaN/Inf) GradScaler detects inf, skips step, reduces scale Gradients computed in fp16 locally → upcast to fp32 immediately. The fp16 window is tiny (single backward pass on one rank). If overflow occurs here, it's a learning rate / architecture issue, not a scaling issue.
Accumulated fp16 round-off in optimizer Optimizer operates on fp32 master weights (separate copy) Identical — optimizer operates on fp32 sharded master weights natively.
Bottom line: reduce_dtype=fp32 eliminates the primary failure mode that GradScaler exists to solve (gradient underflow during accumulation/reduction). The remaining risk (local fp16 gradient overflow during backward on a single rank) is rare for well-configured training and indicates a hyperparameter problem, not a scaling problem.

When You MIGHT Still Want Loss Scaling

There is one edge case: if you set reduce_dtype=torch.float16 (to minimize communication) AND your model produces very small gradients, you could still underflow during the reduce-scatter. In this case, you'd need manual loss scaling. But on V100, this is not recommended — use reduce_dtype=fp32 and avoid the complexity.

V100 fp16 Dangers: The Dynamic Range Problem

Understanding the numerical limits of fp16 is essential for debugging training instability:

Propertyfp16bf16fp32
Exponent bits588
Mantissa bits10723
Max value65,5043.4 × 10³⁸3.4 × 10³⁸
Min positive normal6.1 × 10⁻⁵1.2 × 10⁻³⁸1.2 × 10⁻³⁸
Min subnormal5.96 × 10⁻⁸9.2 × 10⁻⁴¹1.4 × 10⁻⁴⁵

The V100 disadvantage: fp16's max value of 65,504 means any intermediate result > 65,504 becomes inf. In attention computations, Q @ K.T / sqrt(d) with large sequence lengths or high-magnitude embeddings can overflow. bf16 (available on A100/H100) shares fp32's exponent range and never has this issue. On V100, you must be vigilant about overflow in attention.

Attention Overflow: The Most Common V100 fp16 Failure

The attention score computation Q @ K.T for ViTs with large embedding dimensions:

# ViT-Huge: head_dim = 1280 / 16 heads = 80
# Attention scores: [batch, heads, seq_len, seq_len]
#
# If Q and K entries have magnitude ~1.0 (post-LayerNorm), then:
#   QK entry ≈ sum of 80 products of ~1.0 magnitude values
#   Expected magnitude: ~sqrt(80) ≈ 8.9 (Central Limit Theorem)
#   After scaling by 1/sqrt(80): ~1.0
#
# But with fp16, outlier values can push individual entries to ~50-100
# before scaling. This is fine for fp16 (max 65504).
#
# HOWEVER, if you forget the scaling, or if embeddings aren't well-normalized:
#   QK entry without scaling: can reach ~80 × 5 = 400 (if values ~5)
#   After softmax: exp(400) = inf → NaN propagates everywhere

Defenses Against fp16 Overflow in ViT

# 1. Scaled dot-product attention (PyTorch 2.0+) — handles this internally
# It computes attention in a numerically stable way, even in fp16.
# timm's ViT uses this by default. ALWAYS use it on V100.
output = torch.nn.functional.scaled_dot_product_attention(Q, K, V)

# 2. If using a custom attention: scale BEFORE matmul, not after
# BAD (overflow risk):
scores = Q @ K.T / math.sqrt(head_dim)

# GOOD (overflow prevented):
Q_scaled = Q / math.sqrt(math.sqrt(head_dim))  # Scale Q by d^{-1/4}
K_scaled = K / math.sqrt(math.sqrt(head_dim))  # Scale K by d^{-1/4}
scores = Q_scaled @ K_scaled.T                  # Product is scaled by d^{-1/2}

# 3. Clamp attention scores before softmax (last resort, loses gradient info)
scores = scores.clamp(min=-65000, max=65000)
For your ViT-Huge training: If you're using timm's implementation (as in Lesson 003), it uses scaled_dot_product_attention which is numerically stable in fp16. No additional action needed. But if you ever implement custom attention (e.g., for defect detection with cross-attention to reference images), remember the scaling-before-matmul pattern.

LayerNorm Precision: A Subtle Correctness Issue

LayerNorm computes mean and variance across features. In fp16:

# LayerNorm(x) = (x - mean(x)) / sqrt(var(x) + eps) * gamma + beta
#
# Problem: variance computation in fp16 is numerically unstable.
# For ViT-Huge with hidden_dim=1280:
#   mean = sum(x_i) / 1280  — in fp16, sum of 1280 values can overflow
#   var = sum((x_i - mean)^2) / 1280 — squared differences amplify magnitude
#
# PyTorch's LayerNorm handles this correctly:
# It computes the reduction (mean, var) in fp32 internally,
# even when input is fp16. This is NOT controlled by MixedPrecisionPolicy —
# it's baked into the LayerNorm kernel.
Good news: PyTorch's native nn.LayerNorm always computes reductions in fp32 internally, regardless of input dtype. The gamma and beta parameters (which ARE sharded by FSDP2) are typically fp32 at rest and cast to fp16 for the multiply/add — this is handled correctly by the precision lifecycle above. No manual intervention needed.

The ~1.3× communication cost for the recommended config: all-gathers move fp32 data (4 bytes/param), reduce-scatter moves fp32 data (4 bytes/param). Compared to a hypothetical all-fp16 pipeline (2 bytes/param everywhere), you pay 2× on comm per byte. But comm volume is only a fraction of total step time, so the net overhead is ~30% on communication, which translates to ~5-10% on total step time (compute-dominated for large models).

What About All-Gathering in fp16?

A natural question: can we store master weights in fp32 but all-gather in fp16 to save communication bandwidth?

# This is NOT directly configurable via MixedPrecisionPolicy in current FSDP2.
# The all-gather operates on the stored parameter dtype (fp32 masters).
#
# What actually happens with param_dtype=fp16, reduce_dtype=fp32:
#   1. Parameters at rest: fp32 (master weights)
#   2. All-gather: transmits fp32 shards → assembles full fp32 param
#   3. Cast: fp32 → fp16 (local operation after all-gather)
#   4. Compute: fp16
#   5. Grad: fp16 → cast to fp32 → reduce-scatter in fp32
#
# So the all-gather bandwidth cost is fp32 (4 bytes/param), not fp16.
#
# This is a known trade-off. The PyTorch team considered "cast-before-gather"
# (cast to fp16, then all-gather fp16 shards), which would halve all-gather
# bandwidth. This is planned but not yet implemented as of PyTorch 2.5.
#
# Workaround: store parameters in fp16 as the "master" dtype and use fp32
# only in the optimizer via a separate mechanism. But this adds complexity
# and is not recommended for stability.
Current limitation: FSDP2 all-gathers in the storage dtype (fp32 for masters). This means all-gather bandwidth is 2× what it could be if casting happened before communication. On your V100 NVLink (300 GB/s), this is rarely the bottleneck for ViT-Huge sized models. But at larger scale (billions of params) or with InfiniBand-heavy topologies, it matters. Keep this in mind for future optimization.

Comparing Memory Footprints

Per-GPU memory for ViT-Huge (632M params), 4 GPUs, FSDP2:

ComponentNo MP (all fp32)With MP (fp16 compute, fp32 reduce)
Master weight shard 632M/4 × 4 = 632 MB 632M/4 × 4 = 632 MB (unchanged — always fp32)
Gradient shard 632M/4 × 4 = 632 MB 632M/4 × 4 = 632 MB (fp32 after reduction)
Adam m shard 632M/4 × 4 = 632 MB 632M/4 × 4 = 632 MB (unchanged)
Adam v shard 632M/4 × 4 = 632 MB 632M/4 × 4 = 632 MB (unchanged)
Transient unsharded param (1 block) ~20M × 4 = 76 MB (fp32) ~20M × 2 = 38 MB (fp16!)
Activations (batch=16, 224²) ~12 GB (fp32) ~6 GB (fp16)
Total peak estimate ~15 GB ~9 GB
Mixed precision's biggest memory win: activations. The model-proportional memory (shards + optimizer) is fp32 regardless. But activations (saved for backward) are stored in the compute dtype — fp16. For batch_size=16 with ViT-Huge, this saves ~6 GB. That's the difference between fitting batch=16 and fitting batch=32.

When Training Diverges: Debugging Precision Issues

Symptoms and diagnoses for fp16 training on V100:

SymptomLikely causeDiagnosisFix
Loss becomes NaN suddenly (one step) fp16 overflow in attention or large activations Add torch.autograd.detect_anomaly() or check for inf in attention scores Use scaled_dot_product_attention; reduce learning rate; check for exploding embeddings
Loss plateaus early, no learning Gradient underflow — many grads become zero in fp16 Compare grad norms with fp32 run; check (grad == 0).float().mean() Verify reduce_dtype=fp32; increase learning rate; check for vanishing activations
Loss is unstable / oscillates fp16 precision loss in accumulation or normalization Run same config in fp32; if stable, precision is the issue Ensure LayerNorm computes in fp32 (default); consider gradient clipping

Debugging Utility

def check_precision_health(model: nn.Module, step: int) -> None:
    """Call periodically (every 100 steps) to detect precision issues early."""
    for name, param in model.named_parameters():
        if param.grad is not None:
            grad = param.grad
            # Access local tensor if DTensor
            if hasattr(grad, '_local_tensor'):
                grad = grad._local_tensor

            grad_abs = grad.abs()
            n_zero = (grad_abs == 0).sum().item()
            n_inf = torch.isinf(grad).sum().item()
            n_nan = torch.isnan(grad).sum().item()

            total = grad.numel()
            zero_pct = n_zero / total * 100

            if n_inf > 0 or n_nan > 0:
                print(f"[Step {step}] ⚠️  {name}: {n_inf} inf, {n_nan} nan")
            elif zero_pct > 50:
                print(f"[Step {step}] ⚠️  {name}: {zero_pct:.1f}% zero gradients "
                      f"(possible underflow)")

Tensor Core Alignment on V100

V100 Tensor Cores operate on fp16 matrices with specific alignment requirements:

# V100 Tensor Core requirements for maximum throughput:
# - Matrix dimensions (M, N, K) should be multiples of 8
# - Input tensors should be contiguous in memory
#
# ViT-Huge dimensions:
#   hidden_dim = 1280  → 1280 / 8 = 160 ✓
#   mlp_dim = 5120     → 5120 / 8 = 640 ✓
#   num_heads = 16     → head_dim = 80 → 80 / 8 = 10 ✓
#   patch_embed output = 1280 ✓
#
# Batch × seq_len = 16 × (224/14)² = 16 × 256 = 4096 → 4096 / 8 = 512 ✓
#
# All ViT-Huge dimensions are multiples of 8 → maximum Tensor Core utilization.
# No padding needed.
#
# If you train with non-standard image sizes (e.g., 518×518 for DINOv2):
#   seq_len = (518/14)² = 37² = 1369 → 1369 / 8 = 171.125 ✗
#   This will still work but with slightly reduced Tensor Core efficiency.
#   Padding to 1376 tokens (37.1 patches → round to 38² = 1444?) is complex.
#   In practice, the efficiency loss for non-aligned seq_len is small (~2-5%).

The output_dtype Knob: When You Need It

# output_dtype is rarely needed. The use case:
#
# You have two adjacent FSDP units where:
# - Unit A computes in fp16 (param_dtype=fp16)
# - Unit B expects fp32 input for numerical reasons
#
# Without output_dtype:
#   Unit A output → fp16 tensor → passed to Unit B → Unit B's pre-forward
#   hook doesn't cast inputs (only params are cast)
#
# With output_dtype=torch.float32 on Unit A:
#   Unit A output → cast to fp32 → passed to Unit B
#
# In practice for ViTs: all blocks use the same policy, so this isn't needed.
# It becomes relevant for heterogeneous architectures (e.g., mixing a
# quantized encoder with a full-precision decoder).

# Example (hypothetical):
policy_encoder = MixedPrecisionPolicy(
    param_dtype=torch.float16,
    reduce_dtype=torch.float32,
    output_dtype=torch.float32,  # Cast output to fp32 for decoder
)
policy_decoder = MixedPrecisionPolicy(
    param_dtype=torch.float32,  # Decoder runs in fp32
    reduce_dtype=torch.float32,
)

Per-Module Precision Policies

FSDP2 allows different policies for different FSDP units:

def apply_fsdp2_with_mixed_policies(model: nn.Module, mesh) -> nn.Module:
    """
    Example: fp16 for transformer blocks, fp32 for the classification head.

    Rationale: The head is small (1280 × num_classes), so fp32 cost is minimal.
    But classification logits in fp16 can lose precision for rare classes
    with small probabilities — this avoids subtle accuracy degradation.
    """
    mp_fp16 = MixedPrecisionPolicy(
        param_dtype=torch.float16,
        reduce_dtype=torch.float32,
    )
    mp_fp32 = MixedPrecisionPolicy(
        param_dtype=torch.float32,
        reduce_dtype=torch.float32,
    )  # No casting — everything stays fp32

    # Transformer blocks: fp16 compute (Tensor Cores)
    for block in model.blocks:
        fully_shard(block, mesh=mesh, mp_policy=mp_fp16)

    # Could also apply fp32 to specific sensitive layers:
    # fully_shard(model.head, mesh=mesh, mp_policy=mp_fp32)
    # But model.head is part of the root FSDP unit, so:

    # Root (includes patch_embed, head, pos_embed): fp16 is fine here too
    fully_shard(model, mesh=mesh, mp_policy=mp_fp16)

    return model
In practice for ViT training: using a uniform fp16 policy everywhere works fine. Per-module policies are more relevant for: (1) models with mixed quantized/full-precision components, (2) architectures where specific layers are precision-sensitive (e.g., the final projection in contrastive learning), or (3) fine-tuning scenarios where only some layers are trained.

Gradient Clipping with FSDP2

Gradient clipping is a common stability tool that interacts with FSDP2's sharded gradients:

# With FSDP2, gradients AFTER backward are sharded (each rank has 1/N).
# torch.nn.utils.clip_grad_norm_ works correctly on sharded DTensor gradients
# because it uses DTensor's all-reduce internally to compute the global norm.

# Pattern:
loss.backward()

# Clip BEFORE optimizer step
# This computes the global grad norm across all ranks (requires all-reduce)
# then clips each rank's sharded grad in-place.
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)

optimizer.step()
optimizer.zero_grad()
Performance note: clip_grad_norm_ with FSDP2 triggers an additional all-reduce to compute the global gradient norm (each rank has only a partial view of the total norm). This adds one extra collective per step. For most training, this is negligible (~1-2ms on NVLink), but be aware it exists.

Check Your Understanding

Q1: With MixedPrecisionPolicy(param_dtype=fp16, reduce_dtype=fp32), what dtype is transmitted during the all-gather in the pre-forward hook?

Correct. FSDP2 stores master weights in fp32. The all-gather transmits fp32 shards and assembles the full fp32 parameter. Only THEN is it cast to fp16 for compute. This means all-gather bandwidth is 4 bytes/param, not 2. The "cast-before-gather" optimization (transmitting fp16 and saving bandwidth) is not yet implemented in FSDP2 as of PyTorch 2.5.

Q2: Why does mixed precision save more activation memory than model-proportional memory with FSDP2?

Correct. The optimizer states (Adam m, v) and master weights are fp32 by design — MixedPrecisionPolicy doesn't change their storage dtype. Only the transient compute (forward activations saved for backward) uses fp16. So model-proportional memory is unchanged by mixed precision, while activation memory is halved. Answer D is also partially true (activations often dominate), but the root cause is that model-prop memory is fp32-locked.

Q3: Your ViT-Huge FSDP2 training on V100 shows loss=NaN at step 847. Loss was decreasing normally before. What's your first diagnostic step?

Correct. Sudden NaN (was fine, then explodes) on V100 fp16 is almost always attention overflow. As training progresses, embedding magnitudes can grow, pushing Q@K.T products past fp16's max (65504). First check: are you using scaled_dot_product_attention (which handles this internally)? If using custom attention, log attn_scores.max() in the steps before 847 — you'll likely see it approaching 65504. Fix: ensure SDPA usage or apply the scale-before-matmul pattern.

Q4: You want to verify Tensor Cores are actually being used for your fp16 ViT-Huge matmuls on V100. How?

Correct. Use torch.profiler or NVIDIA Nsight Systems (nsys). In the trace, look for CUDA kernel names containing "h884" (Volta's Tensor Core instruction set) or "hmma" (half-precision matrix multiply-accumulate). If you see "sgemm" (single-precision GEMM), Tensor Cores aren't engaged — likely due to non-fp16 inputs or non-aligned dimensions. Example: volta_h884gemm_256x128_ldg8_nn = Tensor Core kernel.

Key Takeaways

  1. MixedPrecisionPolicy controls the full precision lifecycle: storage (fp32) → all-gather (fp32) → cast → compute (fp16) → grad (fp16) → cast → reduce-scatter (fp32) → optimizer (fp32).
  2. No GradScaler needed because reduce_dtype=fp32 eliminates the gradient underflow/overflow that GradScaler exists to solve.
  3. V100's fp16 danger zone: max value 65504. Attention scores can overflow. Use scaled_dot_product_attention (default in timm ViT) as defense.
  4. Activation memory is halved by mp_policy (stored in param_dtype=fp16). Model-proportional memory is unchanged (always fp32).
  5. All-gather currently transmits fp32 (cast happens after gather). This is a known inefficiency — "cast-before-gather" is planned.
  6. Gradient clipping works on sharded DTensor grads but adds one all-reduce for global norm computation.
  7. Tensor Core utilization: ensure matrix dims are multiples of 8. ViT-Huge's 1280 hidden dim is naturally aligned.
