Lesson 002 Foundations

FSDP1 vs FSDP2: The Death of FlatParamHandle

Understanding why PyTorch rewrote FSDP from scratch — and what the new substrate looks like.

FSDP1: The Wrapper Approach

FSDP1 (torch.distributed.fsdp.FullyShardedDataParallel, introduced PyTorch 1.11) works like DDP — it's a module wrapper:

# FSDP1 — wrapping approach
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP

model = ViTHuge()
# Wraps the entire model (or individual submodules via auto_wrap_policy)
model = FSDP(model, sharding_strategy=ShardingStrategy.FULL_SHARD)

Internally, FSDP1 uses FlatParamHandle — the core abstraction that caused most of its problems:

FSDP1 Internal: FlatParamHandle ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Original module parameters: encoder.layer_0.attn.q_proj.weight [1024 × 1024] encoder.layer_0.attn.q_proj.bias [1024] encoder.layer_0.attn.k_proj.weight [1024 × 1024] encoder.layer_0.attn.k_proj.bias [1024] ... FlatParamHandle flattens ALL of these into one contiguous 1-D tensor: flat_param: [████████████████████████████████████████] ← single allocation ↑ q.weight ↑ q.bias ↑ k.weight ↑ ... Sharding slices this 1-D tensor across N ranks: Rank 0: [████████████] Rank 1: [████████████] Rank 2: [████████████] Rank 3: [████████████]

Why FlatParamHandle Exists

It was an optimization: one contiguous buffer means one all-gather call per FSDP unit instead of many small ones. On 2021-era NCCL, many small collectives were catastrophically slower than one large one. The flattening was a pragmatic concession to communication efficiency.

Why FlatParamHandle Is Toxic

ProblemRoot CauseConsequence
torch.compile graph breaks Parameters lose their identity — the flat_param is not a "real" module parameter. torch.compile cannot trace through the unflatten/reshard logic. Cannot compile FSDP1-wrapped modules without severe graph breaks → poor performance.
State dict complexity Original param names map to offsets within a flat buffer. Saving/loading requires metadata to reconstruct the mapping. Checkpoint code is fragile; converting between sharded ↔ full state dicts is error-prone.
Composability with AC Activation checkpointing (checkpoint_wrapper) wraps modules. FSDP also wraps modules. Nesting wrappers creates ordering dependencies and subtle bugs. Incorrect memory savings, recomputation of communication, or silent correctness bugs.
Per-parameter flexibility lost All parameters in a FlatParamHandle are sharded identically. Cannot mix strategies (e.g., shard large weights, replicate small biases). Suboptimal memory/communication trade-offs for heterogeneous architectures.
Module structure distortion The wrapper replaces module attributes. model.encoder.layer_0 is no longer the original module — it's wrapped. Code that walks model.named_parameters() or model.named_modules() behaves differently. Hooks break. Debugging is harder.
The fundamental tension: FSDP1 was designed before torch.compile existed. The wrapper + flat-buffer approach is antithetical to graph tracing. PyTorch had to choose: patch FSDP1 forever, or redesign from first principles. They chose redesign.

FSDP2: The Composable Approach

FSDP2 (torch.distributed._composable.fsdp.fully_shard, PyTorch 2.4+) is not a wrapper. It's a function that mutates a module in-place, replacing its parameters with DTensor objects:

# FSDP2 — composable approach
from torch.distributed._composable.fsdp import fully_shard, MixedPrecisionPolicy

model = ViTHuge()

# Apply per-module — no wrapping, no class change
for layer in model.encoder.layers:
    fully_shard(layer)  # Each transformer block is an FSDP unit

fully_shard(model)  # Root-level shard for remaining params (embeddings, head)

After fully_shard(layer), the module's parameters are still accessible as layer.attn.q_proj.weight, but they are now DTensor instances with a Shard(0) placement on a DeviceMesh.

The Two New Abstractions

1. DTensor (Distributed Tensor)

DTensor is a tensor type that encodes how the tensor is distributed across devices. It wraps a local tensor shard and carries metadata about its global shape and placement:

from torch.distributed._tensor import DTensor, Shard, Replicate

# After fully_shard(), a parameter looks like:
param = layer.attn.q_proj.weight
print(type(param))           # <class 'torch.distributed._tensor.DTensor'>
print(param.shape)           # torch.Size([1024, 1024])  ← GLOBAL shape
print(param._local_tensor.shape)  # torch.Size([256, 1024])  ← LOCAL shard (4 GPUs)
print(param.placements)      # (Shard(0),)  ← sharded along dim 0
Key property: A DTensor reports its global shape. Code that calls param.shape sees the full [1024, 1024], not the local shard. This is what makes DTensor transparent to model code — operations on DTensors produce DTensors with correct global semantics, and the communication is handled internally.

The placement types that matter for FSDP2:

PlacementMeaningWhen used in FSDP2
Shard(dim) Tensor is split along dim across the mesh At rest — parameters and gradients are sharded (dim=0 by default)
Replicate() Full tensor is present on every rank in the mesh During compute — after all-gather, param is temporarily Replicate
Partial(reduce_op) Each rank holds a partial result that needs reduction During backward — gradients before reduce-scatter are Partial(sum)

2. DeviceMesh

DeviceMesh encodes the physical/logical topology of your GPUs. For FSDP2, you need at minimum a 1-D mesh (all GPUs in one flat group). For HSDP, you use a 2-D mesh:

from torch.distributed.device_mesh import init_device_mesh

# 1-D mesh: full sharding across all 8 GPUs
mesh_1d = init_device_mesh("cuda", (8,))

# 2-D mesh for HSDP: (replicate across 2 nodes, shard within 4 GPUs per node)
# Shape: (num_replicas, shard_group_size)
mesh_2d = init_device_mesh("cuda", (2, 4), mesh_dim_names=("replicate", "shard"))
1-D DeviceMesh (8 GPUs, full shard): ┌────────────────────────────────────────────────────────────────┐ │ GPU0 GPU1 GPU2 GPU3 GPU4 GPU5 GPU6 GPU7 │ │ ◀──────────────── single shard group ────────────────────────▶│ └────────────────────────────────────────────────────────────────┘ 2-D DeviceMesh (8 GPUs, HSDP: 2 replicas × 4 shards): ┌────────────── Replica Group 0 ──────────────┐ ┌────────────── Replica Group 1 ──────────────┐ │ GPU0 GPU1 GPU2 GPU3 │ │ GPU4 GPU5 GPU6 GPU7 │ │ ◀──── shard group (intra-node) ────▶ │ │ ◀──── shard group (intra-node) ────▶ │ └─────────────────────────────────────────────┘ └─────────────────────────────────────────────┘ ◀────────── replicate across these two groups (inter-node) ──────────▶
For your V100 cluster: 4 GPUs per node with NVLink, InfiniBand across nodes. The natural HSDP mapping is: mesh_2d = init_device_mesh("cuda", (num_nodes, 4), mesh_dim_names=("replicate", "shard")). Shard within the fast NVLink domain, replicate across the slower InfiniBand links. We'll implement this in a later lesson.

The Lifecycle of a Parameter in FSDP2

This is the most important mental model for FSDP2. Let's trace what happens to a single parameter through one training step:

Parameter lifecycle during one forward + backward pass: ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ State at rest (between steps): param: DTensor, placement=Shard(0), local shape=[256, 1024] (1/4 of [1024,1024]) ─── FORWARD ─────────────────────────────────────────────────────────────────── [1] Pre-forward hook fires for this FSDP unit → Triggers all-gather on param → param.placements transitions: Shard(0) → Replicate() → local tensor is now full [1024, 1024] on every rank → This is the "unsharded" parameter [2] Module's forward() executes normally → Uses the full [1024, 1024] parameter → Produces activations (saved for backward) [3] Post-forward hook fires → Frees the unsharded parameter (returns to Shard(0) view) → Memory reclaimed immediately → Only the 1/4 shard is retained ─── BACKWARD ────────────────────────────────────────────────────────────────── [4] Pre-backward hook fires for this FSDP unit → Triggers all-gather on param AGAIN (needs full param for grad computation) → param: Shard(0) → Replicate() [5] Backward computation executes → Computes gradients w.r.t. the full parameter → Gradient is initially a full [1024, 1024] tensor on each rank → But each rank's gradient is a PARTIAL sum (only from its micro-batch) [6] Post-backward hook fires → Triggers reduce-scatter on the gradient → Each rank receives 1/4 of the SUMMED gradient: shape [256, 1024] → Gradient placement: Partial(sum) → Shard(0) → Frees the unsharded parameter (back to Shard(0)) ─── OPTIMIZER STEP ──────────────────────────────────────────────────────────── [7] Optimizer runs on SHARDED state only → param shard: [256, 1024] → grad shard: [256, 1024] → adam_m shard: [256, 1024] → adam_v shard: [256, 1024] → No communication needed! → Updates param shard in-place
Critical insight: Steps [3] and [6] are where memory is saved. The full parameter exists only transiently during compute. Between FSDP units, memory holds only the shards. This is why FSDP's peak memory ≈ model_sharded + largest_unit_unsharded + activations.

Implementation: Hooks, Not Wrappers

FSDP2 achieves this lifecycle through module hooks registered by fully_shard():

# Conceptual view of what fully_shard(module) does internally:

def fully_shard(module: nn.Module, mesh: DeviceMesh = None, ...):
    # 1. Replace each parameter with a DTensor (Shard(0) placement)
    for name, param in module.named_parameters(recurse=False):
        sharded = distribute_tensor(param.data, mesh, placements=[Shard(0)])
        # Parameter identity preserved — same name, same module attribute
        setattr(module, name, nn.Parameter(sharded))

    # 2. Create FSDPState (manages communication scheduling)
    state = FSDPState(module, mesh, ...)

    # 3. Register hooks
    module.register_forward_pre_hook(state._pre_forward)    # all-gather
    module.register_forward_hook(state._post_forward)        # free unshard
    # Backward hooks are registered on the autograd graph, not the module

    return module  # Same module, mutated in place — NOT wrapped

This is radically different from FSDP1:

AspectFSDP1FSDP2
Module identity type(model) == FSDP — original class lost type(model) == ViTHuge — preserved
Parameter identity Replaced by flat_param offsets Preserved as named DTensor attributes
Sharding granularity Per FSDP-wrap boundary (coarse) Per parameter (fine-grained, though grouped by FSDP unit for efficiency)
torch.compile Graph breaks at every FSDP boundary Traceable — DTensor ops have torch.compile support
State dict Requires special StateDictType context managers Standard model.state_dict() returns sharded DTensors; DCP handles the rest
Activation checkpointing Separate wrapper, ordering-sensitive torch.utils.checkpoint applied independently — orthogonal composition
API surface FSDP(..., auto_wrap_policy=..., sharding_strategy=...) fully_shard(module, mesh=..., mp_policy=...) per module

Why "Composable"?

The term composable in FSDP2's official name (torch.distributed._composable.fsdp) refers to a design principle: distributed training features should compose like function applications, not wrapper nesting:

# FSDP2 composes cleanly with other distributed features:
from torch.distributed._composable.fsdp import fully_shard
from torch.utils.checkpoint import checkpoint

model = ViTHuge()

for layer in model.encoder.layers:
    # These are independent, order doesn't matter:
    fully_shard(layer)                       # Shard this block's params
    layer.forward = checkpoint(layer.forward) # Activation checkpoint this block
    # Could also apply tensor parallelism here in future

fully_shard(model)  # Shard remaining (embedding, head)
Why this matters for you: If you're integrating FSDP into an existing framework at Fraunhofer, the composable API means you don't restructure your model class hierarchy. You apply fully_shard() to existing modules. Your custom hooks, custom layers (pybind11 extensions), and existing checkpoint logic remain undisturbed.

The Communication Scheduling Detail

FSDP2 doesn't naively all-gather one layer, compute, free, all-gather next layer. It uses prefetching — overlapping communication with computation:

Timeline for 3 transformer blocks (simplified): ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Block 0 Block 1 Block 2 Compute: ████████████ ████████████ ████████████ Comms: ▓▓▓(AG B0)▓▓▓(AG B1) ▓▓▓(AG B2) ▓▓▓(RS B2)▓▓▓(RS B1)▓▓▓(RS B0) ↑ Prefetch: all-gather Block 1 starts DURING Block 0's compute Legend: AG = all-gather, RS = reduce-scatter, ████ = compute, ▓▓▓ = communication

The FSDPState manages this via:

  • forward_prefetch (default: True) — starts all-gather of the next FSDP unit before current unit's compute finishes
  • backward_prefetch — same for backward pass (default: BACKWARD_PRE, meaning prefetch the next unit's params before current grad computation)
  • CUDA streams — communication runs on a separate stream from compute, enabling true overlap on your V100s

What "FSDP Unit" Means in Practice

Each call to fully_shard(module) creates one FSDP unit. The granularity choice matters:

GranularityMemory peakCommunication efficiencyRecommendation
One unit = entire model Full model unsharded during compute (defeats the purpose) One large all-gather (maximally efficient) ❌ Never do this
One unit = one transformer block One block unsharded at a time One all-gather per block (good on modern NCCL) ✓ Standard choice
One unit = one linear layer One layer unsharded at a time Many small all-gathers (potentially slower) Only if blocks still don't fit
For ViT-Huge on V100-32GB: One FSDP unit per transformer block is ideal. Each block is ~20M params = ~38 MB unsharded (fp16). The peak memory from unsharding is trivial (~38 MB) relative to activation memory. Finer granularity would add communication overhead for no memory benefit.

Summary: The Architecture Shift

Check Your Understanding

Q1: After calling fully_shard(layer), what is the type of layer.attn.q_proj.weight?

Correct. FSDP2 replaces parameters with DTensor instances. The DTensor carries a Shard(0) placement (at rest) and reports the global shape, while its ._local_tensor holds only the rank's shard. This is what makes FSDP2 transparent to model code and traceable by torch.compile.

Q2: Why does FSDP2 all-gather the parameters twice per training step (once in forward, once in backward)?

Correct. This is the core memory-communication trade-off. After forward compute on a layer, the post-forward hook discards the full-size parameter (transitions back to Shard). When backward reaches that layer, it needs the full parameter again to compute gradients. So it all-gathers a second time. The alternative — keeping it unsharded — would negate the memory savings.

Q3: What is the primary reason FSDP1's FlatParamHandle breaks torch.compile?

Correct. torch.compile traces the computation graph by following tensor operations through module attributes. When FSDP1 flattens parameters into an opaque 1-D buffer and manages them through internal handles (not visible as module attributes), the tracer cannot connect inputs to outputs through these parameters. Each FSDP boundary becomes a graph break. FSDP2's DTensor parameters are standard module attributes with well-defined torch.compile dispatch rules.

Q4: In a 2-D DeviceMesh of shape (2, 4) with dim_names ("replicate", "shard"), which communication happens over InfiniBand on your cluster?

Correct. In HSDP (Hybrid Sharded Data Parallel), the "shard" dimension (size 4) maps to intra-node NVLink, and the "replicate" dimension (size 2) maps to inter-node InfiniBand. Sharding ops (all-gather, reduce-scatter) happen within each 4-GPU group over fast NVLink. But since the model is replicated across the two groups, gradients must be all-reduced across the replicate dimension — that traffic goes over InfiniBand.

Key Takeaways

  1. FSDP1 uses a wrapper class + FlatParamHandle (parameters flattened into one 1-D buffer). This was pragmatic but toxic for composability, torch.compile, and debugging.
  2. FSDP2 uses in-place mutation + DTensor. Each parameter becomes a DTensor with Shard(0) placement. Module identity and parameter names are preserved.
  3. DTensor encodes distribution semantics (Shard, Replicate, Partial) and reports global shapes. FSDP2's lifecycle is a sequence of placement transitions: Shard → Replicate (all-gather) → compute → Shard (free) → Replicate (all-gather in bwd) → Partial (grad) → Shard (reduce-scatter).
  4. DeviceMesh encodes your GPU topology. 1-D for full sharding, 2-D for HSDP (shard intra-node over NVLink, replicate inter-node over InfiniBand).
  5. FSDP unit = one fully_shard() call. Standard choice for transformers: one unit per block. This determines peak memory (one block unsharded at a time) and communication granularity.
  6. Prefetching overlaps communication with compute — FSDP2 automatically starts all-gathering the next unit while the current one computes.
