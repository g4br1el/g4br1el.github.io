Lesson 010 Performance Compilation

torch.compile + FSDP2: Tracing, Graph Breaks, Speedups

How FSDP2's DTensor design enables compilation, where it still breaks, and the real speedup on V100.

Why Compilation Matters for FSDP2

From Lesson 008, you know that ViT-Huge on your V100 NVLink cluster is compute-bound (ratio ~9×). Communication is fully hidden. So the only way to further improve throughput is to make the compute faster. torch.compile does this by:

  • Kernel fusion: Combines multiple small ops (LayerNorm → dropout → add → GELU) into single GPU kernels, reducing kernel launch overhead and memory round-trips
  • Memory planning: Optimizes intermediate tensor allocation, reducing fragmentation and cudaMalloc calls
  • Triton codegen: Generates optimized Triton kernels for fused operations (V100 supports Triton, though less optimally than Ampere+)
  • Operator reordering: Reorders independent operations for better GPU occupancy

On V100 with ViT-Huge, expect 10–20% throughput improvement from compilation. On A100/H100 the gains are larger (20–40%) due to better Triton support and hardware features.

The FSDP1 Problem (Why It Didn't Work Before)

# FSDP1 + torch.compile: every FSDP boundary was a graph break
#
# torch.compile traces the forward pass as a graph:
#   Input → Op1 → Op2 → ... → Output
#
# FSDP1's wrapper inserted Python-level hooks at each boundary:
#   Input → [GRAPH BREAK: FSDP unflatten] → Op1 → Op2 → [GRAPH BREAK: FSDP reshard]
#
# Result: N tiny graphs instead of one large one.
# Each graph break:
#   - Exits compiled code → returns to Python interpreter
#   - Triggers recompilation risk if shapes change
#   - Prevents cross-boundary fusion (can't fuse across breaks)
#
# With 32 transformer blocks: 64+ graph breaks per forward pass.
# Compilation overhead outweighed any speedup → net negative on FSDP1.

FSDP2's Compilation Story

FSDP2 was designed with torch.compile in mind. DTensor operations have registered decompositions that the compiler understands:

# FSDP2 + torch.compile: communication becomes graph nodes

# What the compiler sees (conceptual FX graph):
#
# %sharded_param = placeholder(param)          # DTensor, Shard(0)
# %full_param = all_gather(%sharded_param)     # Communication node
# %fp16_param = cast(%full_param, float16)     # Dtype cast
# %attn_out = scaled_dot_product_attention(%x, %fp16_param, ...)  # Fused attention
# %mlp_out = fused_mlp(%attn_out, %mlp_weights)                  # Fused MLP
# %grad = ... backward ...
# %scattered_grad = reduce_scatter(%grad)      # Communication node
#
# The compiler can:
# 1. Fuse everything BETWEEN communication nodes
# 2. Keep communication nodes as-is (they call NCCL — can't be compiled)
# 3. Optimize memory layout around communication boundaries
The key insight: FSDP2's communication ops (all-gather, reduce-scatter) become opaque nodes in the compiled graph. The compiler treats them as black-box functions with known input/output shapes and types. Everything between them — the actual model computation — is fully compiled and fused. No graph breaks at FSDP boundaries.

How to Apply torch.compile with FSDP2

import torch
from torch.distributed._composable.fsdp import fully_shard, MixedPrecisionPolicy
import timm


def build_compiled_fsdp2_model(mesh, mp_policy):
    """Build model with FSDP2 + torch.compile."""

    # 1. Build model
    model = timm.create_model("vit_huge_patch14_224", pretrained=False, num_classes=1000)

    # 2. Activation checkpointing (before FSDP2)
    model.set_grad_checkpointing(enable=True)

    # 3. Apply FSDP2
    for block in model.blocks:
        fully_shard(block, mesh=mesh, mp_policy=mp_policy)
    fully_shard(model, mesh=mesh, mp_policy=mp_policy)

    # 4. Compile AFTER FSDP2
    model = torch.compile(model)

    return model
Order: build → checkpoint → fully_shard → compile. This order is critical. torch.compile must come LAST because it wraps the model in a compiled callable. If you compile before sharding, fully_shard() would try to mutate a compiled module — which doesn't work reliably. If you shard before checkpointing, the hooks might not compose correctly with compilation. The canonical order from torchtitan is: model → AC → FSDP2 → compile.

Compilation Modes

# torch.compile offers several modes with different trade-offs:

# Default mode: balanced compile time vs runtime performance
model = torch.compile(model)

# "reduce-overhead" mode: minimizes Python overhead, uses CUDA graphs
# CAREFUL: CUDA graphs capture a fixed execution pattern — NCCL collectives
# inside a CUDA graph can deadlock if not carefully managed.
# As of PyTorch 2.5: this DOES work with FSDP2, but only in specific configs.
model = torch.compile(model, mode="reduce-overhead")

# "max-autotune" mode: tries many kernel variants, picks fastest
# Longer compile time (minutes), best runtime. Good for production.
model = torch.compile(model, mode="max-autotune")

# Recommendation for V100:
# Start with default mode. If compile time is acceptable (< 5 min),
# try "max-autotune" for production runs.
# Avoid "reduce-overhead" until you've verified it works with your
# specific FSDP2 + NCCL configuration.

Where Graph Breaks Still Occur

FSDP2 eliminates FSDP-boundary graph breaks, but other sources remain:

# Common graph break sources in ViT + FSDP2 training:

# 1. Python control flow that depends on tensor values
#    BAD:
if x.max() > threshold:  # Graph break! Compiler can't trace through this
    x = special_handling(x)
#    FIX: Use torch.where or masked operations instead

# 2. Data-dependent shapes
#    BAD:
mask = x > 0
filtered = x[mask]  # Dynamic shape → graph break
#    FIX: Use fixed-size operations with masking

# 3. print() or logging inside forward
#    BAD:
def forward(self, x):
    print(f"input shape: {x.shape}")  # Graph break!
    ...
#    FIX: Remove or guard with if not torch.compiler.is_compiling():

# 4. .item() or .numpy() calls (materialize to Python)
#    BAD:
loss_val = loss.item()  # Syncs GPU→CPU, breaks graph
#    FIX: Only call .item() outside compiled region

# 5. Custom ops without torch.library registration
#    Your NMS kernel (pybind11) would cause a graph break if called
#    inside compiled code. But since NMS runs post-model on predictions,
#    it's outside the compiled region — no issue for you.

Detecting Graph Breaks

# Method 1: Compile with fullgraph=True (strict mode — errors on any break)
try:
    model = torch.compile(model, fullgraph=True)
    # If this succeeds → no graph breaks in forward/backward!
    # If this fails → tells you exactly where the break is
except Exception as e:
    print(f"Graph break detected: {e}")

# Method 2: Use TORCH_LOGS to see breaks during compilation
# Set environment variable before running:
# export TORCH_LOGS="+dynamo"
# This prints detailed logs about what the compiler traced and where it broke.

# Method 3: torch._dynamo.explain()
import torch._dynamo
explanation = torch._dynamo.explain(model)(sample_input)
print(f"Graph breaks: {explanation.break_reasons}")
print(f"Number of graphs: {explanation.graph_count}")
# Ideal: graph_count = 1 (everything in one compiled graph)
# Acceptable: graph_count = 2-3 (a few breaks, still major fusion benefit)
# Bad: graph_count > 10 (too many breaks, compilation overhead dominates)
For timm's ViT-Huge: Most timm models compile cleanly with zero or few graph breaks in default mode. The scaled_dot_product_attention, LayerNorm, GELU, and linear layers are all fully traceable. The main risk is custom modifications you've added to the model (custom attention patterns, conditional logic, etc.).

What Gets Fused in Practice

For a ViT transformer block, torch.compile typically fuses:

Unfused (eager execution): ~15-20 separate CUDA kernel launches per block ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ LayerNorm → Q_proj → K_proj → V_proj → reshape → → scaled_dot_product_attention → out_proj → dropout → → residual_add → LayerNorm → FC1 → GELU → FC2 → → dropout → residual_add Each → is a kernel launch (overhead: ~5-10μs per launch on V100) Total overhead: 15 × 7.5μs ≈ 112μs per block × 32 blocks ≈ 3.6ms per forward Fused (compiled): ~4-6 kernel launches per block ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ [fused_norm_qkv_proj] → [sdpa_kernel] → [fused_out_proj_dropout_add] → → [fused_norm_fc1_gelu] → [fused_fc2_dropout_add] Kernel launches reduced from ~15 to ~5 per block Overhead: 5 × 7.5μs ≈ 37μs per block × 32 blocks ≈ 1.2ms per forward Saved: ~2.4ms in kernel launch overhead alone Plus: fused kernels avoid writing/reading intermediate results to GPU memory → Memory bandwidth savings → additional 5-10% speedup
The two sources of speedup: (1) Reduced kernel launch overhead (~2.4ms saved). (2) Reduced GPU memory bandwidth usage from fused kernels (intermediates stay in registers/shared memory instead of going to HBM and back). On V100 where HBM bandwidth is ~900 GB/s (less than A100's 2 TB/s), the memory bandwidth savings are proportionally more valuable.

Compilation and the Training Loop

"""
train_fsdp2_compiled.py — Complete script with torch.compile.
"""
import os
import time

import torch
import torch.nn as nn
from torch.utils.data import DataLoader, DistributedSampler
from torch.distributed._composable.fsdp import fully_shard, MixedPrecisionPolicy
from torch.distributed.device_mesh import init_device_mesh
import torch.distributed as dist

import timm


def main():
    dist.init_process_group("nccl")
    local_rank = int(os.environ["LOCAL_RANK"])
    world_size = dist.get_world_size()
    torch.cuda.set_device(local_rank)

    mesh = init_device_mesh("cuda", (world_size,))
    mp_policy = MixedPrecisionPolicy(param_dtype=torch.float16, reduce_dtype=torch.float32)

    # Build model
    model = timm.create_model("vit_huge_patch14_224", pretrained=False, num_classes=1000)
    model.set_grad_checkpointing(enable=True)

    # Apply FSDP2
    for block in model.blocks:
        fully_shard(block, mesh=mesh, mp_policy=mp_policy)
    fully_shard(model, mesh=mesh, mp_policy=mp_policy)

    # Compile (AFTER FSDP2)
    model = torch.compile(model)

    # Optimizer
    optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4, weight_decay=0.05)

    # Data
    dataset = SyntheticImageDataset(10_000, 224, 1000)
    sampler = DistributedSampler(dataset, num_replicas=world_size, rank=dist.get_rank())
    dataloader = DataLoader(
        dataset, batch_size=32, sampler=sampler,
        num_workers=4, pin_memory=True, drop_last=True,
    )

    # Training with compile warm-up awareness
    model.train()
    step_times = []

    for epoch in range(2):
        sampler.set_epoch(epoch)
        for batch_idx, (images, labels) in enumerate(dataloader):
            images = images.to(local_rank, non_blocking=True)
            labels = labels.to(local_rank, non_blocking=True)

            torch.cuda.synchronize()
            t0 = time.perf_counter()

            outputs = model(images)
            loss = nn.functional.cross_entropy(outputs, labels)
            loss.backward()
            torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
            optimizer.step()
            optimizer.zero_grad()

            torch.cuda.synchronize()
            t1 = time.perf_counter()

            step_time_ms = (t1 - t0) * 1000
            step_times.append(step_time_ms)

            if batch_idx % 10 == 0 and local_rank == 0:
                if batch_idx < 5:
                    label = "(compiling)" if batch_idx == 0 else "(warm-up)"
                else:
                    label = ""
                print(f"  [E{epoch}][B{batch_idx}] {step_time_ms:.1f}ms "
                      f"loss={loss.item():.4f} {label}")

    # Report (skip first 5 steps = compilation + warm-up)
    if local_rank == 0:
        steady_state = step_times[5:]
        avg = sum(steady_state) / len(steady_state)
        print(f"\nSteady-state avg step: {avg:.2f} ms")
        print(f"Throughput: {32 * world_size / (avg / 1000):.0f} img/s")
        print(f"Peak memory: {torch.cuda.max_memory_allocated(local_rank) / 1e9:.2f} GB")

        # Show compilation cost
        print(f"\nFirst step (compilation): {step_times[0]:.0f} ms")
        print(f"Step 2 (warm-up):         {step_times[1]:.0f} ms")
        print(f"Step 5+ (steady):         {avg:.1f} ms")

    dist.destroy_process_group()


class SyntheticImageDataset(torch.utils.data.Dataset):
    def __init__(self, n, size, classes):
        self.n, self.size, self.classes = n, size, classes
    def __len__(self): return self.n
    def __getitem__(self, i):
        return torch.randn(3, self.size, self.size), torch.randint(0, self.classes, (1,)).item()


if __name__ == "__main__":
    main()

Interaction: torch.compile + FSDP2 Hooks

Understanding how compilation interacts with FSDP2's hook mechanism:

# When you call torch.compile(model):
# 1. The compiler wraps model.__call__ (which calls forward)
# 2. On first invocation, it traces the forward pass
# 3. FSDP2's pre-forward hooks fire BEFORE the compiled region starts
#    (hooks are at module.__call__ level, not inside forward())
# 4. The compiled graph sees parameters as already-unsharded (Replicate)
# 5. Post-forward hooks fire AFTER the compiled forward returns

# Visually:
# model(input)
#   → __call__ dispatch
#     → PRE-FORWARD HOOK (FSDP2: all-gather) — NOT compiled, runs eagerly
#     → compiled_forward(input)              — COMPILED, optimized
#     → POST-FORWARD HOOK (FSDP2: free)      — NOT compiled, runs eagerly
#   → return output

# Implication: FSDP2's communication is OUTSIDE the compiled graph.
# The compiler only sees and optimizes the compute between communication points.
# This is by design — NCCL calls can't be compiled (they're side-effectful
# communication with other processes).
The compiled region is the compute within each FSDP unit. For a transformer block, this includes: LayerNorm → Q/K/V projection → attention → output projection → residual → LayerNorm → MLP → residual. All of this is compiled and fused. The FSDP2 communication (all-gather, reduce-scatter) remains as eager Python/NCCL calls surrounding the compiled region.

Compile Per-Module vs Whole Model

# Option A: Compile the whole model (recommended)
model = torch.compile(model)
# The compiler will trace through all blocks
# Produces the largest possible compiled regions
# Downside: longer initial compilation time

# Option B: Compile individual blocks (faster compile, but less fusion)
for block in model.blocks:
    block.forward = torch.compile(block.forward)
# Each block is compiled independently
# Cannot fuse across block boundaries
# Upside: faster compilation, easier debugging
# Downside: ~5% less fusion benefit

# Option C: Compile with dynamic=True for variable input shapes
model = torch.compile(model, dynamic=True)
# Allows different batch sizes without recompilation
# Slightly less optimized kernels (can't hard-code shapes)
# Useful during evaluation where batch size may vary

# For your training with fixed batch size and image size:
# Option A is best. Shapes are constant → compiler can specialize fully.

V100-Specific Compilation Considerations

# V100 differences from A100/H100 for torch.compile:

# 1. No native bf16 → all mixed-precision is fp16
#    Compiler generates fp16 Triton kernels (works fine)

# 2. Smaller L2 cache (6 MB vs 40-50 MB on A100)
#    Fused kernels that fit in L2 on A100 might spill to HBM on V100
#    Impact: some fusions less beneficial than on newer GPUs

# 3. Older Triton support
#    V100 (sm_70) has full Triton support but some advanced features
#    (like TMA loads on H100) aren't available
#    Impact: generated kernels are simpler, slightly less optimized

# 4. Tensor Core instruction set (HMMA vs newer HFMA2)
#    V100 Tensor Cores have different performance characteristics
#    torch.compile respects this and generates appropriate kernels

# 5. Limited GPU memory may constrain compilation memory
#    Compilation itself can use significant GPU memory for autotuning
#    If you OOM during compilation: try mode="default" instead of "max-autotune"

# Net impact on V100:
#   Expected speedup: 10-20% (vs 20-40% on A100/H100)
#   Still very much worth it for production training runs.

#   - Fused kernels may use different accumulation order
#   - Triton kernels may use different intermediate precision

# Verification:
def verify_compile_correctness(model_eager, model_compiled, sample_input):
    with torch.no_grad():
        out_eager = model_eager(sample_input)
        out_compiled = model_compiled(sample_input)
    diff = (out_eager - out_compiled).abs().max().item()
    print(f"Max abs diff: {diff:.2e}")
    assert diff < 1e-3, f"Compilation changed results too much: {diff}"

torch.compile + Activation Checkpointing Interaction

# When both are active:
# 1. Activation checkpointing discards intermediate activations
# 2. During backward, it RE-RUNS forward for each checkpointed block
# 3. torch.compile compiles BOTH:
#    - The original forward (for the forward pass)
#    - The re-computation (triggered during backward)
#
# The recomputation uses the SAME compiled kernels as the original forward
# (same graph structure, same shapes). So:
# - No additional compilation cost for checkpointing
# - The recomputed forward is equally fast as the original
# - Net: checkpointing's 33% compute overhead is on the COMPILED compute
#   (which is 10-20% faster) → effective overhead with compile:
#   33% × (1 - speedup) ≈ 33% × 0.85 ≈ 28% overhead

# This is why compile + checkpointing compose well:
# The recomputation is faster (compiled), partially offsetting the overhead.

Full Production Configuration

"""
Production-ready FSDP2 + compile configuration.
All optimizations from lessons 003-010 combined.
"""

def build_production_model(
    world_size: int,
    local_world_size: int,
    compile_model: bool = True,
    compile_mode: str = "default",
):
    """
    Canonical order:
    1. Build model (CPU)
    2. Activation checkpointing
    3. FSDP2 (children first, root last)
    4. torch.compile (last)
    """
    # Mesh (auto-detect topology)
    num_nodes = world_size // local_world_size
    if num_nodes == 1:
        mesh = init_device_mesh("cuda", (world_size,))
    else:
        mesh = init_device_mesh(
            "cuda", (num_nodes, local_world_size),
            mesh_dim_names=("replicate", "shard"),
        )

    # Mixed precision (V100)
    mp_policy = MixedPrecisionPolicy(
        param_dtype=torch.float16,
        reduce_dtype=torch.float32,
    )

    # Model
    model = timm.create_model("vit_huge_patch14_224", pretrained=False, num_classes=1000)

    # Activation checkpointing
    model.set_grad_checkpointing(enable=True)

    # FSDP2
    for block in model.blocks:
        fully_shard(block, mesh=mesh, mp_policy=mp_policy)
    fully_shard(model, mesh=mesh, mp_policy=mp_policy)

    # Compile
    if compile_model:
        model = torch.compile(model, mode=compile_mode)

    return model, mesh

The torch.compile + FSDP2 Mental Model

Complete picture: what runs where in one forward pass ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ For each FSDP unit (transformer block): ┌─── EAGER (Python) ─────────────────────────────────────────┐ │ Pre-forward hook: all-gather params (NCCL, comms stream) │ │ Pre-forward hook: cast fp32 → fp16 │ └────────────────────────────────────────────────────────────┘ ↓ ┌─── COMPILED (Inductor/Triton) ─────────────────────────────┐ │ Fused LayerNorm + Q/K/V projection │ │ Scaled dot-product attention (cuDNN/Triton) │ │ Fused output projection + dropout + residual │ │ Fused LayerNorm + FC1 + GELU │ │ Fused FC2 + dropout + residual │ └────────────────────────────────────────────────────────────┘ ↓ ┌─── EAGER (Python) ─────────────────────────────────────────┐ │ Post-forward hook: free unsharded params │ │ (Prefetch: start next block's all-gather on comms stream) │ └────────────────────────────────────────────────────────────┘
This is the final performance picture: FSDP2 manages communication eagerly (hooks, NCCL), while torch.compile optimizes everything inside — the actual neural network computation. They're orthogonal optimizations that multiply: FSDP2 gives you memory scalability + communication overlap, compile gives you faster compute within each unit.

Check Your Understanding

Q1: Why must torch.compile(model) be called AFTER fully_shard()?

Correct. fully_shard() modifies the module's parameters (replaces with DTensors) and registers forward/backward hooks. torch.compile() then wraps the fully-configured module for graph tracing. If you compiled first, fully_shard() would try to mutate a compiled module — the hooks and parameter replacements wouldn't be visible to the compiler. Note: FSDP2 hooks are NOT inside the compiled graph — they run eagerly at the __call__ level, surrounding the compiled forward.

Q2: FSDP2's communication operations (all-gather, reduce-scatter) are NOT inside the compiled graph. What is compiled?

Correct. The compiled region is the actual neural network computation within each FSDP unit's forward (and its corresponding backward). FSDP2's pre-forward hook (all-gather) runs eagerly BEFORE the compiled forward; post-forward hook (free params) runs eagerly AFTER. The compiler sees parameters as regular tensors (already unsharded and cast to fp16) and optimizes the math between communication points. Backward IS also compiled (torch.compile handles both directions).

Q3: Your first training step takes 45 seconds with torch.compile. Steps 5+ take 330ms. You're running a 50-step hyperparameter search. Should you use compile?

Correct. For 50 steps: compiled = 45s + 50×0.33s = 61.5s. Eager = 50×0.38s = 19s. Compilation makes the run 3× slower! Only enable compile when amortization makes sense (typically > 200-500 steps). However, if the TORCHINDUCTOR_CACHE_DIR has a warm cache from a previous run with the same model/shapes, compilation is near-instant — in that case, always compile. Answer B is partially valid only if the cache is pre-warmed.

Q4: You observe that with torch.compile + FSDP2, throughput improved by 15% but peak memory increased by 8%. Why?

Correct. Compilation can increase memory usage because: (1) Fused kernels may use larger workspace buffers than individual kernels. (2) The Inductor memory planner pre-allocates buffer pools for known-size intermediates rather than using the default allocator's more conservative approach. (3) The autograd graph for compiled regions stores additional nodes for the decomposed operations. The 8% increase is typical and expected — it's the trade-off for 15% faster compute. If memory is tight, this might force you to reduce batch size, partially offsetting the throughput gain.

Key Takeaways

  1. Canonical order: build → AC → fully_shard → compile. Compile always comes last.
  2. FSDP2 was designed for torch.compile. DTensor ops have compiler support; no graph breaks at FSDP boundaries (unlike FSDP1).
  3. Communication stays eager; compute is compiled. Pre/post-forward hooks (NCCL) run outside the compiled graph. Everything between (attention, MLP, norms) is compiled and fused.
  4. Expected V100 speedup: 10–20%. Sources: kernel fusion (40%), memory bandwidth savings (35%), better occupancy (25%).
  5. Compilation cost: 30–60s first step. Only amortizes over long runs (>200 steps). Use TORCHINDUCTOR_CACHE_DIR for persistent caching across jobs.
  6. Compile may increase memory by 5–10%. Fused kernels use larger workspace buffers. Factor this into your batch size calculations.
  7. Use torch._dynamo.explain() to find graph breaks. timm ViTs compile cleanly; custom models may need fixes (remove .item(), control flow on tensor values, etc.).
  8. Compile + checkpointing compose well: recomputation uses the same compiled kernels, making the recomputed forward faster. Effective overhead drops from 33% to ~28%.
