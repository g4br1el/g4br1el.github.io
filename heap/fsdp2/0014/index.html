Lesson 014 Integration Migration

Migrating an Existing DDP Pipeline to FSDP2

A systematic process for converting your Fraunhofer training framework from DDP to FSDP2 with minimal disruption and full correctness verification.

Migration Philosophy

The goal is NOT to rewrite your training pipeline. It's to surgically replace the distribution strategy while keeping everything else (data loading, logging, evaluation, model definition) unchanged. FSDP2's composable design makes this possible — but you need a structured approach to avoid subtle bugs.

The migration has 7 discrete steps. Each step is independently testable. You can stop at any step and have a working system.

Step 0: Audit Your Current DDP Pipeline

Before changing anything, document what your existing DDP code does:

# Typical DDP pipeline structure (what you likely have):

Step 1: Remove DDP Wrapping, Add FSDP2

The minimal change — replace the distribution strategy:

# AFTER (FSDP2):
from torch.distributed._composable.fsdp import fully_shard, MixedPrecisionPolicy

model = build_model()  # On CPU — do NOT call .cuda()

mesh = init_device_mesh("cuda", (world_size,))

fully_shard(model, mesh=mesh, mp_policy=mp_policy)
The critical helper: get_transformer_blocks(). You need to identify which submodules are the repeated units to shard individually. For timm models: model.blocks. For HuggingFace ViT: model.vit.encoder.layer. For custom models: whatever your repeated layer container is. This is the ONE model-specific knowledge you need.

Finding the Sharding Units in Any Model

def find_sharding_units(model: nn.Module) -> list[nn.Module]:
    """
    Heuristic: find repeated modules that should be individual FSDP units.
    Works for most transformer architectures.
    """
    # Strategy: find the largest repeated submodule class
    from collections import Counter

    class_counts = Counter()
    class_modules = {}

    for name, module in model.named_modules():
        cls_name = type(module).__name__
        class_counts[cls_name] += 1
        if cls_name not in class_modules:
            class_modules[cls_name] = []
        class_modules[cls_name].append((name, module))

    # Find the most-repeated class with substantial parameters
    candidates = []
    for cls_name, count in class_counts.most_common():
        if count < 4:  # At least 4 repetitions
            continue
        modules = class_modules[cls_name]
        param_count = sum(p.numel() for p in modules[0][1].parameters())
        if param_count > 1_000_000:  # At least 1M params per unit
            candidates.append((cls_name, count, param_count, modules))

    if not candidates:
        print("⚠️ No obvious sharding units found. Shard root only.")
        return []

    # Pick the one with most params × count (total contribution)
    best = max(candidates, key=lambda x: x[1] * x[2])
    cls_name, count, param_count, modules = best

    print(f"[Auto-detect] Sharding unit: {cls_name} "
          f"({count} instances, {param_count:,} params each)")

    return [m for _, m in modules]

Step 2: Remove AMP / GradScaler

# BEFORE (DDP + AMP):
scaler = torch.cuda.amp.GradScaler()

for images, labels in dataloader:
    with torch.cuda.amp.autocast(dtype=torch.float16):
        outputs = model(images)
        loss = criterion(outputs, labels)

    scaler.scale(loss).backward()
    scaler.unscale_(optimizer)
    torch.nn.utils.clip_grad_norm_(model.module.parameters(), max_norm=1.0)
    scaler.step(optimizer)
    scaler.update()
    optimizer.zero_grad()


# AFTER (FSDP2 — precision handled by mp_policy):
for images, labels in dataloader:
    outputs = model(images)           # No autocast needed
    loss = criterion(outputs, labels)

    loss.backward()                   # No scaler needed
    torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)  # No .module!
    optimizer.step()                  # Direct step
    optimizer.zero_grad()
Simplification win: Five lines of AMP/scaler ceremony collapse to zero. The MixedPrecisionPolicy you passed to fully_shard() handles all dtype transitions internally. Your training loop becomes cleaner and less error-prone.

Breaking change: DDP checkpoints (.pt files) are NOT directly loadable by FSDP2 (they're full state dicts, FSDP2 expects sharded). To migrate existing checkpoints: load the .pt on CPU into the unsharded model BEFORE calling fully_shard(), then save with DCP for future use.

Migrating Existing Checkpoints

def migrate_ddp_checkpoint_to_fsdp2(
    ddp_checkpoint_path: str,
    model: nn.Module,
    mesh,
    mp_policy,
    output_dcp_dir: str,
):
    """
    One-time migration: load old DDP checkpoint, save as DCP.
    Run this once, then use DCP checkpoints going forward.
    """
    # 1. Load DDP checkpoint into unsharded model (on CPU)
    state_dict = torch.load(ddp_checkpoint_path, map_location="cpu", weights_only=True)

    # Handle model.module prefix if saved from DDP
    if any(k.startswith("module.") for k in state_dict.keys()):
        state_dict = {k.replace("module.", "", 1): v for k, v in state_dict.items()}

    model.load_state_dict(state_dict, strict=True)

    if dist.get_rank() == 0:
        print(f"[Migrate] Loaded DDP checkpoint: {ddp_checkpoint_path}")

    # 2. Apply FSDP2 (this distributes the loaded weights)
    for block in find_sharding_units(model):
        fully_shard(block, mesh=mesh, mp_policy=mp_policy)
    fully_shard(model, mesh=mesh, mp_policy=mp_policy)

    # 3. Save as DCP
    from torch.distributed.checkpoint.state_dict import get_model_state_dict
    state = {"model": get_model_state_dict(model)}
    dcp.save(state, checkpoint_id=output_dcp_dir)

    if dist.get_rank() == 0:
        print(f"[Migrate] Saved DCP checkpoint: {output_dcp_dir}")

    return model

Step 6: Handle Framework-Specific Patterns

Your Fraunhofer framework likely has custom patterns. Here are common ones and their FSDP2 equivalents:

DDP PatternFSDP2 EquivalentNotes
model.no_sync() for grad accum Not needed — just accumulate FSDP2 must all-gather every forward anyway; reduce-scatter still happens per micro-batch
Custom LR scheduler accessing model.module Access model directly No .module indirection
EMA (Exponential Moving Average) model EMA on sharded params (see below) Requires care with DTensor
Multi-task heads with different LR Use param_groups with sharded params Works identically — param_groups reference the sharded DTensors
Gradient penalty (accessing params in forward) Works — params are Replicate during forward Access params inside forward() as normal
torch.cuda.amp.autocast in specific submodules Remove — mp_policy handles globally Per-module precision via different mp_policy per FSDP unit if needed
SyncBatchNorm Same — SyncBN works with FSDP2 Ensure SyncBN uses the correct process group
Custom backward hooks (register_hook) Works on DTensor grads Hook receives sharded grad tensor; handle accordingly

EMA with FSDP2 (Common in Vision)

class ShardedEMA:
    """
    Exponential Moving Average compatible with FSDP2 sharded parameters.

    Key insight: EMA state is maintained as SHARDED tensors matching
    the training model's sharding. No gathering needed.
    """

    def __init__(self, model: nn.Module, decay: float = 0.999):
        self.decay = decay
        # Store EMA of sharded params (same shape as model params)
        self.shadow = {}
        for name, param in model.named_parameters():
            if hasattr(param, '_local_tensor'):
                # DTensor: store EMA of the local shard
                self.shadow[name] = param._local_tensor.detach().clone()
            else:
                self.shadow[name] = param.detach().clone()

    @torch.no_grad()
    def update(self, model: nn.Module) -> None:
        """Update EMA after optimizer step."""
        for name, param in model.named_parameters():
            if name not in self.shadow:
                continue

            local = param._local_tensor if hasattr(param, '_local_tensor') else param
            self.shadow[name].lerp_(local, 1.0 - self.decay)

    def apply_to(self, model: nn.Module) -> None:
        """Replace model params with EMA values (for evaluation)."""
        for name, param in model.named_parameters():
            if name not in self.shadow:
                continue

            if hasattr(param, '_local_tensor'):
                param._local_tensor.copy_(self.shadow[name])
            else:
                param.data.copy_(self.shadow[name])

    def state_dict(self) -> dict:
        """For checkpointing EMA state."""
        return {"shadow": self.shadow, "decay": self.decay}

    def load_state_dict(self, state: dict) -> None:
        self.shadow = state["shadow"]
        self.decay = state["decay"]


# Usage:
ema = ShardedEMA(model, decay=0.9999)

for step, (images, labels) in enumerate(dataloader):
    # ... forward, backward, optimizer step ...
    ema.update(model)

# For evaluation:
ema.apply_to(model)
# ... evaluate ...
# Restore original weights after eval if continuing training

Step 7: Verify Correctness

The most critical step. After migration, you must verify that FSDP2 produces the same results as DDP (within fp precision):

def verify_migration_correctness(
    ddp_checkpoint: str,
    fsdp2_model: nn.Module,
    sample_batch: tuple[torch.Tensor, torch.Tensor],
    local_rank: int,
    tolerance: float = 1e-4,
):
    """
    Verify that FSDP2 model produces same output as DDP for same input.

    Run this once after migration, on the same input data.
    """
    images, labels = sample_batch
    images = images.to(local_rank)
    labels = labels.to(local_rank)

    # --- FSDP2 forward ---
    fsdp2_model.eval()
    with torch.no_grad():
        fsdp2_output = fsdp2_model(images)
        fsdp2_loss = nn.functional.cross_entropy(fsdp2_output, labels)

    # --- DDP reference (single GPU, same weights) ---
    if local_rank == 0:
        from torch.distributed.checkpoint.state_dict import get_model_state_dict, StateDictOptions

        # Get full weights from FSDP2 model
        options = StateDictOptions(full_state_dict=True, cpu_offload=True)
        full_state = get_model_state_dict(fsdp2_model, options=options)

        # Build reference model
        ref_model = build_model().cuda()
        ref_model.load_state_dict(full_state)
        ref_model.eval()

        with torch.no_grad():
            with torch.cuda.amp.autocast(dtype=torch.float16):  # Match FSDP2's mp
                ref_output = ref_model(images)
                ref_loss = nn.functional.cross_entropy(ref_output, labels)

        # Compare
        output_diff = (fsdp2_output - ref_output).abs().max().item()
        loss_diff = abs(fsdp2_loss.item() - ref_loss.item())

        print(f"[Verify] Output max diff: {output_diff:.2e} (tolerance: {tolerance})")
        print(f"[Verify] Loss diff: {loss_diff:.2e}")

        if output_diff < tolerance and loss_diff < tolerance:
            print("[Verify] ✓ Migration correctness verified!")
        else:
            print("[Verify] ⚠️ Differences exceed tolerance — investigate!")
            print("  Common causes: different autocast scope, missing weight loading,")
            print("  different dropout state, or batch normalization running stats.")

Incremental Migration Strategy

For a production framework, don't migrate everything at once. Use a feature flag:

def create_distributed_model(
    model: nn.Module,
    strategy: str = "ddp",  # "ddp" or "fsdp2"
    local_rank: int = 0,
    world_size: int = 1,
    **kwargs,
) -> nn.Module:
    """
    Factory function that supports both DDP and FSDP2.
    Allows gradual migration and A/B comparison.
    """
    if strategy == "ddp":
        model = model.cuda()
        model = torch.nn.parallel.DistributedDataParallel(
            model, device_ids=[local_rank]
        )
        return model

    elif strategy == "fsdp2":
        mesh = init_device_mesh("cuda", (world_size,))
        mp_policy = MixedPrecisionPolicy(
            param_dtype=torch.float16, reduce_dtype=torch.float32
        )

        if kwargs.get("activation_checkpointing", True):
            if hasattr(model, "set_grad_checkpointing"):
                model.set_grad_checkpointing(enable=True)

        sharding_units = find_sharding_units(model)
        for unit in sharding_units:
            fully_shard(unit, mesh=mesh, mp_policy=mp_policy)
        fully_shard(model, mesh=mesh, mp_policy=mp_policy)

        return model

    else:
        raise ValueError(f"Unknown strategy: {strategy}")

def train_step(
    model: nn.Module,
    images: torch.Tensor,
    labels: torch.Tensor,
    optimizer: torch.optim.Optimizer,
    strategy: str,
    scaler=None,  # Only for DDP
    max_grad_norm: float = 1.0,
) -> float:
    """
    Strategy-agnostic training step.
    """
    if strategy == "ddp":
        with torch.cuda.amp.autocast(dtype=torch.float16):
            outputs = model(images)
            loss = nn.functional.cross_entropy(outputs, labels)
        scaler.scale(loss).backward()
        scaler.unscale_(optimizer)
        torch.nn.utils.clip_grad_norm_(model.module.parameters(), max_grad_norm)
        scaler.step(optimizer)
        scaler.update()
        optimizer.zero_grad()

    elif strategy == "fsdp2":
        outputs = model(images)
        loss = nn.functional.cross_entropy(outputs, labels)
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), max_grad_norm)
        optimizer.step()
        optimizer.zero_grad()

    return loss.item()

Common Migration Pitfalls

PitfallSymptomFix
Calling model.cuda() before fully_shard() Works but wastes GPU memory briefly; for very large models, OOM Remove .cuda() — let fully_shard() handle placement
Building optimizer before fully_shard() Optimizer states are full-sized → no memory savings from sharding Always: model → shard → optimizer
Keeping GradScaler with FSDP2 Double-scaling; incorrect gradient magnitudes; training diverges Remove GradScaler entirely; reduce_dtype=fp32 handles underflow
Using model.module (DDP habit) AttributeError: 'ViT' has no attribute 'module' Remove .module everywhere — FSDP2 doesn't wrap
Saving checkpoint from rank 0 only Other ranks hang waiting at the next collective dcp.save() is collective — all ranks must call
Loading old .pt checkpoint after fully_shard() Shape mismatch errors (full shapes vs sharded) Load .pt BEFORE fully_shard(), or convert to DCP first
Custom forward hooks that call .item() or print() Graph breaks (if using torch.compile); performance loss Guard with if not torch.compiler.is_compiling():
Different random seeds across ranks for model init Parameters differ across ranks → reduce-scatter produces garbage Ensure all ranks use same seed for model init (or broadcast from rank 0)

Check Your Understanding

Q1: You're migrating a DDP pipeline that uses model.no_sync() for gradient accumulation (4 micro-batches). What's the FSDP2 equivalent?

Correct. In DDP, model.no_sync() skips the gradient all-reduce on intermediate micro-batches — a valid optimization because DDP has full params on each rank. In FSDP2, you CANNOT skip the forward all-gather (params are sharded — no compute without gathering). The reduce-scatter theoretically could be deferred, but the practical benefit is minimal and the API isn't straightforward. Just accumulate normally: each micro-batch triggers full communication, and the optimizer steps once after N accumulations. The loss in communication efficiency is unavoidable with FSDP2's sharding model.

Q2: Your existing DDP pipeline saves checkpoints with torch.save(model.module.state_dict(), path) on rank 0. After migrating to FSDP2, you want to load this old checkpoint for continued training. What's the correct approach?

Correct. The simplest migration path: build model on CPU → torch.load() + model.load_state_dict() (standard PyTorch, on CPU) → then fully_shard(). The sharding operation distributes the already-loaded weights across ranks. This works because at the point of loading, the model is still a regular (unsharded) model with regular parameters. Answer D also works but requires an extra conversion step. Answer B is wrong — DCP cannot read standard .pt files. Answer C fails because after fully_shard(), parameters are sharded DTensors and won't accept full-sized tensors from load_state_dict().

Q3: After migration, you notice that FSDP2 training loss is consistently 0.01 higher than DDP for the same data after 100 steps. Is this a bug?

Correct. A 0.01 loss difference after 100 steps is within expected floating-point divergence. Causes: (1) DDP uses all-reduce (reduce-scatter + all-gather), FSDP2 uses reduce-scatter directly — different summation order means different fp rounding. (2) DDP's autocast scope may differ slightly from FSDP2's MixedPrecisionPolicy dtype transitions. (3) Activation checkpointing (if added) changes the recomputation graph slightly. These small differences accumulate over steps but don't affect convergence. If the difference were > 1.0 or growing exponentially, THEN investigate.

Q4: Your framework has a hook that logs gradient statistics: for p in model.module.parameters(): log(p.grad.norm()). After FSDP2 migration, what changes?

Correct. After FSDP2's reduce-scatter, p.grad is a sharded DTensor with local shape [P/N, ...]. Calling .norm() on a DTensor computes the norm correctly (DTensor handles the distributed reduction internally for norm operations). However, if you access p.grad._local_tensor.norm(), you get only the local shard's norm — NOT the global gradient norm. For correct global gradient norms, use torch.nn.utils.clip_grad_norm_ (which handles DTensors) or call p.grad.norm() which internally triggers the correct distributed computation. The key change: remove .module and understand that gradients are sharded DTensors, not regular tensors.

Key Takeaways

  1. Migration is surgical, not a rewrite. 7 discrete steps, each independently testable. Data loading, model definition, evaluation metrics — all unchanged.
  2. The core diff: Remove DDP wrap + GradScaler + autocast + .module. Add DeviceMesh + MixedPrecisionPolicy + per-block fully_shard() + root fully_shard().
  3. Order matters: build model (CPU) → load pretrained (if any) → AC → fully_shard (children → root) → optimizer → [optional: compile].
  4. Checkpoint migration: Load old .pt BEFORE sharding. Save with DCP going forward. One-time conversion for existing checkpoints.
  5. Feature flag approach: Support both DDP and FSDP2 in your framework via a config switch. This enables gradual rollout and A/B testing.
  6. Verify correctness: Compare forward outputs, gradient norms, and loss curves between DDP and FSDP2. Small fp differences (< 1e-4 relative per step) are expected and harmless.
  7. model.no_sync() has no FSDP2 equivalent for the all-gather. Gradient accumulation still works but doesn't save communication.
