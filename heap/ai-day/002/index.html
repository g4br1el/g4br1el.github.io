2. Why LLM Inference Is Fundamentally Different

With CNNs (your domain), inference is straightforward: one forward pass, fixed input shape, fixed compute. You build a TensorRT engine, optimize the graph, and you're done. LLM inference breaks every assumption:

PropertyCNN Inference (your experience)LLM Inference (new)
Compute pattern Single forward pass Autoregressive: N sequential forward passes for N output tokens
Bottleneck Compute-bound (FLOPS) Memory-bandwidth-bound (weight loading dominates)
Input shape Fixed (e.g., 224×224×3) Variable sequence length, growing at each step
State Stateless Stateful: KV-cache grows with sequence length
Batching Static padding to max shape Dynamic: requests arrive/finish at different times
Latency metric Single number (ms/image) Two numbers: TTFT + TPS (explained below)
Memory scaling Constant (fixed activations) Linear with sequence length (KV-cache)

The Two Phases of LLM Inference

Every LLM inference request has two distinct phases with different compute characteristics:

  1. Prefill (prompt processing): Process all input tokens in parallel. This IS compute-bound (like a CNN forward pass). Produces the KV-cache for all input positions. Measured by TTFT (Time To First Token).
  2. Decode (token generation): Generate tokens one at a time, each requiring a forward pass through the full model but only for a single token. This is memory-bandwidth-bound because you load all model weights for a single token's worth of compute. Measured by TPS (Tokens Per Second) or inter-token latency.

The decode phase is the bottleneck. For a 70B model in FP16, each token requires loading ~140 GB of weights from HBM. On an H100 (3.35 TB/s bandwidth), that's ~42 ms per token minimum, even ignoring KV-cache reads. This is why quantization matters so much for LLMs — it directly reduces the bytes loaded per token.

2.1 The Arithmetic Intensity Problem

Arithmetic intensity = FLOPs / bytes loaded. For decode phase with batch size 1: 

# For a single token through a linear layer (d_in × d_out):
FLOPs = 2 × d_in × d_out          (matmul)
Bytes = d_in × d_out × bytes_per_param  (load entire weight matrix)

# For Llama-3 70B, FP16:
# Arithmetic intensity ≈ 2 / 2 = 1 FLOP/byte
# H100 roofline: 3958 TFLOPS / 3350 GB/s ≈ 1181 FLOPS/byte needed for compute-bound

# → Decode is ~1000× below the roofline ridge point
# → GPU compute units are almost entirely idle during decode
# → You're paying for TFLOPS but bottlenecked on bandwidth

This is why batching is critical: if you process B tokens simultaneously, arithmetic intensity scales by B. At batch size 64, you're at 64 FLOPS/byte — still memory-bound on H100, but much better GPU utilization.

Your mental model: Think of it like your CUDA kernel profiling work — but instead of optimizing compute occupancy, the entire game is maximizing memory bandwidth utilization and amortizing weight loads across as many tokens as possible. The roofline analysis you'd do for a CUDA kernel applies identically here.

3. The KV-Cache: LLM's Unique Memory Challenge

3.1 What It Is

In self-attention, each token attends to all previous tokens via Query × Key and then weighted sum over Values. Without caching, generating token N requires recomputing attention for all N positions — O(N²) total compute for a sequence.

The KV-cache stores the Key and Value projections of all previous tokens so they don't need to be recomputed. Each new token only computes its own Q, K, V and attends to the cached K, V: 

# KV-cache memory per token per layer:
bytes_per_token_per_layer = 2 × n_heads × d_head × bytes_per_element
# (2 for K and V, n_heads × d_head = d_model typically)

# For Llama-3 70B (80 layers, 64 KV-heads × 128 dim, FP16):
# Per token: 2 × 64 × 128 × 2 bytes × 80 layers = 2.62 MB per token
# For 4096 tokens: 2.62 MB × 4096 = 10.7 GB
# For 128k context: 2.62 MB × 131072 = 336 GB (!)

# This is why long-context inference is a memory nightmare.
# The KV-cache can exceed the model weights themselves.

3.2 Paged Attention (vLLM → TensorRT-LLM)

Classic KV-cache allocation pre-allocates contiguous memory for the maximum sequence length per request. If you allocate for 4096 tokens but the response is only 200 tokens, you've wasted 95% of that memory. With many concurrent requests, this fragmentation kills throughput.

Paged Attention (Kwon et al., 2023) borrows from OS virtual memory: KV-cache is stored in fixed-size "pages" (blocks) that can be non-contiguous in physical GPU memory. A page table maps logical token positions to physical memory blocks. 

# Paged Attention benefits:
# 1. Near-zero memory waste — allocate pages on demand
# 2. Memory sharing — identical prefixes share KV pages (copy-on-write)
#    e.g., system prompt cached once, shared across all requests
# 3. Dynamic memory — no need to know max sequence length upfront
# 4. Preemption — can evict pages to disk/CPU to handle load spikes

# TensorRT-LLM implements this as "KV-cache block management"
# Configured via: kv_cache_config in the executor API

Why This Matters for Performance Engineering

KV-cache management is now the primary determinant of serving throughput — not model compute. A well-tuned KV-cache system (page size, eviction policy, prefix caching hit rate) can 2–3× throughput without touching the model itself. This is exactly the kind of systems-level optimization the JR1980206 role handles.

Key Architecture: The Executor API

TensorRT-LLM's runtime is centered on the Executor — a C++ component that manages:

  • Request scheduling (which requests run in this iteration)
  • KV-cache block allocation/deallocation
  • In-flight batching (inserting new requests, removing completed ones)
  • Multi-GPU coordination (tensor parallelism across NCCL communicators)

Think of it as a "mini OS" for LLM inference — it solves the same scheduling/memory problems an OS solves for processes, but for concurrent LLM requests.

4.1 In-Flight Batching (Continuous Batching)

In classic TensorRT serving, you batch N requests, wait for all to complete, then start the next batch. Short requests are blocked by long ones. GPU utilization drops as requests finish at different times.

In-flight batching (Orca, Yu et al., 2022) operates at the iteration level: each decode step, the scheduler can:

  • Add new requests that just arrived (insert into the batch)
  • Remove requests that just finished (free their KV-cache)
  • Preempt low-priority requests if memory is exhausted
# Iteration-level scheduling (pseudocode):
while requests_pending():
    # 1. Select which requests participate in this decode step
    active_batch = scheduler.select(
        pending_requests,
        available_kv_blocks,
        max_batch_tokens   # memory constraint
    )

    # 2. Run one decode step for all active requests
    #    (each request generates exactly 1 token)
    new_tokens = model.decode_step(active_batch)

    # 3. Check stopping criteria
    for req in active_batch:
        if req.is_finished(new_tokens[req]):
            scheduler.release(req)  # free KV blocks
            output_queue.put(req)

    # 4. Accept new arrivals
    scheduler.enqueue(new_arrivals())

The result: GPU utilization stays high because the batch is always full. Throughput improvements of 2–5× over static batching are typical, with no latency penalty.

Your analogy: Think of this like Slurm job scheduling — but at microsecond granularity. Instead of scheduling jobs to nodes, you're scheduling inference requests to GPU memory blocks. The constraints are identical: memory capacity, fairness, priority, preemption.

5. Quantization for LLMs

You already know INT8 PTQ and calibration. LLM quantization has the same goal (reduce memory → faster decode) but different challenges:

  • Outlier features: LLMs have activation outliers (values 100× larger than median) concentrated in a few channels. Naive per-tensor INT8 quantization destroys accuracy because the dynamic range is dominated by outliers.
  • Weight-only vs. weight+activation: Since decode is memory-bound, quantizing only weights (keeping activations in FP16) still gives the full speedup — the bottleneck is weight loading.
  • Granularity matters more: Per-channel and per-group quantization (e.g., 128-element groups) is essential for aggressive formats like INT4.

5.1 Quantization Methods Landscape

MethodWhat It QuantizesPrecisionKey IdeaAccuracy Impact

AWQ Weights only INT4 (group-wise) Protect salient weights (identified by activation magnitude) with per-channel scaling Very low for INT4
GPTQ Weights only INT4/INT3 Layer-wise optimal quantization using second-order information (Hessian approx) Low, but requires calibration data
FP8 (Hopper) Weights + activations FP8 E4M3 Native HW support. Per-tensor dynamic scaling. Drop-in via Transformer Engine Negligible (well within noise)

SmoothQuant — The Clever Trick

The insight: if activation channel j has outliers (large dynamic range) but the corresponding weight column j has small values, you can divide the activation by a scaling factor s_j and multiply the weight by the same s_j. Mathematically equivalent (Y = XW = (X/s)(sW)), but now both are "smooth" — easier to quantize. 

# SmoothQuant transformation:
# Original: Y = X @ W
# Smoothed: Y = (X @ diag(s)^-1) @ (diag(s) @ W)
# Where s_j = max(|X_j|)^α / max(|W_j|)^(1-α), α ∈ [0.5, 0.75]

# After smoothing, both X' and W' have manageable dynamic ranges
# → INT8 quantization works for both with minimal error

FP8 on Hopper: What You Need to Know

Two formats defined by Micikevicius et al. (2022):

  • E4M3 (4-bit exponent, 3-bit mantissa): Range ±448, precision 0.0625 at scale 1. Used for forward pass (weights and activations).
  • E5M2 (5-bit exponent, 2-bit mantissa): Range ±57344, lower precision. Used for gradients (needs wider range, can tolerate noise).

On Hopper, FP8 matrix multiply is done by the Tensor Cores natively — 2× throughput vs FP16. The Transformer Engine handles per-tensor scaling automatically: it tracks the maximum absolute value of each tensor (using a delayed scaling strategy — the scale from iteration N is used at iteration N+1) and requantizes on the fly.

For inference specifically, FP8 E4M3 for both weights and activations is standard. The accuracy loss is negligible for most models — it's essentially a free 2× speedup on Hopper.

Your existing knowledge extension: You've done INT8 PTQ with TensorRT (calibration, histogram entropy, per-tensor vs per-channel). FP8 is actually simpler — no calibration dataset needed for the common "delayed scaling" approach. The scaling factors are computed online from the previous iteration's statistics. AWQ/GPTQ are analogous to your INT8 calibration workflow but with more sophisticated weight-selection heuristics.

5.2 KV-Cache Quantization

A frontier technique: quantize the KV-cache itself (not just weights) to INT8 or FP8. Since the KV-cache is the memory bottleneck for long sequences, compressing it directly increases the number of concurrent requests you can serve: 

# KV-cache quantization impact:
# Llama-3 70B, 4096 context, FP16 KV-cache:
#   KV per request: 10.7 GB
#   With 80 GB GPU, ~5 concurrent requests (after model weights)

# Same model, INT8 KV-cache:
#   KV per request: 5.35 GB
#   With 80 GB GPU, ~10 concurrent requests
#   → 2× throughput improvement from KV quantization alone

# TensorRT-LLM supports FP8 and INT8 KV-cache via:
# quantize(model, quant_config=QuantConfig(kv_cache_quant_algo="FP8"))

6. Speculative Decoding

The decode phase is memory-bandwidth-bound: each token requires loading all weights for minimal compute. Speculative decoding trades compute for latency by exploiting the fact that GPU compute is underutilized during decode: 

# Speculative decoding algorithm:
# 1. A small "draft" model (e.g., 1B params) generates K candidate tokens quickly
# 2. The large "target" model verifies all K tokens in ONE forward pass (parallel)
# 3. Accept tokens where draft and target agree; reject from first disagreement

# Example: K=5 draft tokens
# Draft generates: ["The", "cat", "sat", "on", "the"]
# Target verifies in parallel (single forward pass, like prefill)
# Target agrees with first 4, disagrees at position 5
# → Accept 4 tokens in 1 target forward pass instead of 4 separate passes

# Speedup depends on acceptance rate α:
# Expected tokens per step = 1/(1-α) (geometric distribution)
# If α = 0.8: expected 5 tokens per target forward pass → ~5× latency reduction
# If α = 0.5: expected 2 tokens → ~2× latency reduction

# Acceptance rate depends on domain (structured text → high α)
# and draft model quality (larger draft → higher α but slower draft)

Key variants in TensorRT-LLM:

  • Draft-model speculative decoding: Separate smaller model as draft
  • Self-speculative / Medusa: Additional prediction heads on the target model itself (no separate model needed, but requires fine-tuning the heads)
  • Eagle: Uses hidden states from previous tokens to predict future tokens via a lightweight autoregressive head
  • Lookahead decoding: Parallel Jacobi iteration without a draft model

When Speculative Decoding Helps (and When It Doesn't)

  • Helps: Low-batch-size, latency-sensitive scenarios (interactive chat, coding assistants). When decode is strongly memory-bound and compute is idle.
  • Doesn't help: High-batch-size throughput scenarios (offline processing). At large batch sizes, decode is already closer to compute-bound, and the extra draft model compute competes with serving more requests.

7. CUDA Graphs for LLM Inference

Each decode step launches hundreds of small CUDA kernels (attention, FFN layers, norms, etc.). The CPU-side kernel launch overhead (~5–10 μs per kernel) accumulates to milliseconds per step — significant when a decode step should take ~20–40 ms total.

CUDA Graphs capture an entire decode step as a single GPU-side graph, eliminating per-kernel launch overhead. TensorRT-LLM uses them aggressively: 

# Without CUDA Graphs:
# CPU launches 200+ kernels sequentially
# Each launch: CPU-GPU synchronization + overhead
# Total overhead: ~1-2 ms per decode step (5-10% of total time)

# With CUDA Graphs:
# First iteration: record all kernel launches into a graph
# Subsequent iterations: replay the graph with a single CPU call
# Overhead: ~10 μs per decode step

# Constraint: Graph topology must be static
# → Input tensor shapes must be fixed within a graph
# → TensorRT-LLM pre-builds graphs for common batch sizes
# → When batch size changes (request arrives/finishes), switch graphs

# This is why in-flight batching + CUDA graphs interact subtly:
# Batch size changes every iteration → need graph switching logic
Direct connection to your work: You write custom CUDA kernels and understand launch overhead. The JR1980206 role specifically mentions "Graph Compilation" as a new SW feature. CUDA Graphs for LLM inference is exactly this. Your profiling experience (measuring kernel launch overhead, GPU utilization gaps) directly applies to understanding when CUDA Graphs help and what their limitations are (static shapes, graph switching cost).

The Throughput–Latency Trade-off

Larger batch sizes improve throughput (more tokens/sec total) but increase per-request latency (each request gets less bandwidth share). This is the fundamental tension in LLM serving:

  • Interactive (chat): Optimize for TTFT < 500ms and TPS > 30 (human reading speed). Batch size limited.
  • Batch processing (summarization, classification): Maximize throughput. Latency can be seconds. Pack as many requests as GPU memory allows.

The scheduler must balance these — this is where the engineering complexity lives.

10. Structured Sparsity (2:4)

Hopper and Blackwell Tensor Cores support 2:4 structured sparsity: in every group of 4 consecutive weights, exactly 2 must be zero. The hardware skips zero computations, giving 2× speedup with zero software overhead at inference time. 

# 2:4 sparsity pattern:
# Original weights: [0.3, 0.1, -0.7, 0.2, 0.5, -0.1, 0.4, 0.8]
# After pruning:    [0.3, 0.0, -0.7, 0.0, 0.5,  0.0, 0.4, 0.8]
#                    ^^^       ^^^^        ^^^        ^^^  ^^^
#                    (2 nonzero per group of 4)

# The sparse format stores:
# 1. Compressed values (only non-zeros): [0.3, -0.7, 0.5, 0.4, 0.8]
# 2. A 2-bit index metadata (which 2 of 4 positions are non-zero)

# Tensor Core sparse GEMM:
# - Loads compressed weight matrix (50% size)
# - Hardware decompresses on-the-fly using metadata
# - Compute at 2× the dense FLOPS rate

# Accuracy: typically <1% degradation after fine-tuning
# The pruning decision (which 2 to keep) is made by magnitude
# Requires a brief fine-tuning phase after pruning to recover accuracy
Connection: This is model compression you're familiar with from VitisAI/FPGA work — but with hardware-native support. No custom kernels needed; the Tensor Cores handle decompression. Combinable with quantization: FP8 sparse = 4× effective compression vs FP16 dense.

11. FlashAttention and Kernel-Level Optimizations

FlashAttention (Dao et al., 2022) is the most impactful single kernel optimization for transformers. You should understand it at the systems level: 

# Standard attention (naive):
# 1. S = Q @ K^T         → materialized: (seq × seq) matrix in HBM
# 2. P = softmax(S)      → read S from HBM, write P to HBM
# 3. O = P @ V           → read P from HBM

# Memory: O(seq²) for the attention matrix
# Bandwidth: 3 HBM round-trips for the (seq × seq) matrix

# FlashAttention:
# Never materializes the full (seq × seq) matrix
# Processes attention in tiles that fit in SRAM (shared memory)
# Fuses Q@K^T, softmax, and @V into a single kernel
# Uses online softmax (numerically stable running computation)

# Memory: O(seq) — only stores output and running softmax stats
# Bandwidth: 1 HBM pass (reads Q, K, V once, writes O once)
# Speedup: 2-4× for long sequences, enables 128k+ context

# TensorRT-LLM uses FlashAttention-2/3 variants:
# - FlashAttention-3 (Hopper): exploits async copy (TMA), FP8 attention
# - Paged FlashAttention: combines paged KV-cache with flash kernel

Why FlashAttention Matters for the Job

FlashAttention is a perfect example of what the JR1980206 team does: taking a mathematically equivalent computation and rewriting it as a custom kernel that exploits hardware memory hierarchy (SRAM vs HBM). Your CUDA kernel experience (tiled inference, shared memory usage) gives you the foundation to understand — and potentially contribute to — these optimizations.

13. What's New in 2025–2026 (What Habert Will Likely Cover)

Beyond the fundamentals above, here are the frontier topics she may touch:

  • FP4 on Blackwell: Native 4-bit floating point on B100/B200. 2× throughput vs FP8. Early results show minimal accuracy loss for inference when combined with fine-grained scaling. Still research-stage for activations; weights-only FP4 is production-ready.
  • Disaggregated serving: Separate prefill and decode onto different GPU pools. Prefill GPUs are compute-optimized (high batch, high FLOPS). Decode GPUs are bandwidth-optimized (high HBM bandwidth, lower compute). Reduces cost by right-sizing hardware per phase.
  • Multi-token prediction: Models trained to predict multiple future tokens simultaneously (Meta's approach in Llama-3). Enables ~2× decode speedup without a separate draft model.
  • KV-cache compression beyond quantization: Evicting old tokens (attention sinks), merging similar KV entries, learned compression. Active research for million-token context.
  • Mixture-of-Experts (MoE) inference: Only 2 of 8 experts activated per token, but all expert weights must reside in memory. Expert offloading, expert caching, and expert parallelism are hot topics.
