BF16/FP32 reductions, FSDP2 MixedPrecisionPolicy, and bandwidth/memory accounting

Skill: Given model size Ψ, world size N and a MixedPrecisionPolicy: name the dtype of every tensor in one FSDP2 step, estimate per-rank communication and memory, and justify reduce_dtype.

1. Collectives refresher (ring algorithm)

S = full tensor size in bytes. The table shows per-rank traffic, where sent ≈ received.

The ZeRO-3/FSDP full-shard step does all-gather (forward) + all-gather (backward) + reduce-scatter. That is 3·(N−1)/N·S, compared with DDP's 2·(N−1)/N·S, so 1.5× DDP volume at equal dtype. FSDP2 shrinks this by all-gathering in param_dtype.

2. Where precision is lost in a reduction

  • Rounding per hop. A ring reduce-scatter adds each chunk over N−1 hops. With a BF16 accumulator, every hop rounds (unit roundoff u = 2−8).
    • The worst-case relative error grows ≈ (N−1)·u.
    • A typical random-walk error is ≈ √(N−1)·u.
    • Tree reductions have only log2N levels.
    • NCCL picks the algorithm by size and topology, so by default it is not under your control.
  • Overflow (FP16). Summing N gradients can exceed 65504 even when each one is small. The fix is to pre-divide. FSDP1 had gradient_predivide_factor; FSDP2 exposes a divide factor on the module (check your version). BF16 rarely overflows.
  • Divide timing. mean = Σ/N.
    • Dividing before the reduction risks underflow in FP16.
    • Dividing after risks overflow.
    • Splitting the factor (√N before, √N after) is the classic compromise.
  • Local precision is not restored. reduce_dtype=float32 protects only the cross-rank sum. Each rank's backward has already produced BF16 gradients.

3. FSDP2 MixedPrecisionPolicy

Verify: the search summary lists param_dtype_override_fn (selective overrides) in the main docs only. I could not verify it, and it is not in the stable docs. Check help(MixedPrecisionPolicy) in your installed version before you mention it in an interview.

Dtype flow in one step (param_dtype=BF16, reduce_dtype=FP32)

sharded FP32 params (DTensor; optimizer state lives here = master weights)
   │  cast to param_dtype, all-gather       (2 B/param on the wire)
   ▼
unsharded BF16 params ──► forward
   │  root inputs cast to BF16 if cast_forward_inputs=True
   │  outputs cast to output_dtype at module boundary (if set)
   │  reshard after forward (default) → all-gather again in backward
   ▼
unsharded BF16 grads
   │  cast to reduce_dtype (FP32), reduce-scatter   (4 B/param on the wire)
   ▼
sharded FP32 grads ──► optimizer.step() on FP32 shards

Key facts

  1. Master weights for free. The sharded parameters keep their original dtype (FP32). Only the all-gathered copies are BF16, so there is no separate master copy (compare the L1 nuance on PyTorch AMP).
  2. reduce_dtype=None falls back to param_dtype. So MixedPrecisionPolicy(param_dtype=torch.bfloat16) reduces in BF16.
  3. Module-level, not op-level. Every parameter in a fully_shard group gets param_dtype, including norm weights.
    • Activations are saved for backward in low precision.
    • To keep a module in FP32 (for example a router or final norm), shard it in its own fully_shard call with its own policy.
  4. output_dtype is per call. Set float32 on the root (or LM-head group) policy to get FP32 logits for softmax/CE (L3).
  5. Order of operations. Apply bottom-up (blocks first, then root). Build the optimizer after fully_shard, from the DTensor parameters.
  6. autocast on top is possible but adds op-level casts. Decide deliberately, and avoid redundant casts.

4. Worked example: 7B model, N = 8, BF16 params, FP32 reduce

Ψ = 7·109, (N−1)/N = 0.875, reshard_after_forward=True.

An FP32 reduce costs 49 / 36.75 ≈ 1.33× the traffic of a BF16 reduce. At an assumed ~400 GB/s effective per-rank bandwidth, that is ≈ 0.12 s vs 0.09 s per step, mostly overlappable with compute. This figure is illustrative only; measure on your hardware.

Persistent memory per rank (Adam, FP32 shards): (4 param + 4 grad + 4 m + 4 v)·Ψ/N = 112 GB / 8 = 14 GB. On top of that come the transient unsharded BF16 params and grads of the current and prefetched groups, plus activations.

6. DDP, FSDP1, FSDP2

  • DDP: comm hooks fp16_compress_hook / bf16_compress_hook (in torch.distributed.algorithms.ddp_comm_hooks.default_hooks). They compress gradients for the all-reduce and decompress afterwards.
  • FSDP1: MixedPrecision(param_dtype, reduce_dtype, buffer_dtype) on a FlatParameter. FP16 training used ShardedGradScaler.
  • FSDP2: per-parameter DTensor sharding and MixedPrecisionPolicy, with no buffer_dtype field. For FP16, check which grad scaler your version supports.

7. Interview answer (30 s)

"FSDP2 keeps sharded params in FP32, so the optimizer steps on master weights. It all-gathers in param_dtype, usually BF16, which halves gather bandwidth. Gradients come out of backward in BF16 and are cast to reduce_dtype before the reduce-scatter. I use FP32 there at large world sizes because ring reductions round at every hop, so the error grows with N. That costs about a third more traffic than a BF16 reduce when params are gathered in BF16. Mixed precision is module-level, so I give sensitive modules their own policy and set output_dtype=float32 at the root for the loss. With FP16 I'd also pre-divide gradients to avoid overflow in the sum."

8. Lab (~30 min)

Part A (CPU): reduction error vs N. The inputs are BF16-rounded, so only the communication error is measured.

import torch
torch.manual_seed(0)

def ring_sum(gs, dt):
    acc = gs[0].to(dt)
    for g in gs[1:]:
        acc = acc + g.to(dt)          # rounds to dt at every hop
    return acc.double()

def tree_sum(gs, dt):
    xs = [g.to(dt) for g in gs]
    while len(xs) > 1:
        nxt = [xs[i] + xs[i + 1] for i in range(0, len(xs) - 1, 2)]
        if len(xs) % 2:
            nxt.append(xs[-1])
        xs = nxt
    return xs[0].double()

for N in [2, 8, 64, 512]:
    gs = [torch.randn(20_000).bfloat16().float() for _ in range(N)]
    ref = torch.stack([g.double() for g in gs]).sum(0)
    for name, f, dt in [("ring bf16", ring_sum, torch.bfloat16),
                        ("tree bf16", tree_sum, torch.bfloat16),
                        ("ring fp32", ring_sum, torch.float32)]:
        err = ((f(gs, dt) - ref).norm() / ref.norm()).item()
        print(f"N={N:4d} {name:9s} rel_err={err:.2e}")

Predict first: how does the ring BF16 error scale from N=8 to N=512? Linearly or as √N? Is the tree better?

Part B (CPU): FP16 overflow and pre-division.

import torch
g = torch.full((64,), 2000.0, dtype=torch.float16)

acc = torch.tensor(0.0, dtype=torch.float16)
for x in g:
    acc = acc + x
print("sum then divide:", acc.item())          # inf (64*2000 = 128000 > 65504)

acc = torch.tensor(0.0, dtype=torch.float16)
for x in g:
    acc = acc + x / 64
print("pre-divide:", acc.item())               # 2000.0

Part C (optional, ≥ 2 GPUs): inspect FSDP2 dtypes. Run with torchrun --nproc_per_node=2 lab11.py.

import os, torch, torch.distributed as dist
from torch.distributed.device_mesh import init_device_mesh
from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy

dist.init_process_group("nccl")
torch.cuda.set_device(int(os.environ["LOCAL_RANK"]))
rank = dist.get_rank()
mesh = init_device_mesh("cuda", (dist.get_world_size(),))

class Probe(torch.nn.Linear):
    def forward(self, x):
        if rank == 0:
            print(f"[{self.tag}] input={x.dtype} weight={self.weight.dtype}")
        return super().forward(x)

model = torch.nn.Sequential(Probe(1024, 1024), torch.nn.GELU(), Probe(1024, 1024)).cuda()
model[0].tag, model[2].tag = "lin0", "lin2"

block_mp = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32)
root_mp  = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32,
                                output_dtype=torch.float32)   # FP32 output for the loss
for m in (model[0], model[2]):
    fully_shard(m, mesh=mesh, mp_policy=block_mp)
fully_shard(model, mesh=mesh, mp_policy=root_mp)
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)          # after fully_shard

x = torch.randn(8, 1024, device="cuda")                       # FP32 input
out = model(x)
out.float().pow(2).mean().backward()
if rank == 0:
    p = model[0].weight
    print("output:", out.dtype)
    print("sharded param:", type(p).__name__, p.dtype, "local shape", p.to_local().shape)
    print("sharded grad:", p.grad.dtype)
opt.step()
dist.destroy_process_group()

Expected:

  • Inputs and weights inside the layers are BF16.
  • The output is FP32, because of the root policy.
  • The sharded params and grads are FP32 DTensors with half the rows per rank.
