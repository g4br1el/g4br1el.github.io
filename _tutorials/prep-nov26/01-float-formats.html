Lesson 1 · Float Bit Layouts & Why FP16 Training Needs Master Weights and Loss Scaling

Week 1 · ~45 min reading + ~30 min lab + quiz · Target: Research / Senior DL Engineering interviews

0. Interview skill

Given exponent bits E and mantissa bits M, derive every key number of a float format on a whiteboard in under 5 minutes. Then explain each part of the Micikevicius mixed-precision recipe from those numbers.

1. One formula set for all formats

Bias b = 2E−1 − 1. The exponent field with all ones is reserved for Inf/NaN (IEEE-style), so the largest usable exponent is 2E − 2 − b.

Normal value(−1)s · 2e−b · (1 + f/2M)
Max finite(2 − 2−M) · 22E − 2 − b
Min normal21−b
Min subnormal21−b−M
Machine epsilon (ulp at 1.0)2−M
Unit roundoff2−(M+1)
Decimal digits≈ (M+1) · log102

3. Whiteboard drills

Try each drill yourself before you expand the solution.

Drill 1: Decode FP16 0x7BFF

0 11110 1111111111 → 230−15 · (1 + 1023/1024) = 215 · (2 − 2−10) = 65504.

Drill 2: Convert FP32 1.0 to BF16

Keep the top 16 bits (in hardware, with round-to-nearest-even): 0x3F800000 → 0x3F80. The conversion is cheap and keeps FP32's full range.

Drill 3: "Is BF16 more precise than FP16?"

No. FP16 has 3 more mantissa bits, so its resolution is finer. It has 3 fewer exponent bits, so its normal range is only about 2−14 to 216. BF16 has FP32's range but is 8× coarser near 1.0.

Drill 4: Derive E5M2 max finite with the IEEE formula

b = 15, top usable exponent = 25 − 2 − 15 = 15, mantissa factor = 2 − 2−2 = 1.75 → 1.75 · 215 = 57344.

4. From bit layout to failure modes

The three techniques in Micikevicius et al. each fix one failure mode.

Failure modeCauseFix
Lost updatesIf |Δw| < ½ ulp(w), then w + Δw rounds back to w. Near w ≈ 1, ulp = 2−10, so updates more than about 211 times smaller than the weight disappear.FP32 master weights. The optimizer step runs in FP32, then the result is cast to FP16.
Gradient underflowMany activation gradients fall below 2−24 and become 0. For example, 1e−8 flushes to zero.Loss scaling. L′ = S·L, so all gradients are multiplied by S. Unscale before the optimizer step.
Accumulation swampingLong FP16 sums stall. For example, 2048 + 1 = 2048 (ulp = 2, and the tie rounds to even).FP32 accumulation in dot products and reductions. Softmax and norms also stay in FP32.

The paper used fixed scale factors. The dynamic procedure from NVIDIA's guide works like this:

  1. Check the gradients for Inf/NaN.
  2. If found, skip the step and halve S.
  3. After N clean steps, double S.

5. Two nuances that set strong candidates apart

5.1 PyTorch native AMP has no separate FP16 weight copy

  • Parameters stay FP32, and autocast casts them per operation.
  • So the "master weights" are simply the parameters themselves.
  • The FP16-model-plus-FP32-master design is the Apex O2 / paper style.

5.2 Mixed precision does not save optimizer memory

SetupBytes per parameter
Classic MP + Adam2 (FP16 w) + 2 (FP16 g) + 4 (master) + 4 (m) + 4 (v) = 16
Pure FP32 + Adam4 + 4 + 4 + 4 = 16

The real savings are activation memory, memory bandwidth and Tensor Core throughput. This 16-byte accounting is also where ZeRO starts (verify the reference).

6. Interview answer (aim for 30 seconds)

"FP16 has a 5-bit exponent, so the smallest subnormal is 2−24. Many activation gradients are smaller and flush to zero, which is why we scale the loss and unscale before the step. Dynamic scaling backs off and skips the step on Inf/NaN. Separately, with 10 mantissa bits an update more than about 211 times smaller than the weight is rounded away. So the optimizer works on FP32 master weights, and reductions accumulate in FP32. BF16 removes the range problem but is 8× coarser, so accumulation and master weights still matter."

Practice: say it out loud with a timer, then write the FP16 row of the table from memory.

7. Lab (~30 min)

Before running each part, write down what you expect it to print.

import torch

# 1) Verify the format table
for dt in [torch.float32, torch.float16, torch.bfloat16,
           torch.float8_e4m3fn, torch.float8_e5m2]:
    fi = torch.finfo(dt)
    print(f"{str(dt):22s} max={fi.max:.4g} tiny={fi.tiny:.4g} eps={fi.eps:.4g}")

# 2) Lost update: FP16 vs FP32
w16, w32 = torch.tensor(1.0, dtype=torch.float16), torch.tensor(1.0)
print("fp16:", (w16 + 1e-4).item(), "fp32:", (w32 + 1e-4).item())

# 3) Underflow and loss scaling
g = torch.tensor(1e-8)
print("unscaled ->", g.half().item())                                # 0.0
print("scaled S=1024 ->", (g * 1024).half().float().item() / 1024)   # ~1e-8

# 4) Accumulation swamping
acc16 = torch.tensor(0.0, dtype=torch.float16)
for _ in range(4096):
    acc16 += 1
print("fp16 running sum of 4096 ones:", acc16.item())                 # 2048.0
Stretch: repeat part 4 with torch.bfloat16. Predict the stall value first.

BF16 has M = 7, so the ulp becomes 2 at 28 = 256. Then 256 + 1 is a tie that rounds to even, so the sum stalls at 256. This is why BF16 still needs FP32 accumulation.
