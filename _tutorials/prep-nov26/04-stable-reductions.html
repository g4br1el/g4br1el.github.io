2. Summation error

2.1 Bounds (first order, u = unit roundoff)

MethodWorst-case |error|Typical (random rounding)Cost
Recursive (naive loop, cumsum)≈ (n−1)·u·Σ|xi|~ √n·u·Σ|xi|n adds, sequential
Pairwise / tree (GPU reductions, NumPy sum)≈ ⌈log2n⌉·u·Σ|xi|~ √(log n)·u·Σ|xi|n adds, parallel
Kahan (compensated)≈ 2u·Σ|xi| + O(n·u²)~ independent of n4 flops per element, plus a compensation variable
Wider accumulator (FP32 for BF16 inputs)Bound uses u of the accumulatorFree in registers; costs memory if stored

The relative error is the bound divided by |Σxi|, so it scales with the condition number κ = Σ|xi| / |Σxi|. Kahan fixes accumulated rounding error, but not cancellation in ill-conditioned sums.

2.2 Stagnation

Adding a to a running sum S does nothing once a < ulp(S)/2. At exactly half an ulp, the tie rounds to even. Summing 1.0 repeatedly therefore stops at 2p, where p is the number of significand bits:

FormatpΣ 1.0 stops at
BF168256
FP16112048
FP322416,777,216

Before it stops completely, the error is often biased, not random. Inside one binade, every addition of 0.1 rounds in the same direction. Lab part 1 shows a 1% systematic drift.

2.3 Kahan summation

s = 0; c = 0              # c holds the low-order bits lost so far
for x in xs:
    y = x - c             # corrected addend
    t = s + y             # big + small: low bits of y are lost
    c = (t - s) - y       # (what was actually added) - (what we wanted) = -lost bits
    s = t
Compilers with fast-math, or torch.compile algebraic rewrites, can simplify (t − s) − y to 0. Check the generated code if you rely on it.

3. Log-sum-exp and stable losses

LSE(x) = m + log Σ exp(x_i − m), m = max_i x_i log_softmax(x)_i = x_i − LSE(x) CE(x, y) = LSE(x) − x_y ∂CE/∂x = softmax(x) − onehot(y)
  • With m subtracted, every exponent is ≤ 0, so nothing overflows. The largest term is exp(0) = 1, so the sum is ≥ 1 and log never sees 0.
  • Overflow thresholds for exp(x): FP16 x > ≈11.09, FP32/BF16 x > ≈88.72, FP64 x > ≈709.8.
  • Never write log(softmax(x)). A softmax output that underflows to 0 gives −Inf.
BCE-with-logits(z, y) = max(z, 0) − z·y + log1p(exp(−|z|))

Use binary_cross_entropy_with_logits, log1p, expm1, softplus and xlogy for the same reason: they avoid forming a value that rounds to 0 or 1 before you take its log.

4. Online softmax and FlashAttention

4.1 Online normalizer (Milakov & Gimelshein, 2018)

The state is (m, d), where m is the running max and d = Σ exp(xi − m).

update with block b: m' = max(m, max(b)); d' = d·exp(m − m') + Σ exp(b_i − m') merge (m1,d1),(m2,d2): m = max(m1, m2); d = d1·exp(m1 − m) + d2·exp(m2 − m)

The merge is associative and commutative up to rounding. That allows a single pass, tiling and parallel splits such as split-KV / Flash-Decoding. The initial state is (−Inf, 0). Watch out: if a block is entirely −Inf, then m − m' = −Inf − (−Inf) = NaN, the same trap as Lesson 3. Real kernels guard against this.

4.2 FlashAttention forward (one query block)

m = -inf; l = 0; O = 0                       # all FP32, kept on-chip
for each key/value block j:
    S = (Q_i @ K_j^T) * scale                # FP32 accumulate
    m_new = max(m, rowmax(S))
    P = exp(S - m_new)
    alpha = exp(m - m_new)                   # rescale old contributions
    l = alpha * l + rowsum(P)
    O = alpha * O + P @ V_j                  # P cast to fp16/bf16 for the Tensor Core GEMM (verify per version)
    m = m_new
O = O / l;  LSE = m + log(l)                 # store LSE (one float per row) for backward
PropertyWhy
Exact, not an approximationThe rescaling identity is algebraically exact. Differences from a naive softmax come only from rounding order.
Numerically safeMax-subtraction in every block; FP32 m, l and O accumulators; scores never round-trip through HBM in FP16.
Memory O(N) instead of O(N²)The N×N score/probability matrix is never materialized. Backward recomputes S and P from Q, K and the saved LSE: P = exp(S − LSE).
Where precision is lostInput rounding of Q, K and V; P rounded to BF16/FP16 before P·V; FP8 variants (FA3) add more (verify).
FA2 refinementKeeps O unnormalized and divides by l once at the end, which saves non-matmul FLOPs.

Interactive: online-softmax stepper (float64)

A naive exp(x)/Σexp(x) overflows in float64 above ≈709.8, which gives Inf/Inf = NaN.

5. Variance: Welford and Chan

E[x²] − E[x]² subtracts two numbers of size ≈ mean². In FP32 with mean ≈ 10⁴, both terms are ≈ 10⁸, where the ulp is 8. The result is a multiple of 8, so the true variance of 1 is lost.

Welford (streaming): n += 1; δ = x − mean; mean += δ/n; M2 += δ·(x − mean); var = M2/n Chan merge (parallel): δ = mean_b − mean_a; n = n_a + n_b mean = mean_a + δ·n_b/n; M2 = M2_a + M2_b + δ²·n_a·n_b/n

The Chan merge is what makes block-parallel LayerNorm/BatchNorm kernels and cross-GPU SyncBatchNorm stable. A cheap alternative is to shift by any sample (x − x0) before using the naive formula.

6. Reproducibility: reduction order is part of the result

  • Floating-point addition is not associative. A different reduction tree gives different low-order bits.
  • The tree changes with: the number of GPUs or the all-reduce algorithm; the kernel chosen for a shape (split-K, tile sizes); atomics, e.g. FlashAttention's backward dQ and some index_add/scatter_add; batch size and padding.
  • Batch invariance: row 0 of A·B may differ bitwise depending on how many other rows are in the batch, because a different kernel runs. This matters for LLM inference reproducibility (Thinking Machines, "Defeating Nondeterminism in LLM Inference", 2025, verify).
  • PyTorch: torch.use_deterministic_algorithms(True) plus CUBLAS_WORKSPACE_CONFIG=:4096:8 gives run-to-run determinism on the same setup. It doesn't give invariance across GPU counts or batch sizes. Expect a slowdown, and errors for ops without deterministic implementations.
  • Rule of thumb: differences in the last digits (about 1e−6 relative in FP32, 1e−2 to 1e−3 in BF16) that stay bounded are normal. Differences that grow over steps mean either chaotic training dynamics (normal for long runs) or a bug. Compare loss curves statistically, not bitwise.

7. Interview answers (30 s each, say them out loud)

"Why is FlashAttention numerically safe, and is it approximate?"
"It's exact. It uses the online-softmax identity: keep a running max m and normalizer l per query row, and when a new key block raises the max, rescale the old l and the output accumulator by exp(m_old − m_new). All of that stays in FP32 on-chip, and every exponent is ≤ 0. It never materializes the N×N matrix, so memory is O(N). For backward it stores one LSE per row and recomputes P. Precision is lost only from input rounding and from casting P to BF16 for the PV GEMM."
"Same seed, 8 vs. 16 GPUs, the loss differs in the 6th digit. Bug?"
"Probably not. FP addition isn't associative, and changing the world size changes the all-reduce tree and the per-rank batch shapes, which changes kernel choices. I'd check that the difference starts at the rounding level and that the curves agree statistically. Deterministic mode gives me run-to-run reproducibility on a fixed setup, but not invariance across GPU counts. One thing I'd verify is that the loss is normalized by the global token count, because that's a real bug that looks similar."
"Can we drop the FP32 master weights?"
"Only if we handle swamping. A BF16 update smaller than half an ulp is lost: at w = 1, that's anything below about 0.004. The options are a BF16 Kahan compensation buffer, which brings us to 4 instead of 6 bytes per param and recovers the lost bits, or stochastic rounding, which is unbiased in expectation. I'd validate it against an FP32-master baseline on the loss curve, especially late in training when updates are smallest."

Part 1: Naive vs. pairwise vs. Kahan (CPU, NumPy)

import math, time, numpy as np
n = 10**6
x = np.full(n, 0.1, dtype=np.float32)
exact = math.fsum(x.astype(np.float64))         # exact sum of the float32 values

def kahan(v):
    s = np.float32(0); c = np.float32(0)
    for xi in v:                                # xi is np.float32: all math stays in float32
        y = xi - c; t = s + y; c = (t - s) - y; s = t
    return s

t0 = time.time(); k = kahan(x); dt = time.time() - t0
results = [("naive (cumsum)", np.cumsum(x)[-1]),    # sequential float32 accumulator
           ("pairwise (sum)", x.sum()),             # NumPy uses pairwise summation
           ("kahan", k),
           ("float64 acc", x.sum(dtype=np.float64))]
print(f"exact          {exact:.4f}")
for name, val in results:
    print(f"{name:14} {float(val):.4f}  rel err {abs(float(val) - exact) / exact:.1e}")
print(f"kahan python loop took {dt:.1f}s")
Expected and why
  • exact = 100000.0015, because float32(0.1) is slightly more than 0.1.
  • naive ≈ 1.01e5, about 1% high. The drift is systematic. In [65536, 131072) the ulp is 2−7, and 0.1 = 12.8 ulps rounds up to 13 ulps every time.
  • pairwise has a relative error of about 1e−7 or smaller. kahan gives 100000.0, the nearest float32 (rel ≈ 1.5e−8). float64 accumulation is essentially exact.
  • Kahan in a Python loop takes seconds. In a kernel it is almost free, because summation is memory-bound.

Part 3: Online softmax and a mini FlashAttention (CPU, torch)

import torch, math
torch.manual_seed(0)

def online_stats(x, block):
    m, d = torch.tensor(float("-inf")), torch.tensor(0.0)
    for i in range(0, x.numel(), block):
        b = x[i:i + block]
        m_new = torch.maximum(m, b.max())
        d = d * torch.exp(m - m_new) + torch.exp(b - m_new).sum()
        m = m_new
    return m, d

x = torch.randn(10_000) * 30
m, d = online_stats(x, 128)
print("max |online - softmax|:", (torch.exp(x - m) / d - torch.softmax(x, 0)).abs().max().item())
print("LSE:", (m + d.log()).item(), "vs", torch.logsumexp(x, 0).item())

def flash_attn(q, k, v, Br=64, Bc=64, p_dtype=torch.float32):
    N, D = q.shape; scale = 1 / math.sqrt(D)
    O, L = torch.zeros(N, D), torch.empty(N)
    for i in range(0, N, Br):
        qi = q[i:i + Br].float() * scale
        m = torch.full((qi.shape[0],), float("-inf")); l = torch.zeros(qi.shape[0]); acc = torch.zeros(qi.shape[0], D)
        for j in range(0, N, Bc):
            s = qi @ k[j:j + Bc].float().T
            m_new = torch.maximum(m, s.max(-1).values)
            p = torch.exp(s - m_new[:, None])
            alpha = torch.exp(m - m_new)
            l = alpha * l + p.sum(-1)
            acc = alpha[:, None] * acc + (p.to(p_dtype) @ v[j:j + Bc].to(p_dtype)).float()
            m = m_new
        O[i:i + Br] = acc / l[:, None]; L[i:i + Br] = m + l.log()
    return O, L

N, D = 512, 64
q, k, v = (torch.randn(N, D) for _ in range(3))
ref = torch.softmax(q.double() @ k.double().T / math.sqrt(D), -1) @ v.double()
for p_dtype in (torch.float32, torch.bfloat16):
    O, L = flash_attn(q, k, v, p_dtype=p_dtype)
    print(f"P in {str(p_dtype):15} max |O - ref64| = {(O.double() - ref).abs().max().item():.1e}")
lse_ref = torch.logsumexp(q.double() @ k.double().T / math.sqrt(D), -1)
print("LSE max diff:", (L.double() - lse_ref).abs().max().item())
Expected

Online vs. softmax: about 1e−8 or smaller, and the LSEs agree to FP32 precision. Flash with FP32 P: about 1e−6, because it is exact up to rounding. With BF16 P (and V): about 1e−3, which is the cost of the Tensor Core cast. Change Bc: the results move only in the last bits.

Part 4: Order, cancellation, batch invariance

import torch
torch.manual_seed(0)
x = torch.randn(1_000_000)
a, b = x.sum(), x[torch.randperm(x.numel())].sum()
print(f"sum {a.item():.6f} | permuted {b.item():.6f} | bitwise equal: {torch.equal(a, b)} | fp64 {x.double().sum().item():.6f}")
print(f"8 chunks ('8 GPUs'): {sum(c.sum() for c in x.chunk(8)).item():.6f}")

y = 10_000 + torch.randn(1_000_000)
naive = (y * y).mean() - y.mean() ** 2
y0 = y - y[0]
print("naive var:", naive.item(), "| torch.var:", y.var(correction=0).item(),
      "| shifted:", ((y0 * y0).mean() - y0.mean() ** 2).item())

if torch.cuda.is_available():                     # 4c: batch invariance (optional)
    torch.backends.cuda.matmul.fp32_precision = "ieee"
    A = torch.randn(2048, 4096, device="cuda"); B = torch.randn(4096, 4096, device="cuda")
    full, single = (A @ B)[:1], A[:1] @ B
    print("row 0 bitwise equal:", torch.equal(full, single), "| max diff:", (full - single).abs().max().item())
Expected
  • The three sums usually differ in the last digits, so bitwise equal is usually False, and all of them are close to the FP64 value. That is non-associativity.
  • naive var is a multiple of 8 (0, 8, −8, 16, …) because both terms are ≈ 1e8, where the FP32 ulp is 8. torch.var and the shifted version give ≈ 1.0.
  • 4c: often False with a difference around 1e−5. M = 1 and M = 2048 select different kernels and reduction orders. This depends on hardware and library version.
