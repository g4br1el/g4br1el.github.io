The bridge between your physical GPU topology and FSDP2's logical sharding strategy.

Why DeviceMesh Matters

DeviceMesh is not just a convenience wrapper around process groups — it's the single source of truth for how your GPUs relate to each other. Get it wrong, and FSDP2 will:

  • Route all-gathers over InfiniBand instead of NVLink (2–10× slower)
  • Create process groups that span physical boundaries inefficiently
  • Miss HSDP opportunities entirely (sharding across slow links when it should replicate)

On your V100 cluster (4 GPUs/node, NVLink intra-node, InfiniBand inter-node), the mesh construction directly determines whether FSDP2 exploits the bandwidth hierarchy.

1-D Mesh: The Simple Case

from torch.distributed.device_mesh import init_device_mesh

# All GPUs in one flat shard group — the simplest topology
# Appropriate when: single node, or you want maximum sharding regardless of link speed
mesh_1d = init_device_mesh("cuda", (world_size,))

# What this creates internally:
# - One ProcessGroup containing ALL ranks
# - DTensors with Shard(0) will shard across ALL GPUs in this group
# - All collectives (all-gather, reduce-scatter) use this single group

On one node with 4× V100 NVLink: this is optimal. All communication is intra-node over NVLink (~300 GB/s bidirectional). No reason to complicate things.

On 2+ nodes: this is suboptimal. All-gathers and reduce-scatters now span InfiniBand (~12.5 GB/s per link), mixed with NVLink. The collective treats all ranks equally even though some pairs are 24× faster to communicate with.

2-D Mesh: Exploiting the Bandwidth Hierarchy

A 2-D mesh encodes two levels of the topology. For your cluster:

# 2-node × 4-GPU configuration
# Mesh shape: (num_replicas, shard_group_size)
# Convention: mesh dimensions are ordered outer → inner
#   dim 0 (outer): slow link — inter-node InfiniBand — REPLICATE here
#   dim 1 (inner): fast link — intra-node NVLink — SHARD here

mesh_2d = init_device_mesh(
    "cuda",
    (2, 4),  # 2 replica groups, 4 GPUs per shard group
    mesh_dim_names=("replicate", "shard"),
)

How Ranks Map to Mesh Coordinates

Physical Cluster: ┌─── Node 0 (NVLink) ───┐ ┌─── Node 1 (NVLink) ───┐ │ GPU0 GPU1 GPU2 GPU3 │ │ GPU4 GPU5 GPU6 GPU7 │ └────────────────────────┘ └────────────────────────┘ ◀──── InfiniBand ────▶ DeviceMesh("cuda", (2, 4), mesh_dim_names=("replicate", "shard")): Mesh coordinates [replica_idx, shard_idx]: [0,0]=GPU0 [0,1]=GPU1 [0,2]=GPU2 [0,3]=GPU3 ← Replica group 0 (Node 0) [1,0]=GPU4 [1,1]=GPU5 [1,2]=GPU6 [1,3]=GPU7 ← Replica group 1 (Node 1) ↕ ↕ ↕ ↕ replicate replicate replicate replicate ← Communication across dim 0 (IB) (IB) (IB) (IB) uses InfiniBand ◀──── shard (NVLink within each row) ────▶ ← Communication across dim 1 uses NVLink
Critical insight: init_device_mesh assigns ranks to mesh coordinates in row-major (C) order. Rank 0,1,2,3 fill the first row; rank 4,5,6,7 fill the second row. Since your nodes assign local_rank 0–3 to the 4 GPUs within a node, this naturally maps rows to nodes. If your cluster used a different rank assignment scheme, you'd need to verify this mapping.

How FSDP2 Uses the 2-D Mesh (HSDP)

When you pass a 2-D mesh to fully_shard(), FSDP2 automatically implements HSDP:

# HSDP setup:
mesh_2d = init_device_mesh("cuda", (2, 4), mesh_dim_names=("replicate", "shard"))

for block in model.blocks:
    fully_shard(block, mesh=mesh_2d, mp_policy=mp_policy)
fully_shard(model, mesh=mesh_2d, mp_policy=mp_policy)

# Result:
# - Parameters at rest: placements = (Replicate(), Shard(0))
#     Replicate on dim 0 → same shards on both nodes
#     Shard(0) on dim 1 → partitioned across 4 GPUs within each node
#
# - Forward all-gather: operates on dim 1 ("shard") only → NVLink!
#     Within each node: all-gather across 4 GPUs via NVLink
#     No inter-node communication for all-gather
#
# - Backward reduce-scatter: operates on dim 1 ("shard") only → NVLink!
#     Within each node: reduce-scatter across 4 GPUs via NVLink
#
# - Gradient sync across replicas: operates on dim 0 ("replicate") → InfiniBand
#     all-reduce of sharded gradients across the 2 nodes
#     Each rank only all-reduces its OWN shard (P/4 data, not full P)
HSDP's bandwidth advantage: The expensive per-layer collectives (all-gather, reduce-scatter) run exclusively over NVLink. Only the gradient sync (one all-reduce per step) crosses InfiniBand — and it moves only P/4 data (each rank's shard), not the full model. Compare to 1-D mesh where ALL collectives cross InfiniBand for half the ranks.

Communication Volume Analysis: 1-D vs 2-D

Let's quantify for ViT-Huge (632M params, fp16 = 1.2 GB) on 8 GPUs across 2 nodes:

StrategyAll-gather (per step)Reduce-scatter (per step)Replica syncInfiniBand traffic
1-D Mesh (8 GPUs flat) 2 × P × 7/8 = 2.1 GB
(fwd + bwd, mixed NVLink/IB)		 P × 7/8 = 1.05 GB
(mixed NVLink/IB)		 None ~1.6 GB (half of all traffic crosses nodes)
2-D HSDP (2×4) 2 × P × 3/4 = 1.8 GB
(NVLink only!)		 P × 3/4 = 0.9 GB
(NVLink only!)		 P/4 × 2 = 0.6 GB
(all-reduce, IB)		 0.6 GB (only replica sync)
Result: HSDP reduces InfiniBand traffic from ~1.6 GB to ~0.6 GB per step — a 2.7× reduction in cross-node communication. On your InfiniBand-limited cluster, this directly translates to higher throughput when scaling beyond one node. The trade-off: each node must fit the model sharded across only 4 GPUs (P/4 per GPU) instead of 8 (P/8 per GPU). For ViT-Huge, P/4 = ~300 MB model-proportional memory — trivially fits on V100-32GB.

When to Use 1-D vs 2-D Mesh

Use caseRecommendationRationale
Single node (4 GPUs) 1-D mesh, size 4 Only NVLink available. No hierarchy to exploit.
2 nodes, model fits in 1/4 per GPU 2-D HSDP (2, 4) Minimize InfiniBand traffic. Model-proportional mem (P/4) easily fits.
2 nodes, model ONLY fits in 1/8 per GPU 1-D mesh, size 8 Must shard across all 8 GPUs. Cannot afford to only shard within-node.
8 nodes (32 GPUs), model fits in 1/4 per GPU 2-D HSDP (8, 4) 8 replicas, 4-way shard. Replica sync moves only P/4 over IB.
8 nodes, model needs 1/32 per GPU 1-D mesh, size 32 Forced full sharding. Or consider 2-D (4, 8) to shard across 2 nodes via IB but limit IB traffic.
8 nodes, model fits in 1/4 per GPU, very large batch 2-D HSDP (8, 4) Effective batch = per_gpu_batch × 4 × 8. HSDP gives DDP-like scaling with FSDP memory savings.
The decision criterion is simple: Can you fit P × 16 / shard_group_size per GPU (for model-proportional memory)? If yes with shard_group_size = GPUs_per_node → use HSDP. If not → must shard across nodes (larger shard group or full 1-D mesh). For ViT-Huge (9.6 GB total model-prop), shard_group=4 → 2.4 GB per GPU. Easily fits on V100-32GB.

Constructing the Mesh in Multi-Node Slurm

import os
import torch.distributed as dist
from torch.distributed.device_mesh import init_device_mesh


def create_mesh_for_cluster() -> "DeviceMesh":
    """
    Auto-detect topology and create appropriate mesh.

    Assumptions:
    - torchrun sets LOCAL_RANK, RANK, WORLD_SIZE
    - Ranks are assigned contiguously per node (torchrun default)
    - All nodes have the same number of GPUs
    """
    world_size = dist.get_world_size()
    local_world_size = int(os.environ.get("LOCAL_WORLD_SIZE", torch.cuda.device_count()))
    num_nodes = world_size // local_world_size

    if num_nodes == 1:
        # Single node: simple 1-D shard
        mesh = init_device_mesh("cuda", (world_size,))
        if dist.get_rank() == 0:
            print(f"Mesh: 1-D flat shard, {world_size} GPUs")
    else:
        # Multi-node: HSDP with intra-node sharding
        mesh = init_device_mesh(
            "cuda",
            (num_nodes, local_world_size),
            mesh_dim_names=("replicate", "shard"),
        )
        if dist.get_rank() == 0:
            print(f"Mesh: 2-D HSDP, {num_nodes} replicas × "
                  f"{local_world_size} shards/replica")

    return mesh
Rank ordering assumption: init_device_mesh fills the mesh in row-major order from rank 0. torchrun assigns ranks contiguously per node: node 0 gets ranks 0..3, node 1 gets ranks 4..7. This means row 0 of the mesh = node 0, row 1 = node 1 — exactly what we want. If you use a different launcher that doesn't guarantee this ordering, you'd need to pass a custom rank-to-coordinate mapping.

Slurm Multi-Node Launch

#!/bin/bash
#SBATCH --job-name=fsdp2_hsdp
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=1       # One task per node (torchrun spawns processes)
#SBATCH --gpus-per-node=4
#SBATCH --cpus-per-task=32        # 8 CPUs per GPU × 4 GPUs
#SBATCH --mem=128G
#SBATCH --time=02:00:00
#SBATCH --partition=gpu

# Get master address from first node
export MASTER_ADDR=$(scontrol show hostnames $SLURM_JOB_NODELIST | head -n1)
export MASTER_PORT=29500

# torchrun on each node (via srun)
srun torchrun \
    --nnodes=$SLURM_NNODES \
    --nproc_per_node=4 \
    --rdzv_id=$SLURM_JOB_ID \
    --rdzv_backend=c10d \
    --rdzv_endpoint=$MASTER_ADDR:$MASTER_PORT \
    train_fsdp2.py
Common Slurm pitfall: Using --ntasks-per-node=4 + srun python train.py (without torchrun) creates 4 processes per node but doesn't set LOCAL_RANK or LOCAL_WORLD_SIZE correctly for DeviceMesh. Always use --ntasks-per-node=1 with torchrun, which handles the per-node process spawning itself.

DeviceMesh Internals: What Happens Under the Hood

# What init_device_mesh("cuda", (2, 4), mesh_dim_names=("replicate", "shard")) does:

# 1. Creates the mesh tensor:
#    [[0, 1, 2, 3],    ← replica group 0
#     [4, 5, 6, 7]]   ← replica group 1

# 2. For EACH mesh dimension, creates ProcessGroups by slicing along that dim:
#
#    dim 1 ("shard"): slice along rows → groups [0,1,2,3] and [4,5,6,7]
#    dim 0 ("replicate"): slice along columns → groups [0,4], [1,5], [2,6], [3,7]

# 3. Each rank stores references to its own groups:
#    Rank 2: shard_group=[0,1,2,3], replicate_group=[2,6]
#    Rank 5: shard_group=[4,5,6,7], replicate_group=[1,5]

# 4. When FSDP2 calls all-gather for sharded params:
#    It uses the "shard" dimension's ProcessGroup → NVLink within-node group

# 5. When FSDP2 calls all-reduce for gradient sync across replicas:
#    It uses the "replicate" dimension's ProcessGroup → InfiniBand cross-node group

3-D Mesh (Advanced — For Awareness)

If you ever combine FSDP with Tensor Parallelism (TP), you'd use a 3-D mesh:

# 3-D: (data_parallel, shard, tensor_parallel)
# Example: 4 nodes × 4 GPUs, with 2-way TP within each node
mesh_3d = init_device_mesh(
    "cuda",
    (4, 2, 2),  # 4 DP replicas × 2 FSDP shards × 2 TP ranks
    mesh_dim_names=("dp", "fsdp", "tp"),
)
# This is what torchtitan uses for LLaMA-405B scale.
# Out of scope for this course but good to know the extension point.

For your current needs (ViT-Huge, up to 32 GPUs), 1-D or 2-D meshes are sufficient. TP becomes relevant only when a single layer's parameters don't fit on one GPU — not the case for ViT-Huge where the largest layer is ~8M params.

Verifying Your Mesh

def verify_mesh(mesh: "DeviceMesh") -> None:
    """Print mesh info for debugging. Call on all ranks."""
    rank = dist.get_rank()
    local_rank = int(os.environ.get("LOCAL_RANK", 0))

    print(f"[Rank {rank}, Local {local_rank}] Mesh: {mesh}")
    print(f"  ndim: {mesh.ndim}")
    print(f"  shape: {mesh.mesh.shape}")  # The underlying tensor

    if mesh.ndim >= 2:
        # Print which groups this rank belongs to
        for dim_name in mesh.mesh_dim_names:
            sub_mesh = mesh[dim_name]
            # Get the group for this rank along this dimension
            print(f"  dim '{dim_name}': mesh size {mesh.size(mesh.get_dim_by_name(dim_name))}")

    # Verify NVLink grouping: ranks in the same shard group should be on same node
    if mesh.ndim == 2 and "shard" in mesh.mesh_dim_names:
        shard_dim = mesh.get_dim_by_name("shard")
        # Ranks in my shard group:
        my_row = rank // mesh.size(shard_dim)
        shard_ranks = list(range(my_row * mesh.size(shard_dim),
                                  (my_row + 1) * mesh.size(shard_dim)))
        hostname = os.environ.get("HOSTNAME", "unknown")
        print(f"  Shard group ranks: {shard_ranks} (should be same node)")
        print(f"  My hostname: {hostname}")

DeviceMesh and Process Group Lifecycle

Understanding when process groups are created/destroyed helps avoid subtle bugs:

# Process groups are created by init_device_mesh and live until:
# 1. destroy_process_group() is called, OR
# 2. The process exits

# DO NOT call init_device_mesh multiple times with different shapes.
# This creates new ProcessGroups without destroying old ones → resource leak.

# Pattern: create mesh ONCE at startup, pass it everywhere.
mesh = init_device_mesh(...)  # Once
fully_shard(block, mesh=mesh)  # Reuse same mesh
fully_shard(model, mesh=mesh)  # Same mesh

# Anti-pattern:
for block in model.blocks:
    block_mesh = init_device_mesh(...)  # DON'T — creates new PGs each time
    fully_shard(block, mesh=block_mesh)

Check Your Understanding

Q1: On your 2-node, 4-GPU/node cluster with a 2-D HSDP mesh of shape (2,4), how many NCCL process groups are created in total?

Correct. For a mesh of shape (R, S): dim 1 ("shard") creates R groups of size S (one per row = per node). That's 2 groups: [0,1,2,3] and [4,5,6,7]. Dim 0 ("replicate") creates S groups of size R (one per column = per shard position). That's 4 groups: [0,4], [1,5], [2,6], [3,7]. Total: 2 + 4 = 6. (Plus the default world group, but that's not created by DeviceMesh.)

Q2: With 2-D HSDP, why does the gradient all-reduce across replicas only move P/4 data per rank instead of P?

Correct. After the intra-node reduce-scatter (along the "shard" dimension), rank 0 holds gradient shard [0:P/4], rank 1 holds [P/4:P/2], etc. For the replica sync, rank 0 only needs to all-reduce ITS shard with rank 4 (its peer in the replicate group). So each replicate-group all-reduce handles P/4 data, not the full P. This is the multiplicative benefit of HSDP — sharding before replicating reduces the per-link sync volume.

Q3: You have 8 nodes × 4 GPUs and a model where P×16/4 = 5 GB per GPU (fits on V100-32GB). Should you use a (8,4) HSDP mesh or a (2,16) mesh?

Correct. The (8, 4) mesh shards within each 4-GPU NVLink domain (fast) and replicates across 8 nodes (IB). Since P×16/4 = 5 GB fits on V100-32GB, there's no need to shard across nodes. The (2, 16) mesh would shard across 16 GPUs spanning 4 nodes — meaning all-gathers and reduce-scatters would cross InfiniBand, which is 24× slower than NVLink. Always shard within the fastest communication domain when memory allows.

Q4: You notice your multi-node FSDP2 training is slow. You profile and see all-gather latency is high. The mesh is 1-D (8,). What's the most likely fix?

Correct. If all-gather latency is high with a 1-D mesh on multi-node, the problem is that all-gathers span InfiniBand. Switching to HSDP (2,4) confines all-gathers to the intra-node NVLink domain. The cost is adding a gradient all-reduce across replicas — but this moves much less data (P/N_shard) and can overlap with computation. Options A and B might help marginally but don't address the root cause (wrong topology mapping).

Key Takeaways

  1. DeviceMesh maps logical sharding to physical topology. Mesh dimensions correspond to communication domains with different bandwidths.
  2. 1-D mesh: single flat shard group. Use for single-node or when model requires maximum sharding across all GPUs.
  3. 2-D mesh (HSDP): (replicate, shard). Put the fast link (NVLink) on the "shard" dimension, slow link (InfiniBand) on "replicate". All-gathers stay intra-node.
  4. Rank assignment must match node boundaries. torchrun guarantees contiguous rank assignment per node, which maps correctly to row-major mesh filling.
  5. Decision rule: If P×16/GPUs_per_node fits on one GPU → use HSDP. If not → must shard across nodes.
  6. Switching 1-D → 2-D requires only mesh construction change. fully_shard() calls and training loop are unchanged.
  7. Create mesh once, reuse everywhere. Never call init_device_mesh in a loop.
