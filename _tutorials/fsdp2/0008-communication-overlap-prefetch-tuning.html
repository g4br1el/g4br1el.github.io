Understanding CUDA streams, how FSDP2 hides communication latency behind compute, and how to identify when overlap breaks down.

The Fundamental Performance Model

FSDP2's throughput depends on whether communication and computation can run simultaneously. If they can't overlap, you pay the full cost of both sequentially:

Ideal (full overlap): Compute: ████████████████████████████████████████████████ Comms: ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ Step time = max(compute, comms) ← communication is "free" No overlap (sequential): Compute: ████████████████████████ (idle) Comms: (idle) ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ Step time = compute + comms ← communication adds directly to runtime Reality (partial overlap): Compute: ████████████████████████████████████████████████ Comms: ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓████ ← tail exposed Step time = compute + exposed_comm_tail

The goal of prefetch tuning: minimize the exposed communication tail — the portion of communication that isn't hidden behind compute.

CUDA Streams: The Mechanism for Overlap

GPU overlap works because CUDA operations on different streams can execute concurrently (if hardware resources allow):

# Conceptual CUDA stream model in FSDP2:
#
# Stream 0 (default): Compute operations (matmuls, activations, norms)
# Stream 1 (comms):   NCCL collectives (all-gather, reduce-scatter)
#
# Operations on different streams CAN overlap.
# Operations on the SAME stream are sequential.
#
# FSDP2 internally:
#   1. Issues all-gather on Stream 1 (comms stream)
#   2. Returns control to the model's forward on Stream 0 (compute stream)
#   3. Before using the all-gathered result, inserts a stream synchronization
#      (Stream 0 waits for Stream 1 to complete the all-gather)
#
# If the all-gather finishes before Stream 0 needs the result → full overlap
# If the all-gather hasn't finished when Stream 0 needs it → Stream 0 stalls
CUDA Stream Timeline (one FSDP unit): ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Time ──────────────────────────────────────────────────────────────▶ Stream 0 (compute): [Block N-1 compute] [sync wait?] [Block N compute ███████████████] ↑ Wait for AG to complete Stream 1 (comms): [AG Block N ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓] ↑ ↑ Issued during Block N-1 Complete (prefetch!) If AG completes before sync point → no stall (ideal) If AG still in-flight at sync point → compute stalls (bad)

When Overlap Fails

The overlap breaks down in specific situations:

SituationWhy overlap failsOn your V100 cluster
Small model, large batch Compute per layer is fast (finishes before AG completes) → stall at sync Less likely with ViT-Huge (large layers = long compute)
Large model, small batch Compute per layer is fast (small batch) but AG is large (many params) → stall Risk at batch_size=1-2; fine at batch≥16
Slow interconnect AG takes too long relative to compute → can't hide behind one layer's compute Risk with InfiniBand in 1-D mesh (solved by HSDP)
No prefetch AG for block N starts only when block N's forward begins → zero overlap time Fixed by enabling prefetch (default in FSDP2)
PCIe bottleneck If GPU↔NIC goes through PCIe, bandwidth is shared with H2D data transfers V100 SXM2 uses NVLink for GPU-GPU; IB goes through PCIe (separate lanes)

FSDP2 Prefetch Configuration

FSDP2 controls prefetching through the fully_shard API and internal FSDPState configuration:

# As of PyTorch 2.5, prefetch behavior is controlled via:

from torch.distributed._composable.fsdp import fully_shard

# Forward prefetch: start all-gathering block N+1 during block N's compute
# This is ENABLED by default. You rarely need to change it.
for block in model.blocks:
    fully_shard(block, mesh=mesh, mp_policy=mp_policy)
    # Prefetch is automatic — FSDP2 tracks the execution order of FSDP units
    # and issues the next unit's all-gather as soon as the current one starts

# Backward prefetch: during block N's backward, prefetch block N-1's params
# Also enabled by default.

fully_shard(model, mesh=mesh, mp_policy=mp_policy)

How Prefetch Order Is Determined

# FSDP2 determines prefetch order from the execution order:
#
# Forward: blocks execute in order 0, 1, 2, ..., 31
#   → Prefetch: when block i starts forward, issue AG for block i+1
#
# Backward: blocks execute in REVERSE order 31, 30, 29, ..., 0
#   → Prefetch: when block i starts backward, issue AG for block i-1
#
# The FSDPState records execution order during the first forward pass
# (the "lazy initialization" pass) and uses it for all subsequent steps.
#
# This means: the FIRST training step has NO prefetch (FSDP2 is learning
# the execution order). Steps 2+ benefit from prefetch.
# Implication: don't benchmark on step 1.
First-step anomaly: The first training step is always slower because FSDP2 has not yet learned the execution order for prefetching. Always discard the first 1-2 steps when benchmarking. This is also why profiling should start from step 3+.

The Compute-to-Communication Ratio

The key metric for predicting whether overlap will succeed:

# For one FSDP unit (one transformer block):
#
# Compute time (T_compute):
#   FLOPs per block ≈ 2 × batch × seq × hidden² × (4 + 4×mlp_ratio)
#   For ViT-Huge, batch=16, seq=257:
#     ≈ 2 × 16 × 257 × 1280² × (4 + 4×4) = 2 × 16 × 257 × 1638400 × 20
#     ≈ 2.72 × 10¹¹ FLOPs per block
#   V100 fp16 Tensor Core: ~125 TFLOPS peak, ~80 TFLOPS sustained
#   T_compute ≈ 2.72e11 / 80e12 ≈ 3.4 ms per block

# Communication time (T_comm):
#   All-gather data: block params × 4 bytes (fp32) = ~20M × 4 = 76 MB
#   NVLink bandwidth (4 GPUs): ~200 GB/s effective for all-gather
#   T_comm_ag ≈ 76 MB / 200 GB/s ≈ 0.38 ms
#
#   Reduce-scatter: same size = 0.38 ms (but in backward only)

# Ratio:
#   T_compute / T_comm_ag ≈ 3.4 / 0.38 ≈ 9×
#
# Interpretation: compute takes 9× longer than communication
#   → Communication can be FULLY hidden behind compute
#   → FSDP2 overhead should be near-zero on this setup
For ViT-Huge on 4× V100 NVLink: The compute-to-comm ratio is ~9×, meaning communication is easily hidden. You're compute-bound, not communication-bound. This is the ideal regime for FSDP2.

When the Ratio Degrades

ChangeEffect on T_computeEffect on T_commNew ratioOverlap status
batch=4 instead of 16 ÷4 → 0.85 ms Unchanged (params same) ~2.2× Marginal — some exposure
8 GPUs, 1-D mesh (cross IB) ÷2 (smaller batch/rank) IB: 76 MB / 10 GB/s ≈ 7.6 ms ~0.2× ❌ Completely comm-bound
8 GPUs, HSDP (2,4) ÷2 (smaller batch/rank) NVLink: 0.38 ms (AG intra-node) ~4.5× ✓ Good overlap
Smaller model (ViT-Base) ÷10 (86M vs 632M params → less FLOPs) ÷7 (fewer params to gather) ~6× (still good) ✓ Fine
batch=64 (with checkpointing) ×4 → 13.6 ms Unchanged ~36× ✓✓ Trivially compute-bound
Key insight: HSDP exists precisely because the 1-D mesh with InfiniBand destroys the compute-to-comm ratio. Moving all-gathers to NVLink (via HSDP) restores the ratio to a regime where overlap works. This is the quantitative justification for Lesson 005's topology discussion.

Profiling Communication Overlap

Theory is useful, but you need to measure whether overlap is actually happening on your cluster. Two tools:

Tool 1: torch.profiler (Recommended Start)

from torch.profiler import profile, schedule, tensorboard_trace_handler

def train_with_profiling(model, dataloader, optimizer, local_rank):
    """Profile steps 3-7 (skip first 2 for warm-up + prefetch learning)."""

    prof_schedule = schedule(
        wait=1,    # Skip step 0 (unrepresentative)
        warmup=2,  # Steps 1-2: warm-up (profiler overhead stabilizes)
        active=5,  # Steps 3-7: record
        repeat=1,
    )

    with profile(
        activities=[
            torch.profiler.ProfilerActivity.CPU,
            torch.profiler.ProfilerActivity.CUDA,
        ],
        schedule=prof_schedule,
        on_trace_ready=tensorboard_trace_handler(f"./tb_logs/rank{local_rank}"),
        record_shapes=True,
        profile_memory=True,
        with_stack=True,  # Enables source code correlation
    ) as prof:

        for batch_idx, (images, labels) in enumerate(dataloader):
            if batch_idx >= 8:
                break

            images = images.to(local_rank, non_blocking=True)
            labels = labels.to(local_rank, non_blocking=True)

            outputs = model(images)
            loss = nn.functional.cross_entropy(outputs, labels)
            loss.backward()
            optimizer.step()
            optimizer.zero_grad()

            prof.step()  # Signal end of step to profiler

    # After profiling, view in TensorBoard:
    # tensorboard --logdir=./tb_logs

NCCL and SM Contention

A subtle performance issue: NCCL collectives use GPU SMs (Streaming Multiprocessors) to drive communication. On V100 with 80 SMs, NCCL may claim 2-4 SMs for its operations. This means:

# When NCCL and compute overlap:
#   - Compute uses ~76-78 SMs (out of 80)
#   - NCCL uses ~2-4 SMs for its kernels
#   - Compute throughput is reduced by ~2-5%
#
# This "SM sharing tax" is unavoidable but small on V100.
# On newer GPUs (H100), NCCL can use a dedicated copy engine
# without stealing SMs.
#
# Practical impact: your sustained compute throughput during FSDP2 training
# is ~95-98% of what a standalone benchmark would show.
# This is NOT a bug — it's the cost of overlap.

Tuning the Overlap: What You Can Control

1. Batch Size (Most Impactful)

# Larger batch → more compute per FSDP unit → easier to hide communication
#
# ViT-Huge on 4× V100:
#   batch=4:  T_compute ≈ 0.85 ms, T_comm ≈ 0.38 ms → ratio 2.2×  (tight)
#   batch=16: T_compute ≈ 3.4 ms,  T_comm ≈ 0.38 ms → ratio 9×    (comfortable)
#   batch=64: T_compute ≈ 13.6 ms, T_comm ≈ 0.38 ms → ratio 36×   (trivial)
#
# Rule of thumb: if ratio > 3×, overlap is fine. If < 2×, expect visible stalls.

2. FSDP Unit Granularity

# Coarser units → larger all-gathers (more data, longer time)
#                  but also more compute between them
# Finer units → smaller all-gathers (less data, shorter time)
#               but less compute between them (less time to hide comms)
#
# For ViT-Huge with per-block sharding:
#   AG size: 20M params × 4 bytes = 76 MB (moderate)
#   Compute per block: 3.4 ms at batch=16 (plenty of overlap time)
#
# If you sharded per-LAYER (attention, MLP separately):
#   AG size: ~10M params × 4 = 38 MB (smaller, faster to gather)
#   Compute per sub-block: ~1.7 ms (less time to overlap with NEXT AG)
#   Net effect: similar overlap quality, but more collective calls → more latency events
#
# Recommendation: per-block is the sweet spot for transformers.
# Only go finer if a single block doesn't fit unsharded.

3. NCCL Environment Variables

# Tuning NCCL for your V100 NVLink/IB cluster:

# Number of channels (parallel communication lanes)
# More channels → higher bandwidth utilization, more SM usage
# Default is usually fine, but can tune:
export NCCL_MIN_NCHANNELS=4
export NCCL_MAX_NCHANNELS=8

# Algorithm selection for all-gather:
# Ring: good for intra-node NVLink (balanced load)
# Tree: good for cross-node IB (lower latency for small messages)
# Default: NCCL auto-selects based on message size and topology
export NCCL_ALGO=Ring  # or Tree, or leave unset for auto

# Thread model: affects how NCCL interacts with GPU scheduling
export NCCL_NTHREADS=512  # default, rarely needs changing

# Debug: see what NCCL is doing
export NCCL_DEBUG=INFO    # Verbose (shows topology detection, algorithm selection)
export NCCL_DEBUG=WARN    # Quiet (only errors/warnings)

# Network interface selection (for InfiniBand):
export NCCL_IB_HCA=mlx5   # Select IB adapter (if multiple)
export NCCL_SOCKET_IFNAME=ib0  # Fallback interface

# IMPORTANT for V100 NVLink:
# NCCL auto-detects NVLink topology. If it fails to detect:
export NCCL_P2P_LEVEL=NVL  # Force NVLink for peer-to-peer
Don't over-tune NCCL. The defaults work well for standard topologies. Only set these if profiling reveals specific issues (e.g., NCCL choosing Tree when Ring would be faster for your all-gather sizes). Most performance gains come from batch size and HSDP, not NCCL knobs.

4. Gradient Accumulation (Advanced)

If you can't increase batch size (memory limit) but want to improve the compute-to-comm ratio:

def train_with_gradient_accumulation(
    model, dataloader, optimizer,
    local_rank, accumulation_steps: int = 4
):
    """
    Accumulate gradients over multiple micro-batches before communication.

    With FSDP2: each forward/backward STILL triggers all-gather + reduce-scatter
    for EACH micro-batch. Gradient accumulation does NOT eliminate communication!

    But it allows you to use a smaller per-step batch (fitting in memory)
    while achieving the effective batch size of accumulation_steps × micro_batch.

    Communication overhead: same per micro-batch. No overlap improvement.
    Use case: when you need large effective batch but can't fit it in one go.
    """
    model.train()
    optimizer.zero_grad()

    for batch_idx, (images, labels) in enumerate(dataloader):
        images = images.to(local_rank, non_blocking=True)
        labels = labels.to(local_rank, non_blocking=True)

        # Forward + backward (triggers FSDP2 communication)
        outputs = model(images)
        loss = nn.functional.cross_entropy(outputs, labels)
        # Scale loss by accumulation steps to average gradients
        (loss / accumulation_steps).backward()

        if (batch_idx + 1) % accumulation_steps == 0:
            torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
            optimizer.step()
            optimizer.zero_grad()
Gradient accumulation with FSDP2 does NOT reduce communication. Each micro-batch still requires full all-gather + reduce-scatter. Unlike DDP where you can skip gradient sync on intermediate steps (model.no_sync()), FSDP2 must all-gather for every forward (params are sharded — you can't compute without them). Gradient accumulation is useful for effective batch size but NOT for communication reduction.

The no_sync() Caveat

# In DDP:
#   with model.no_sync():  ← skips all-reduce on this step
#       loss.backward()    # Gradients accumulate locally
#   loss.backward()        # This step DOES sync
#
# In FSDP2:
#   There is no equivalent "skip communication" for forward/backward.
#   The all-gather is REQUIRED for forward (can't compute without full params).
#   The reduce-scatter CAN theoretically be deferred, but FSDP2 doesn't expose
#   this cleanly in the current API.
#
# FSDP2 does support set_requires_gradient_sync(False) for the reduce-scatter:
#   → Skips the reduce-scatter, accumulates Partial gradients locally
#   → But local grads are full-sized (not sharded) → USES MORE MEMORY
#   → And all-gather still happens every forward
#
# Net: gradient accumulation with FSDP2 saves no communication on forward,
# and the backward savings require careful memory management.
# It's mainly useful for matching effective batch sizes, not performance.

Measuring Overlap Quality

A practical script to estimate overlap efficiency without a full profiler:

import torch
import time
import torch.distributed as dist


def measure_overlap_efficiency(
    model: torch.nn.Module,
    dataloader,
    local_rank: int,
    num_steps: int = 20,
) -> dict:
    """
    Estimate overlap efficiency by comparing actual step time
    to theoretical compute-only time.

    Method: Run FSDP2 training steps and compare to a single-GPU
    (non-distributed) baseline at the same batch size per GPU.

    Overlap efficiency = 1 - (fsdp_time - compute_time) / comm_time
    Where:
      fsdp_time = actual FSDP2 step time
      compute_time ≈ time for same model forward+backward without communication
      comm_time = measured communication time (from profiler)

    Simpler proxy: compare throughput to single-GPU throughput.
    If FSDP2 with N GPUs gives N× throughput → perfect overlap.
    """
    model.train()

    # Warm up (first 2 steps: prefetch learning + CUDA warm-up)
    warmup_iter = iter(dataloader)
    for _ in range(3):
        images, labels = next(warmup_iter)
        images = images.to(local_rank, non_blocking=True)
        labels = labels.to(local_rank, non_blocking=True)
        outputs = model(images)
        loss = torch.nn.functional.cross_entropy(outputs, labels)
        loss.backward()
        model.zero_grad()

    torch.cuda.synchronize()
    dist.barrier()

    # Measure
    step_times = []
    data_iter = iter(dataloader)

    for step in range(num_steps):
        images, labels = next(data_iter)
        images = images.to(local_rank, non_blocking=True)
        labels = labels.to(local_rank, non_blocking=True)

        torch.cuda.synchronize()
        start = time.perf_counter()

        outputs = model(images)
        loss = torch.nn.functional.cross_entropy(outputs, labels)
        loss.backward()
        model.zero_grad()

        torch.cuda.synchronize()
        end = time.perf_counter()

        step_times.append(end - start)

    avg_step = sum(step_times) / len(step_times)
    std_step = (sum((t - avg_step)**2 for t in step_times) / len(step_times)) ** 0.5

    # Compute throughput
    batch_size = next(iter(dataloader))[0].shape[0]
    world_size = dist.get_world_size()
    throughput = batch_size * world_size / avg_step

    results = {
        "avg_step_ms": avg_step * 1000,
        "std_step_ms": std_step * 1000,
        "throughput_img_per_sec": throughput,
        "per_gpu_throughput": throughput / world_size,
        "step_times_ms": [t * 1000 for t in step_times],
    }

    if local_rank == 0:
        print(f"Average step: {results['avg_step_ms']:.2f} ± {results['std_step_ms']:.2f} ms")
        print(f"Throughput: {results['throughput_img_per_sec']:.0f} img/s "
              f"({results['per_gpu_throughput']:.0f} per GPU)")

        # Compare to expected:
        # If per_gpu_throughput ≈ single_gpu_throughput → overlap is good
        # If per_gpu_throughput << single_gpu_throughput → communication exposed

    return results

Check Your Understanding

Q1: On your V100 cluster with ViT-Huge (batch=16, 4 GPUs NVLink), the compute-to-comm ratio is ~9×. What does this predict about FSDP2's overhead?

Correct. A 9× ratio means the all-gather completes in ~1/9 of the time that the next block's compute takes. With prefetching (start AG during current compute), the all-gather finishes well before it's needed. The exposed tail is effectively zero. The only overhead is the ~2-5% SM sharing tax from NCCL using a few SMs during overlap. Measured scaling efficiency should be 95-98%.

Q2: You profile your 2-node FSDP2 training and see that the compute stream is idle for 4ms between each block's forward pass. What's the most likely cause?

Correct. A 4ms gap in the compute stream between blocks means the GPU is waiting for the all-gather to deliver the next block's parameters. The prefetch started during the previous block's compute, but the previous block's compute wasn't long enough to hide the all-gather latency (especially over InfiniBand). Fix: switch to HSDP (move all-gathers to NVLink), or increase batch size (more compute time to hide the latency).

Q3: Why doesn't gradient accumulation reduce FSDP2's communication volume per effective batch?

Correct. Unlike DDP where you can skip gradient all-reduce on intermediate micro-batches (model.no_sync()), FSDP2 MUST all-gather parameters for every forward pass — the parameters are sharded, so you literally cannot compute without gathering them first. The only potentially skippable communication is the reduce-scatter of gradients (defer to last micro-batch), but the all-gather cost (which is 2/3 of total FSDP communication) remains per micro-batch.

Q4: The first training step is always slower than subsequent steps with FSDP2. Why?

Correct. FSDP2's prefetch system needs to know the order in which FSDP units execute (to prefetch the NEXT unit). This order is recorded during the first forward pass. Step 1 has NO prefetch — each all-gather starts only when the hook fires (no ahead-of-time communication). Steps 2+ use the recorded order to issue prefetch all-gathers early. Note: answers A and C are ALSO true for the very first step but apply to DDP equally — the FSDP2-specific first-step penalty is the lack of prefetch.

Key Takeaways

  1. Overlap works via CUDA streams: compute on Stream 0, NCCL on Stream 1. They run concurrently unless Stream 0 stalls waiting for a result from Stream 1.
  2. Compute-to-comm ratio > 3× → good overlap. For ViT-Huge on V100 NVLink: ratio ~9× (batch=16). Communication is trivially hidden.
  3. HSDP exists to fix the ratio on multi-node. InfiniBand all-gathers destroy the ratio (0.2×). HSDP moves them to NVLink (4.5×).
  4. Prefetch is automatic but learned on step 1. Always discard step 1 for benchmarking. Steps 2+ have prefetch.
  5. Gradient accumulation does NOT reduce FSDP2 communication. All-gathers happen every micro-batch (can't compute without full params).
  6. Profile before tuning. Use torch.profiler → TensorBoard trace. Look for gaps in compute stream = exposed communication.
  7. Tuning priority: (1) HSDP topology, (2) batch size, (3) NCCL env vars, (4) FSDP unit granularity. Most gains come from (1) and (2).
