Before you can shard, you must know exactly what you're sharding and why.

The Memory Budget of a Single GPU

During mixed-precision training with AdamW, GPU memory is consumed by four categories. Let's quantify each for a concrete model:

Running example: ViT-Huge/14 — 632M parameters.

CategoryFormulaViT-H (632M params)Notes
Parameters (fp16 copy) P × 2 bytes 1.2 GB Used in forward/backward
Parameters (fp32 master copy) P × 4 bytes 2.4 GB Maintained by optimizer
Gradients (fp16) P × 2 bytes 1.2 GB Accumulated during backward
Optimizer states (Adam: m + v, fp32) P × 4 × 2 = P × 8 bytes 4.8 GB First & second moment
Σ Model-proportional P × 16 bytes 9.6 GB
Activations Depends on batch, seq_len, hidden_dim ~8–20+ GB Dominant for large batches/resolutions
Temporary buffers + fragmentation ~5–15% overhead ~1–3 GB cuDNN workspace, NCCL buffers
Key insight: For a 632M-param model with AdamW in mixed precision, you need ~9.6 GB just for model-proportional state before a single activation is stored. On a V100-32GB, that leaves ~22 GB for activations — which at batch_size=1 with 224×224 inputs might be fine, but at higher resolutions (512×512, 1024×1024) or batch_size > 1, you overflow.

What DDP Does (And Doesn't Do)

DDP's memory model is simple: full replication.

┌─────────────── Rank 0 (GPU 0) ───────────────┐ ┌─────────────── Rank 1 (GPU 1) ───────────────┐ │ │ │ │ │ Parameters (full) 1.2 GB │ │ Parameters (full) 1.2 GB │ │ FP32 master weights 2.4 GB │ │ FP32 master weights 2.4 GB │ │ Gradients (full) 1.2 GB │ │ Gradients (full) 1.2 GB │ │ Optimizer states (full) 4.8 GB │ │ Optimizer states (full) 4.8 GB │ │ Activations (1/N batch) variable │ │ Activations (1/N batch) variable │ │ │ │ │ │ Communication: all-reduce gradients only │ │ Communication: all-reduce gradients only │ └────────────────────────────────────────────────┘ └────────────────────────────────────────────────┘

DDP splits the data (each rank processes a shard of the batch), but every rank holds:

  • A complete copy of all parameters
  • A complete copy of all gradients
  • A complete copy of all optimizer states (master weights + Adam m + v)

The only communication is an all-reduce on gradients after backward. This is bandwidth-efficient (single collective) but memory-wasteful — every GPU stores redundant copies of the same model state.

The wall: If the model-proportional memory (9.6 GB for ViT-H) + activations for even batch_size=1 exceeds 32 GB, DDP cannot train the model at all. Adding more GPUs does not help — each one still needs the full model.

The Sharding Insight

The ZeRO insight (Rajbhandari et al., 2020) is that the redundancy in DDP is eliminable. If you have N GPUs, each one can hold 1/N of the model state, and reconstruct what it needs on-the-fly via communication:

ZeRO StageWhat's shardedMemory per GPU (model-proportional)Communication cost vs DDP
DDP (no sharding) Nothing P × 16 bytes 1× (all-reduce grads)
Stage 1 Optimizer states P × (4+2+2) + P×8/N = P×8 + P×8/N 1× (same as DDP)
Stage 2 Optimizer states + gradients P×4 + P×2 + (P×2 + P×8)/N 1× (same as DDP)
Stage 3 (= FSDP) Optimizer states + gradients + parameters P × 16 / N 1.5× (all-gather fwd + all-gather bwd + reduce-scatter grads)
FSDP = ZeRO Stage 3 in PyTorch-native form.
With 8 GPUs: model-proportional memory drops from 9.6 GB to 1.2 GB per GPU. The price: 50% more communication volume (but this can be overlapped with compute).

Communication Pattern: DDP vs FSDP

DDP Communication (per training step): ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Forward: (no communication) Backward: all-reduce(gradients) ← 2×P bytes total across ring Optimizer: (local, no communication) FSDP Communication (per training step): ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Forward: all-gather(parameters) ← P bytes per layer, before use Backward: all-gather(parameters) ← P bytes per layer, before grad compute reduce-scatter(gradients) ← P bytes per layer, after grad compute Optimizer: (local on sharded state, no communication) Total DDP: 2P bytes Total FSDP: 3P bytes (1.5× DDP)

The 1.5× communication increase is the fundamental trade-off. On your V100 cluster with NVLink (300 GB/s intra-node) and InfiniBand (100 Gb/s inter-node), this is often acceptable because:

  1. Communication can be overlapped with compute (prefetch next layer's all-gather during current layer's compute)
  2. The alternative (DDP) is impossible — the model doesn't fit
  3. For large models, the compute-to-communication ratio is favorable

Let's do the concrete math for ViT-Huge on your setup:

FSDP, 32 GPUs0.3 GB~31 GB✓ Can increase batch size significantly
Important nuance: The table above shows steady-state memory. During an all-gather, a GPU temporarily holds the full unsharded parameter tensor for the current layer (or group of layers). FSDP manages this by gathering and discarding per-layer. Peak memory is: sharded_model_state + largest_unsharded_layer + activations.

What FSDP2 Adds Over FSDP1

This lesson focuses on the why. Lesson 002 will cover the architectural differences between FSDP1 and FSDP2 in detail. The key motivations for FSDP2:

  • Composability: FSDP1's wrapper class (FullyShardedDataParallel) fights with torch.compile, activation checkpointing, and custom module logic. FSDP2 uses a functional API (fully_shard()) that mutates modules in-place.
  • DTensor substrate: Parameters become DTensor objects with explicit placement semantics — no more opaque FlatParamHandle.
  • Per-parameter sharding: No flattening into mega-tensors. Each parameter retains its identity, enabling torch.compile to trace through cleanly.

Check Your Understanding

Q1: In DDP with 8 GPUs training a 1B-param model with AdamW (fp16 mixed precision), what is the total model-proportional memory across all GPUs combined?

Correct: 128 GB. DDP replicates everything. 1B × 16 bytes = 16 GB per GPU × 8 GPUs = 128 GB total. FSDP would reduce this to 16 GB total (2 GB per GPU).

Q2: FSDP increases communication volume by 1.5× compared to DDP. Where does the extra 0.5× come from?

Correct. DDP: 2P (all-reduce = reduce-scatter + all-gather of gradients). FSDP: P (all-gather params in fwd) + P (all-gather params in bwd) + P (reduce-scatter grads) = 3P total. The "extra" P comes from needing parameters gathered before forward compute — something DDP never needs because it already has them in full.

Q3: On your V100-32GB cluster, what determines whether FSDP enables a larger batch size vs. merely making training possible?

Correct. If DDP already fits (model-prop. mem + activations < 32 GB), then FSDP's benefit is freeing memory for larger batch sizes or higher resolutions. If DDP doesn't fit at all, FSDP is what makes training possible. For ViT-H at high resolution with batch > 1, you're likely in the "makes it possible" regime.

Key Takeaways

  1. Mixed-precision AdamW training costs 16 bytes per parameter in model-proportional memory.
  2. DDP replicates all of this on every GPU — adding GPUs doesn't reduce per-GPU memory.
  3. FSDP (ZeRO-3) shards all model state across N GPUs → P×16/N per GPU.
  4. The cost is 1.5× communication volume (all-gather in forward + all-gather + reduce-scatter in backward).
  5. Peak memory includes the temporarily-unsharded current layer — FSDP is not "memory free."
